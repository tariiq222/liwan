# دليل تشغيل ليوان SaaS التجاري

آخر تحديث: 2026-10-22. الحالة: **مسودة تشغيل جزئية، لا إعلان جاهزية.** بدأ هذا الدليل كمسودة في 2026-10-02 اعتمادًا على worktree `codex/saas-commercial`. الشيفرة الحالية تتضمن مسارات webhook والدفع والتجديد والمصالحة، ومجدولًا في العامل المشترك، وواجهة عمليات تجارية. هذا يثبت وجود مسارات في المصدر فقط؛ لا يثبت قبول إجراءات هذا الدليل أو تشغيل العامل في staging أو production. تبقى كل خطوة موسومة بقبول تشغيلي غير متحقق خارج نطاق التنفيذ حتى يُنجز قبولها في البيئة المقصودة.

## مفتاح حالة التحقق

| الوسم | المعنى |
|---|---|
| **[محلي]** | له دليل تشغيل أو اختبار محلي/scratch؛ لا يثبت إنتاجًا |
| **[غير مختبر]** | الإجراء التشغيلي نفسه لم يُنفذ في البيئة المقصودة |
| **[قبول تشغيلي غير متحقق]** | مسار التنفيذ موجود في المصدر، لكن قبول الإجراء end-to-end لم يُثبت |
| **[محجوب]** | يتطلب بيئة أو مزودًا أو إعدادًا لم يُتحقق من توفره (مثل staging أو SMTP) |

لا يقدّم هذا الدليل وعد SLA تجاريًا؛ أهداف RPO (ساعة) وRTO (أربع ساعات) معتمدة بقرار المالك 2026-11-06 والمرجع لها §5، أما أهداف السعة وSLA التجاري فما زالت مفتوحة (القرارات المفتوحة في `docs/project-closure/saas-hosting-direction-status.md`).

## 1. المكوّنات

| المكوّن | الدور | ملاحظات |
|---|---|---|
| `control-api` | واجهة التحكم (`apps/control-plane/src/http.ts` و`commercial/http.ts` تحت `/v1/commercial`) | مصدر الاتفاق التجاري والأسعار والإصدارات؛ طلبات الواجهة موقّعة عبر BFF |
| `control-worker` | تنفيذ المهام (`src/worker-main.ts`) | لا مجدول فيه |
| `control-worker-shared` | العامل المشترك (`src/shared-worker-main.ts`، سكربت `npm -w apps/control-plane run worker:shared`) | العملية الوحيدة التي تشغّل المجدول التجاري وتدفع حالة المستأجر إلى Odoo. مدخلها [run-shared-worker.sh](../../deploy/control-plane/run-shared-worker.sh) ووحدتها [liwan-shared-worker.service](../../deploy/control-plane/liwan-shared-worker.service) |
| `commercial_outbox` | جدول أحداث خارجة (`schema_013.sql`): `kind, aggregate_id, dedupe_key, status ∈ pending/done/failed` | فريد على (kind, aggregate_id, dedupe_key) لمنع التكرار |
| reconfigure jobs | مهام تغيير الخدمة بعد الاتفاق/الدفع (`shared/job-*`)، وأثرها في `fulfillment_effects` (إيصال، `observed_digest`) | لا يُعلن «applied» قبل readback من Odoo |
| محوّل Moyasar | `commercial/moyasar-adapter.ts`: فاتورة مستضافة + redirect، webhook، token، استرداد | الـwebhook يحمل `secret_token` مشتركًا (بلا HMAC)؛ يُعاد فحص الحالة من المزود قبل الاعتماد |
| محوّل البريد | `commercial/mail-adapter.ts`: SMTP لدعوة المسؤول | رموز الدعوة في `invitation-tokens.ts` |
| محاكي الدفع | `commercial/payment-simulator.ts` | **للاختبار فقط**؛ يرفض الإنتاج و`MOYASAR_MODE=live`. ليس دليل دفع حقيقي |
| مساحات Odoo | قاعدة وfilestore لكل عميل خلف Odoo مشترك | العزل database-per-tenant |

جداول الحالة الأساسية: `orders` (`payment_state`: not_required/awaiting_payment/paid/refund_pending/refunded؛ `fulfillment_state`: not_started/queued/applying/applied/failed/needs_intervention)، `invoices` (draft/issued/paid/void/credit_pending)، `payment_attempts` (created/redirected/pending/succeeded/failed/canceled/unknown)، `payment_events`، `subscriptions` (pending/trialing/active/past_due/suspended/cancelled)، `renewals` (invoiced/charging/paid/past_due/suspended/failed)، `commercial_branches`، `usage_snapshots` (fresh/stale/unavailable).

## 2. الإعداد (أسماء المتغيرات فقط — لا قيم في هذا الملف)

تُحقن عبر بيئة العملية/مدير أسرار، ولا تُسجَّل ولا تُمرَّر في سطر الأوامر. المحوّل يرفض التشغيل عند نقص أي متغير مطلوب (`provider_not_configured` / `mail_not_configured`).

| المتغير | الاستخدام |
|---|---|
| `LIWAN_PAYMENT_PROVIDER` | `moyasar` أو `simulator` (غيرها يرفض) |
| `MOYASAR_MODE` | `test` أو `live` فقط؛ `live` يُستخدم بعد تفويض إنتاج صريح |
| `MOYASAR_SECRET_KEY` | مفتاح API (سر) |
| `MOYASAR_PUBLISHABLE_KEY` | المفتاح العام (`pk_test_` مع `test`، `pk_live_` مع `live`)، لازم للدفع بالبطاقة عبر النموذج فقط؛ الفواتير والتجديدات والاستردادات تعمل بدونه. ليس سرًا لأن المتصفح يحتاجه. عدم تطابقه مع `MOYASAR_MODE` يعطّل محوّل الدفع عند الإقلاع (`key_mode_mismatch`) |
| `MOYASAR_WEBHOOK_REGISTRATION` | اتركه فارغًا. `open` فقط أثناء تسجيل الـwebhook (انظر 4.2) |
| `MOYASAR_WEBHOOK_SECRET` | سر الـwebhook (`secret_token`) (سر)، 32 بايت على الأقل؛ الأقصر يعطّل محوّل الدفع ويُسجَّل السبب عند الإقلاع |
| `MOYASAR_ACCOUNT_NAME` | اسم حساب التاجر؛ أي webhook بحساب آخر يُرفض (`merchant_mismatch`) |
| `LIWAN_PAYMENT_RETURN_ORIGINS` | قائمة مسموحة لعودة الدفع مفصولة بفواصل. كل عنصر origin كامل (`https://app.example.com`) أو نمط `https://*.example.com` (مضيف واحد أو أكثر تحت اللاحقة، وللّاحقة تسمية واحدة على الأقل قبل النطاق الأعلى). في وضع dedicated يُستخدم أول عنصر فقط ولا يقبل النمط. في وضع shared (`LIWAN_TENANCY_MODE=shared`) تُبنى روابط عودة كل عميل من مضيف ربطه المفعّل في سجل المستأجرين، ويجب أن يطابق القائمة؛ عميل له مستأجر بلا ربط مفعّل أو بمضيف خارج القائمة يُرفض بـ`return_url_forbidden` (422) قبل أي كتابة |
| `LIWAN_PAYMENT_PROSPECT_ORIGIN` | وضع shared فقط: origin كامل بلا نمط (`https://app.example.com`) لنطاق ليوان العام، ويجب أن يكون ضمن `LIWAN_PAYMENT_RETURN_ORIGINS`. إليه تعود دفعة عميل لا مستأجر له بعد (أول طلب غير مدفوع)، وتعرض الويب هناك صفحة `/payment-done` فقط (مع ترحيل نداء الدفع وملفات البناء) بعد التحقق من رمز الوكيل المشترك، ويجب أن يطابق `NUXT_CUSTOMER_COMMERCIAL_PUBLIC_ORIGIN` مضيفه. غير مضبوط: يُرفض هذا العميل بـ`return_url_forbidden` (422). يضبط الحارس المشترك مضيفه في `LIWAN_PROSPECT_HOST` (مضيف بلا مخطط)، فيمرّر لهذا المضيف وحده المسارات الثلاثة المذكورة مع حقن رمز الوكيل، ويبقى كل مضيف آخر غير مسجل مرفوضًا |
| `LIWAN_MAIL_MODE` | الافتراضي `smtp`؛ غيره يرفض |
| `LIWAN_MAIL_SMTP_HOST`, `LIWAN_MAIL_SMTP_PORT`, `LIWAN_MAIL_FROM` | وجهة الإرسال والمرسِل |
| `LIWAN_MAIL_REQUIRE_TLS` | إلزام TLS |
| `LIWAN_MAIL_SMTP_USER`, `LIWAN_MAIL_SMTP_PASSWORD` | اعتماد SMTP اختياري (سر) |

يوثق [سجل قبول الاستضافة والتجارة، السطر 45](../project-closure/saas-hosting-direction-status.md) اتصالًا حقيقيًا بوضع Moyasar التجريبي في 2026-10-04 لإنشاء فاتورة وقراءتها ورفض مفاتيح الوضع الخاطئ 3/3. هذا لا يثبت توفر المفاتيح الآن أو اكتمال الدفع أو قبول webhook عبر HTTPS عام. توفر staging وSMTP لم يُتحقق منه في هذا التحديث **[محجوب]**. مفاتيح الإنتاج لا تُستخدم في اختبار محلي أبدًا.

### تشغيل العامل المشترك

العامل المشترك (`apps/control-plane/src/shared-worker-main.ts`) هو العملية الوحيدة
التي تشغّل المجدول التجاري وتدفع حالة المستأجر إلى Odoo. غيابه يعني أن التعليق
والتجديد يغيّران قاعدة التحكم فقط ولا يصلان إلى مساحة العميل. يُشغَّل بثلاث طرق
فقط، وكلها تستدعي `deploy/control-plane/run-shared-worker.sh` نفسه:

| البيئة | الآلية | التحقق |
|---|---|---|
| محلية/قبول | `deploy/control-plane/run-local.sh` عند `LIWAN_TENANCY_MODE=shared` في `runtime.env` (يبدأ `shared-worker` ويسجّل pid/start/generation مثل `api` و`worker`) | `deploy/control-plane/status-local.sh` يطبع سطر العامل المشترك |
| خادم оператор | وحدة systemd [liwan-shared-worker.service](../../deploy/control-plane/liwan-shared-worker.service) | `systemctl status liwan-shared-worker` و`journalctl -u liwan-shared-worker` |
| اختبار قبول | `tools/foundation_acceptance/provision_two_tenants.mjs` و`tools/saas_e12/recovery.mjs` | يراقبان `commercial_scheduler_tick` في سجل العامل |

**لماذا لا يوجد service في `deploy/docker-compose.shared.yml`:** شيفرة لوحة التحكم
ليست داخل صورة `liwan-guard` (ولا Node dependencies لها ولا `tsx` ولا عميل Docker)،
والعامل يحتاج مقبس Docker ليشغّل تأثيرات Odoo (`tools/shared_saas_lifecycle`). إضافة
service صحيح تعني صورة كاملة جديدة وعقد أسرار كامل وشبكة تصل إلى كل حاويات المستأجرين
— وهذا خارج هذا التغيير. لذلك المشرف الفعلي هو وحدة systemd على المضيف، لا خدمة Compose.

**التهيئة.** يعمل في المقدمة ويتلقى إشارات الإيقاف مباشرة. استخدم إصدار Node من
`.nvmrc` وثبّت الاعتماديات مع اعتماد التطوير `tsx` عبر
`npm ci --include=dev --ignore-scripts` في نسخة الشيفرة التي سيشغّلها المشرف.
اضبط `LIWAN_TENANCY_MODE=shared` واحقن إعدادات قاعدة التحكم وهوية الخدمة
والمخزون وحالة المشغّل في بيئة العملية. اضبط `LIWAN_SHARED_RUNTIME_CONFIG`
على ملف إعداد التشغيل المشترك و`LIWAN_TENANT_REGISTRY_PATH` على سجل المستأجرين،
بمسارات مطلقة (يرفض `run-local.sh` وضع shared بدونهما). يحتاج العامل إلى الوصول إلى
Docker الخاص بالمكدس؛ تُمرَّر إعدادات قناة الدعوات الداخلية إلى الـAPI والعامل حسب
[عقد TLS والأسرار](../../deploy/shared/README.md). ملف بيئة systemd يستخدم
`KEY=value` بلا `export` (خلافًا لـ`runtime.env` المحلي الذي يكتبه `init-local.sh`).

**التحقق من أن العامل حي.** لا يوجد مسار HTTP خاص به. الدليل الوحيد هو السجل:
المجدول يطبع `console.debug` في `apps/control-plane/src/commercial/scheduler.ts`
سطرًا واحدًا لكل دورة بالصيغة
`{"event":"commercial_scheduler_tick","tick":<n>,"jobs":{...}}`. راقب تكراره:

```sh
journalctl -u liwan-shared-worker -f | grep --line-buffered commercial_scheduler_tick
```

عدم ظهور السطر بعد دورة كاملة يعني عاملًا متوقفًا أو عالقًا قبل أول tick؛ لا تعتبر
`systemctl is-active` وحده دليلًا. في التشغيل المحلي يكون السجل في
`$LIWAN_CONTROL_HOME/logs/shared-worker.log`، و`status-local.sh` يتحقق من
argv/start time/سجل الجيل. رد `GET /healthz` برمز 200 من واجهة التحكم يثبت
اتصالها بقاعدة التحكم فقط، لا حياة العامل.

للتحقق من العامل في قبول معزول، يشغّل [اختبار القبول المعزول](../../tools/foundation_acceptance/README.md)
مدخل التشغيل نفسه ويراقب تجهيز مستأجرين حقيقيين حتى يصبحا نشطين.

## 3. حسابات لوحة تحكم ليوان

الصلاحيات مشتقة من أدوار الحساب (`owner` وغيره)؛ لم يعد هناك منح أو إلغاء يدوي بمعرّف Odoo (أُزيل الأمران `grant` و`revoke`). الأوامر أدناه تتطلب ضبط `ADMIN_SECRET_KEY` و`ADMIN_RP_ID` و`ADMIN_ORIGIN`؛ وبدونها ترفض التنفيذ.

أول مالك للوحة (من خادم التشغيل، من `apps/control-plane`؛ يشغّل `migrate` أولًا ويكتب `audit_events` بالفاعل `operator`):

```sh
npm -w apps/control-plane run admin -- bootstrap-owner <email> "<الاسم الظاهر>" "<سبب 3-1000 حرف>"
```

يطبع سطرًا واحدًا فقط: `<ADMIN_ORIGIN>/enroll#<token>`، وهو رابط يفتح في تطبيق `apps/vendor-admin` على مضيف `admin` (الرمز بعد `#` لا يصل إلى الخادم ولا إلى السجلات). يرفض الأمر مع الرسالة `owner already exists` إذا وُجد أي حساب غير معطّل (نشط أو قيد التسجيل) يحمل دور المالك.

إعادة تعيين مالك مقفل خارج حسابه (أو أي حساب غير معطّل):

```sh
npm -w apps/control-plane run admin -- reset-account <email> "<سبب 3-1000 حرف>"
```

يطبع رابط إعادة تعيين بالصيغة نفسها؛ بريد غير معروف أو حساب معطّل يعيد خطأً عامًا بلا تفصيل.

- الرابط يُرسل يدويًا إلى صاحب الحساب عبر قناة موثوقة، وينتهي بعد 24 ساعة، ويُستعمل مرة واحدة.
- الرابط يظهر مرة واحدة فقط في الطرفية: لا تلصقه في أدوات الدردشة أو التذاكر أو السجلات. إن ضاع فأصدر رابطًا جديدًا (الإصدار الجديد يلغي القديم).
- لا تضع كلمة مرور أو مفتاحًا في سطر الأوامر. **[محلي]** السلوك مختبر على قاعدة scratch فقط؛ لم يُشغَّل أمام staging.

### تشغيل لوحة التحكم محليًا (`apps/vendor-admin`)

1. جهّز لوحة التحكم (`apps/control-plane`) بقاعدة scratch ومنفذ حر، وأضف إلى بيئتها: `ADMIN_SECRET_KEY` (32 بايت على الأقل، ومختلف عن كل مفتاح خدمة) و`ADMIN_RP_ID=localhost` و`ADMIN_ORIGIN=http://localhost:3100`.
2. أنشئ المالك الأول بالأمر `bootstrap-owner` أعلاه، واحتفظ بالرابط المطبوع (يظهر مرة واحدة).
3. شغّل التطبيق من جذر المستودع (Node 22):

```sh
export NUXT_CONTROL_URL=http://127.0.0.1:<منفذ لوحة التحكم>
export NUXT_SERVICE_KEY=<قيمة CONTROL_SERVICE_KEY نفسها>
export NUXT_INSTALLATION_ID=<قيمة CONTROL_INSTALLATION_ID نفسها>
export NUXT_ADMIN_ORIGIN=http://localhost:3100
npm -w apps/vendor-admin run dev -- --port 3100
```

4. افتح الرابط المطبوع (`http://localhost:3100/enroll#...`) في المتصفح، وأكمل تسجيل مفتاح المرور (passkey) وكلمة المرور ورمز TOTP، واحفظ رموز الاسترداد.
5. على خادم الإنتاج يُخدَّم التطبيق من مضيف `admin` المستقل (قالب البيئة `deploy/vendor-admin/env.example` وكتلة الحافة `deploy/vendor-admin/Caddyfile.snippet`)، و`ADMIN_ORIGIN` في لوحة التحكم يساوي `NUXT_ADMIN_ORIGIN` حرفيًا. **[محلي]** لم يُجرَّب أمام staging.

شرح المتغيرات وحدود التطبيق في `apps/vendor-admin/README.md`.

أوامر admin أخرى: `catalog-import <version> <reason>`، `approve-restore <tenant_uuid> <op_backup_id> <reason>` (موافقة ساعة واحدة).

## 4. إجراءات التشغيل

> كل إجراء يبدأ بالقراءة فقط. لا تعدّل جداول مباشرة؛ الحالة المالية لها triggers تمنع التراجع (مثل `order_payment_regression`).

### 4.1 طلب عالق: مدفوع ولم يُطبَّق [قبول تشغيلي غير متحقق] [غير مختبر]

1. حدّد الطلب: `orders` حيث `payment_state='paid'` و`fulfillment_state` ليس `applied`.
2. اقرأ `fulfillment_effects` للطلب: `job_id`، `operation_id`، `receipt`، `observed_digest`، `applied_at`.
3. اقرأ المهمة في طابور العمليات وسجل `audit_events`، وأحداث `commercial_outbox` للطلب (`pending/failed`).
4. التشخيص:

| الحالة | المعنى | الإجراء |
|---|---|---|
| `queued`/`applying` ومهمة حية | قيد التنفيذ | انتظر؛ راقب انتهاء lease |
| `applying` ومهمة منتهية/lease منقضٍ | عامل توقف | أعد تشغيل العامل؛ الاستئناف يعتمد observation لا إعادة تنفيذ أعمى |
| `failed` | فشل التنفيذ نهائيًا بعد استنفاد المحاولات التلقائية أو لخطأ دائم | لا توجد إعادة محاولة يدوية من الواجهة. يوجد إشعار دائن `pending` على الفاتورة (`credit_pending`)؛ ارجع إلى «الاسترداد اليدوي» أدناه |
| `needs_intervention` | يحتاج قرارًا | لا تُعلن نجاحًا؛ تحقق من Odoo يدويًا (readback)، ثم أعد أو عوّض الدفع حسب السياسة |
| `applied` لكن الاشتراك لا يعكس | عدم اتساق | قارن `observed_digest` بحالة Odoo؛ افتح حادثة |

5. لا تصل بالاشتراك إلى «active» ولا تحصّل مرة ثانية؛ الاسترداد لا يتم تلقائيًا (قرار معتمد: لا استرداد تلقائي).

**المحاولات التلقائية.** صف `commercial_outbox` من نوع `fulfillment.enqueue` يُعاد تلقائيًا عند الأخطاء العابرة (`tenant_unavailable`، `shared_adapter_unavailable`، أخطاء قاعدة البيانات والشبكة، وأي خطأ غير معروف): حتى 10 محاولات، تأخير دقيقة يتضاعف حتى 60 دقيقة (نحو 4 ساعات). `attempts` و`next_attempt_at` يظهران في الصف والخطأ الأخير في `payload.error`. حالات الانتظار (`tenant_required`، `enrollment_pending`) لا تستهلك محاولات.

**التجربة الأولى (تسجيل عام).** طلب التجربة الأولى (`kind='new'` و`payment_state='not_required'`) يُستردّ آليًا كالطلب المدفوع: بعد استنفاد محاولات الصف (`retries_exhausted`) أو فشل التنفيذ، يعيد `recoverPaidFulfillment` الطلب بعد 5 ثم 15 ثم 60 دقيقة، ولا ينشئ مستأجرًا ثانيًا ولا دعوة ثانية (`enrollment_request_id` ومفتاح `first-activation`). بعد هذه الثلاث تستمر المحاولات كل 60 دقيقة حتى 72 ساعة من إنشاء الطلب (`FIRST_TRIAL_RETRY_MINUTES` و`FIRST_TRIAL_RETRY_WINDOW_HOURS`). والطلب الذي توقف بـ`provision_needs_intervention` يبقى كما هو في «يحتاج تصرّفك» ما دامت مهمة التجهيز في `needs_intervention`؛ فإذا أصلحها المشغّل انضم الطلب إلى المحاولات الساعية تلقائيًا ولا يحتاج إعادة جدولة يدوية. لا مال يُسترد، لذلك لا يُلغى الطلب بعد آخر محاولة: يبقى `failed` أو `needs_intervention` ويظهر في «يحتاج تصرّفك» كـ`stalled_activation` حتى يعالجه المشغّل (مثل مهمة تجهيز في `needs_intervention`). إن لم تُسلَّم المساحة بعد 10 دقائق من التسجيل يصل العميل بريد واحد (عربي ثم إنجليزي، صف `workspace.delay_notice` لكل عميل) يقول إن المساحة تتأخر ولا إجراء مطلوبًا منه؛ إعادات الاسترداد لا تُراسله، وتصله الدعوة المعتادة عند التسليم. مدة التجربة (14 يومًا) تُحسب من لحظة بناء مهمة التسليم إن تأخر الطلب أكثر من 10 دقائق عن التسجيل (`trial_ends_at` يُعاد ضبطه في المعاملة نفسها التي تبني المهمة، فيتفق مع ما يُرسل إلى Odoo)؛ التسليم في وقته يُبقي التاريخ المحسوب عند التسجيل.

**النهاية.**
- خطأ دائم (`renewal_missing`، `order_not_found`، `enrollment_base_catalog_missing`، `enrollment_link_conflict`، `idempotency_conflict`، `shared_replay_forbidden`) أو استنفاد المحاولات: الطلب `failed`، والفاتورة `credit_pending`، وإشعار دائن `pending` واحد، والصف `failed`.
- `stale_target` و`observed_mismatch` و`provision_needs_intervention` (مهمة تجهيز المستأجر انتهت إلى `needs_intervention`): الطلب `needs_intervention` بلا إشعار دائن؛ المشغّل يعالج المهمة أو يقرأ Odoo ويقرر.
- مهمة مشتركة في `needs_intervention` (مثل عامل سقط وانتهى lease) تمنع كل أمر آخر لنفس المستأجر بـ`shared_reconciliation_required`. الاسترداد: `POST /v1/shared/tenants/<tenant>/jobs/<job>/recover` بجسم `{"reason":"..."}`، ويتطلب `vendor.operations.run` وstep-up حديثًا؛ يردّ 202 (أو 200 لطلب معلّق مكرر) و409 `shared_job_not_recoverable` إن لم تكن المهمة في `needs_intervention` أو كانت عمليتها غير `provision`/`backup`/`restore` (يذكر الرد العملية؛ مهمة `reconfigure` يستأنفها المجدول وفق بروتوكولها ولا تُسترد من هنا). يُسجَّل الطلب في `shared_job_recoveries` وينفّذه العامل المشترك (وحده يصل إلى Odoo): يقرأ الأثر ولا يعيد تنفيذه أبدًا. إن وجد الأثر الدقيق صارت المهمة `verified` ويُقبل أمر جديد؛ وإلا تبقى موقوفة والنتيجة `still_needs_intervention` في الجدول وفي حدث التدقيق `shared_job.recovery_completed`. حالة الأثر الغائب تنتظر قرار المالك.
- إن فشلت معالجة الفشل نفسها (مثل استرداد وصل بين المحاولة والخطوة النهائية) يبقى الصف `pending` ويُسجَّل السبب في `payload.error` بالصيغة `failure_handling_failed: ...` وفي سجل `control-api`.
- `order_not_released` (الطلب مُسترد أو مُلغى): يُغلق الصف ولا يُمس الطلب؛ المال يعالجه `refund_pending`.

**استرداد أول دفعة بالبطاقة (ضمان 14 يومًا).** يضغط المشغّل «طلب استرداد» على الفاتورة المدفوعة، فيفتح النظام إشعارًا دائنًا بكامل الفاتورة ويضع صفًا في `commercial_outbox` من نوع `reconcile.refund` يحمل `adjustment_id` والمشغّل الطالب. يطلب عامل الاسترداد من المزود استرداد المبلغ نفسه مرة واحدة (قفل استشاري لكل طلب، وقراءة المبلغ المُسترد عند المزود قبل أي طلب، فلا يتكرر الاسترداد عند إعادة المحاولة أو الضغط المزدوج أو إعادة تشغيل العامل)، وعند تأكيد المزود يسجّل النظام الإشعار `refunded` بمرجع المزود (`refunded_by` = `system`، وفاعل التدقيق هو المشغّل الطالب، و`executed_by: system` في بيانات الحدث) ويتبعه القفل إلى القاعدة المجانية بالمسار نفسه. لا يحتاج المشغّل إلى أي خطوة يدوية. خلال ذلك لا يُعرض نموذج «تسجيل الاسترداد» ويرفضه الخادم بـ`refund_in_progress` (409). بمجرد أن يعيد المزود المبلغ يُكتب ذلك على الصف نفسه (`provider_refund: returned` مع معرّف دفعة المزود) في كتابة مستقلة قبل محاولة التسجيل؛ فإن تعثّر التسجيل (مثل `lock_pending` أثناء تسليم قفل آخر، أو انقطاع قاعدة البيانات) يُعاد التسجيل وحده بتأخير متصاعد حتى ينجح، ولا يُسلَّم الصف للمشغّل ولا يُطلب من المزود شيء ثانية، وتعرض الصفحة حالة «أعاد المزود المبلغ والتسجيل قيد الإكمال» بلا نموذج يدوي. وإن نُفّذ طلب الاسترداد عند المزود ولم يُتحقق من نتيجته (مهلة أو انقطاع) يُوسم الصف `provider_refund: attempted` وتعرض الصفحة «لم يؤكد المزود بعد»؛ يواصل العامل قراءة المزود ويسجّل عندما يظهر المبلغ مُعادًا، ويبقى النموذج اليدوي مغلقًا حتى لا يُدفع للعميل مرتين. لا يظهر هذان الصفّان في قائمة «اليوم» ما داما `pending`؛ إن طال بقاؤهما فراجع المزود وسجلات العامل (`commercial_refund_handoff_failed` وأخطاء الصف). إن تعذّر على المزود الاسترداد وثبت أنه لم يُرجع شيئًا (خطأ لا تفيد معه إعادة المحاولة، أو انتهت المحاولات) يبقى الإشعار `pending` ويظهر في قائمة «اليوم» بوسم `refund_rejected` وفي صفحة الفاتورة مع السبب، وعندها فقط يُفتح النموذج اليدوي: افتح لوحة المزود وتأكد أن المبلغ لم يُرجع، ثم أرجعه بطريقة أخرى وسجّل المرجع. حدث `refunded` الذي يرسله المزود لاحقًا لا يُنشئ إشعارًا ثانيًا ولا قفلًا ثانيًا. الدفعة بتحويل بنكي لا استرداد لها عند مزود، فتبقى يدوية: يُرجع المشغّل المبلغ بتحويل ويسجّل مرجعه.

**الاسترداد اليدوي (بقية الحالات).** ويُنتج الاسترداد الذي يجريه المزود بعد تطبيق التنفيذ (`payment.intervention`) إشعارًا دائنًا `pending` وفاتورة `credit_pending` بسبب «payment refunded after fulfillment — manual review»؛ المال خرج فعلًا، فيراجع المشغّل الاستحقاق ويسجّل مرجع استرداد المزود على الإشعار. يفتح المشغّل (دور `owner` أو `finance`، مع step-up حديث) صفحة الفاتورة `credit_pending` في وحدة التحكم، ويُرجع مبلغ الإشعار الدائن `pending` من لوحة مزود الدفع، ثم يضغط «تسجيل الاسترداد» ويُدخل مرجع الاسترداد عند المزود والسبب. يصبح الإشعار `refunded` مع المرجع والمسجِّل والوقت، ويُكتب حدث تدقيق `invoice.credit_refunded`. التسجيل لا يُحرّك مالًا، وتكراره بالمرجع نفسه يعيد النتيجة المسجَّلة دون صف تدقيق ثانٍ، ومرجع مختلف على إشعار مغلق يُرفض بـ`credit_note_not_pending` (409). تبقى حالة الفاتورة نفسها `credit_pending` (الفاتورة غير قابلة للتعديل)؛ الحالة الحاسمة هي حالة الإشعار. السياسة في [refund-policy.md](../finance/refund-policy.md).

### 4.1.1 التسجيل العام: تجربة واحدة لكل شركة

- تُمنح التجربة المجانية مرة واحدة لكل بريد، ولكل جوال، ولكل **نطاق بريد مسجَّل** (`public_signup_trials.company_domain`، فريد). النطاق يُشتق من بريد العمل: أحرف صغيرة، IDN إلى punycode، حذف النقطة الأخيرة، ثم آخر مقطعين (أو ثلاثة تحت لاحقة من مستويين مثل `com.sa` و`co.uk`). القاعدة في `signup/company-domain.ts`. فالنطاق الفرعي `mail.acme.sa` والعنوان `a+1@acme.sa` هما الشركة نفسها `acme.sa`، بينما `x.com.sa` و`y.com.sa` شركتان مختلفتان.
- حدود القاعدة: لا توجد مكتبة لقائمة اللواحق العامة. لاحقة من مستويين غير مدرجة في الملف تجعل شركتين مختلفتين تحتها تبدوان شركة واحدة (اتجاه آمن)، ومزوّدو النطاقات الفرعية مثل `github.io` يُعاملون شركة واحدة. أضف اللاحقة في `SECOND_LEVEL_SUFFIXES` فقط.
- الرفض `trial_already_used` (409) لا يظهر إلا بعد التحقق من رمز الجوال ورمز البريد معًا، فلا يعرف زائر مجهول أن شركة ما لديها حساب. تقول الصفحة إن الشركة استخدمت تجربتها، وتطلب من صاحبها تسجيل الدخول أو طلب دعوة من مسؤول الحساب أو التواصل مع الفريق.
- شركة ثانية مشروعة على نطاق مشترك (نادرة): أنشئها من لوحة المورّد (العملاء، إنشاء عميل). هذا المسار لا يمرّ بجدول المطالبات، ويبدأ مدفوعًا ولا يمنح تجربة، فلا يتأثر بالقاعدة ولا يحتاج تغيير كود. العميل الذي أنشأه المورّد لا يمنع تسجيلًا عامًا لاحقًا على نطاقه (المنع للمطالبات بالتجربة فقط).
- مطالبات ما قبل الإصدار 54 التي تشترك في نطاق واحد بقيت كلها؛ الأقدم يحمل النطاق والأحدث يبقى بلا نطاق، والقيد يسري على ما بعدها.

### 4.1.3 تغيير العنوان المسجّل للعميل (`customers.admin_login`) [محلي جزئيًا]

كل ما يصل المستأجر من لوحة التحكم يذهب إلى هذا العنوان: الدعوة وإعادة إصدارها، وإشعارات الفوترة والتجربة والإلغاء والقفل، ورمز تأكيد الحذف وإشعاراته. كان يُكتب عند إنشاء العميل فقط. إن غادر أول مدير فالتغيير من صفحة العميل ← تبويب مساحة العمل ← «العنوان المسجّل» ← «تغيير العنوان» (`PATCH /v1/commercial/customers/:id/admin-login`، الصلاحية `vendor.subscriptions.manage` تُفحص قبل البحث عن العميل، وتأكيد مفتاح مرور حديث، وسبب من 3 أحرف فأكثر، وجسم صارم).

- **القاعدة.** عنوان بريد واحد صالح بالقاعدة نفسها التي ينشئ بها البائع العميل (`z.email().max(100)`)، ويُحفظ بأحرف صغيرة. لا يُطبَّق رفض البريد المجاني لأن إنشاء البائع لا يطبّقه (يُطبَّق في التسجيل العام فقط). لا يوجد قيد تفرّد على `customers.admin_login` ولا فحص تفرّد في أي مسار، فيجوز أن يدير شخص واحد أكثر من عميل. صف التجربة `public_signup_trials.email` مطالبة بالتجربة وليس العنوان المسجّل، ولا يُمسّ: تبقى للشركة تجربتها الواحدة. عميل بلا مساحة عمل يُرفض (`no_workspace` 409)، وكذلك العنوان نفسه (`admin_login_unchanged` 409).
- **شرط التنفيذ.** يُرفض التغيير لمساحة لم يفعّلها أي مدير بعد (لا توجد دعوة مقبولة للمستأجر): 409 `workspace_not_activated` ولا يُكتب شيء. السبب أن مدير Odoo الأول أُنشئ باسم الدخول المثبَّت عند الإنشاء (`shared_onboardings.admin_login`)، وقبول دعوة لعنوان آخر يرفضه `admin-password-runner` بـ `user_missing`، فدعوة لا يمكن قبولها لا تُرسل. البديل اليوم أن يُنشأ العميل من جديد بالعنوان الصحيح، أو انتظار إجراء إعادة تسمية مستخدم Odoo (متابعة معلّقة تحتاج أثرًا تحت `tools/**`).
- **ما يجري تحت قفل الدعوات للمستأجر.** يُحدَّث العنوان، وتُلغى كل دعوة لم تُستهلك للعنوان القديم، ويُلغى رمز حذف حيّ لطلب في حالة `requested` (يُصفَّر `code_hash` ويُسجَّل `tenant_deletion.code_invalidated`، وطلب رمز جديد يصل العنوان الجديد)، ويُسجَّل `customer.admin_login_changed` في `audit_events` (الفاعل حساب البائع، والسبب، وفي `metadata` العنوانان نفسهما والمستأجر ونتيجة رمز الحذف وعنوان العميل)، وتُوضع رسالتان في الصندوق الصادر (النوع `admin_login.notice` من مهمة `admin-login-notices`): إلى العنوان القديم وإلى الجديد، نص عادي بلا رابط يفعل شيئًا، ليرى صاحب العنوان السابق أي تغيير يجريه البائع. لا تصدر دعوة جديدة، فالمدير فعّل مساحته أصلًا.
- **تحذير التكرار.** لا قيد تفرّد، فقد يكون العنوان الجديد مسجّلًا لعميل آخر. الواجهة تطلب قبل التأكيد معاينة بلا كتابة (`PATCH` بالجسم `{admin_login, dry_run:true}`، بلا سبب، بنفس الصلاحية والتأكيد الحديث) تعيد `preview.other_customers_with_address`، فتعرض تحذيرًا لأن «ابحث عن مساحتي» سيعرض كل مساحات ذلك البريد.
- **سجل التدقيق.** `GET /v1/audit` (الصلاحية `vendor.audit.read`) يختار الأعمدة `id, actor, action, subject, reason, created_at` فقط ولا يعيد `metadata` أبدًا ولا يبحث فيه إلا بمعرّف العميل، فلا تظهر العناوين في قائمة اللوحة. السبب نص حر يكتبه البائع.
- **الرسائل المنتظرة.** كل مرسِل يقرأ `customers.admin_login` وقت الإرسال، فما كان في الطابور (فوترة، تجربة، إلغاء، قفل، حذف) يذهب إلى العنوان الجديد. الدعوات القديمة تُغلق دون إرسال لأنها ملغاة.
- **ما لا يفعله.** لا يغيّر أي مستخدم أو كلمة مرور أو اسم دخول داخل Odoo، فيجب أن يكون للشخص الجديد حساب في المساحة مسبقًا، وهذا ما تقوله الواجهة.

**سطر «مساحة عملك».** كل رسالة تصل المستأجر من لوحة التحكم (الدعوة، الفوترة، التجربة، الإلغاء، قفل القاعدة المجانية، حذف المساحة، إشعار تغيير العنوان) تحمل سطر «مساحة عملك: <العنوان>» بالعربية و«Your workspace: <origin>» بالإنجليزية، من `workspaceOrigin` و`workspaceLines` في `commercial/return-origin.ts` (المصدر نفسه الذي تستعمله روابط الدفع). عميل بلا عنوان صالح لا يحمل رسالته السطر. إشعار تأخر التسليم لا يحمله لأن المساحة لم تُنشأ بعد.

### 4.1.2 التسجيل العام: التحقق البشري (Cloudflare Turnstile)

- خطوة `start` (التي ترسل الرسالة النصية الأولى وتستهلك رصيد الرسائل) تتطلب رمز Turnstile صالحًا. إعادة إرسال الرسالة النصية هي `start` نفسها، فتتطلب رمزًا جديدًا. `send-email` لا تتطلب رمزًا: لا تعمل إلا بعد التحقق من الجوال (أي بعد رمز مرّ بالفحص)، وحدودها لكل وجهة وعنوان قائمة كما هي. الحدود الحالية للتسليم بقيت دفاعًا إضافيًا.
- المتغيّران على واجهة لوحة التحكم: `LIWAN_SIGNUP_TURNSTILE_SITE_KEY` (عام، يصل الصفحة عبر طلب `terms`) و`LIWAN_SIGNUP_TURNSTILE_SECRET_KEY` (سرّي، لا يغادر لوحة التحكم). غياب أحدهما يوقف التسجيل (`signup_configuration_invalid`). أنشئ أداة Turnstile في Cloudflare بوضع Managed لنطاق التطبيق.
- التحقق في لوحة التحكم وحدها: ترسل الرمز والسر وعنوان الزائر (المحمول في الطلب الموقّع) إلى نقطة siteverify بمهلة ٥ ثوانٍ، ولا تخزّن نتيجة (الرمز يُستعمل مرة واحدة في Cloudflare). رفض الرمز يعيد `human_check_failed` (422) فتعيد الصفحة ضبط الأداة وتطلب إكمال التحقق. تعذّر الوصول إلى Cloudflare أو انتهاء المهلة يعيد `human_check_unavailable` (503) ولا تُرسل رسالة ولا يُحجز من حصة التسليم؛ لا يوجد تجاوز عند العطل.
- ما يغادر المملكة (للإدراج في سياسة الخصوصية): متصفح الزائر يتصل بـ `challenges.cloudflare.com` لتحميل الأداة وإكمال التحدي (عنوان IP وبيانات المتصفح تصل Cloudflare)، ولوحة التحكم ترسل الرمز وعنوان الزائر إلى `challenges.cloudflare.com` للتحقق. لا يُرسل اسم الشركة ولا البريد ولا الجوال.
- سياسة أمان الصفحة: تسمح حافة الحاضنة المشتركة (`deploy/shared/securityHeaders.mjs`) لمسار `/register` وحده بـ `https://challenges.cloudflare.com` في `script-src` و`frame-src` و`connect-src`.

### 4.2 رفض webhook الدفع [قبول تشغيلي غير متحقق] [غير مختبر]

أسباب الرفض في `moyasar-adapter.ts`: `signature_invalid` (سر خاطئ)، `merchant_mismatch`، `mode_mismatch` (live/test)، `invalid_event` (JSON/نوع غير معروف).

1. اقرأ رمز الرفض من سجل `control-api` (الأسرار تُنقَّح من الرسائل).
2. `signature_invalid`: تحقق أن `MOYASAR_WEBHOOK_SECRET` يطابق إعداد لوحة المزود؛ لا تطبع السر. بعد التدوير أعد تشغيل `control-api`.
3. `merchant_mismatch`/`mode_mismatch`: تحقق `MOYASAR_ACCOUNT_NAME` و`MOYASAR_MODE` مقابل البيئة؛ حدث test لا يقبل في live والعكس. هذه إشارة تهيئة خاطئة أو محاولة تزوير؛ لا تُخفّف التحقق.
4. بعد الإصلاح لا تعيد إرسال الأحداث يدويًا قبل مصالحة المحاولة (4.3)؛ الحالة تُحسم بإعادة الفحص من المزود وليس بمحتوى webhook وحده.
5. تسجيل webhook جديد: اضبط `MOYASAR_WEBHOOK_REGISTRATION=open` وأعد تشغيل `control-api`، سجّل الـwebhook في لوحة المزود، أدخل الرمز، ثم احذف المتغير وأعد التشغيل. يرسل المزود حدث `webhook_verification` برمز من ستة أرقام ينتهي بعد 30 دقيقة ويُقفل بعد خمس محاولات خاطئة. المحوّل يجيب 200 ولا يعدّه حدث دفع، ويصل الرمز مع معرّف الـwebhook في تنبيه البائع وفي سجل `control-api` (`payment_webhook_verification`) وفي سجل التدقيق (`payment.webhook_verification`). أدخل الرمز فقط إن كان المعرّف هو المعروض للـwebhook في لوحة المزود. الحدث الذي يحمل السر المشترك يُقبل دائمًا ويجب أن يطابقه؛ الحدث بلا السر يُرفض (401) ما لم يكن التسجيل مفتوحًا، ويُقبل منه عشرة في الساعة كحد أقصى (الزائد يُجاب بـ429 ولا يُسجَّل).

### 4.3 مصالحة محاولات الدفع غير المحسومة [قبول تشغيلي غير متحقق] [غير مختبر]

`payment_attempts.status='unknown'` يحجز المحاولة الحية (فهرس `payment_attempts_one_live`) ويمنع محاولة جديدة للطلب نفسه.

**انتهاء الفاتورة أو إلغاؤها عند المزود.** فاتورة الدفع المستضافة صالحة 30 دقيقة. حين يعيد المزود `expired` أو `canceled` أو `voided` تصبح المحاولة `canceled` ويبقى الطلب `awaiting_payment` (لم يُخصم شيء)، فيبدأ العميل محاولة جديدة على الطلب نفسه والفاتورة المُصدرة نفسها. محاولة حية أقدم من 30 دقيقة تُستعلم عند المزود قبل أن تُعاد للعميل، فتُغلق إن انتهت. أما الرفض (`failed`) فيجعل الطلب `failed` ولا يسمح بمحاولة جديدة، لكن دفعة ناجحة متأخرة تُقبل وفق آلة حالات الطلب.

1. افحص المحاولات `created`/`unknown`/`redirected`/`pending` وسجلات العامل للقراءة فقط.
2. في المصدر، يستدعي `worker:shared` المصالحة بعد عدد دورات يحدده `LIWAN_COMMERCIAL_RECONCILE_EVERY` (الافتراضي 10). تتطلب المصالحة مهايئ دفع مضبوطًا، وتعيد قراءة حالة المزود قبل حسم المحاولة.
3. لا تحدّث جداول المحاولات أو الأحداث يدويًا، ولا تعِد التحصيل عند نتيجة مجهولة. عند اختلاف الحالة أو تعذر قراءة المزود، أبقِ الطلب دون إعادة تحصيل وصعّد الحالة للمراجعة.
4. وجود المسار في المصدر واختباراته لا يثبت تشغيل العامل أو قبول المصالحة مع Moyasar في staging؛ لا تُنفذ إجراءً يدويًا بديلًا قبل توثيق نتيجة القبول.

### 4.4 تشغيل التجديد [قبول تشغيلي غير متحقق] [غير مختبر]

- التجديد يصدر فاتورة واحدة للفترة (`renewals` فريد)، ثم `charging` عبر token المزود إن وُجدت موافقة صريحة، وإلا طلب دفع.
- قبل أي تشغيل جماعي: تحقق الساعة، وأن المزود في الوضع الصحيح، وعدم وجود `renewals` عالقة بـ`charging`.
- تتبّع الحالات: `invoiced → charging → paid | past_due | suspended | failed`. لا يُعاد تشغيل التجديد لفترة سبق إصدار فاتورتها.
- يشغّل `npm -w apps/control-plane run worker:shared` دورة الفوترة افتراضيًا كل 300 ثانية (`LIWAN_COMMERCIAL_BILLING_INTERVAL_SEC`). ابحث عن `commercial_scheduler_tick` في سجل العامل للتحقق من تشغيله في البيئة المقصودة.
- يطبق Odoo سياسة نهاية التجربة عند الموعد المخزن حتى عند توقف عامل التحكم. تبقى التطبيقات غير المشتراة للقراءة والتصدير، وتُقيَّد المقاعد والفروع والملفات الزائدة. لا تُحذف بيانات. تؤكد وحدة التحكم القفل بطلب تغيّر صفري واحد في كل محاولة.
- تسجل معاملة الانتهاء صفًا في `free_base_locks` بسبب `trial_end` (`schema_044.sql`، وأعادت `schema_050.sql` تسميته). يحدد القفل ما يبقى من تقاطع التهيئة المطبقة وبنود الفواتير المسددة بعد طرح الإشعارات الدائنة. ينطبق على الباقات المجانية والمدفوعة والشروط المتفاوض عليها. يبدأ تسعير الدورة الأولى في يوم الانتهاء ويستثني الأيام المسددة لكل بند.
- يرى العميل `trial_ending` بعد الموعد وقبل تسجيل الانتهاء، ثم `lock_pending` حتى تأكيد القفل. تعرض `GET /v1/customer/trial/end-preview` السعة والمبلغ والمقاييس المتاحة. يستطيع مدير الاشتراك طلب إعادة المحاولة عبر `POST /v1/customer/trial/retry` مرة كل خمس دقائق.
- يبقى التعليق اليدوي حتى يستأنف البائع الاشتراك. إذا مر الموعد أثناء التعليق يستأنف الاشتراك دورة الانتهاء العادية. تعرض قائمة «اليوم» «تعليق لم يصل» بعد خمس محاولات فاشلة أو ساعتين دون وصول التعليق، وتستمر المحاولات.
- إن كانت أول فاتورة بعد القفل لباقة أساسها مجاني ولم تُسدد بعد مهلة الباقة، تبطل ويُعاد القفل بسبب `first_invoice_unpaid` على ما لم يُجدّد. المحاولة الحية تنتظر تسويتها. الباقات المدفوعة تتبع سياسة الباقة. التحويل الصريح وحده يشتري كامل التهيئة، وتُزال سياسة انتهاء التجربة عند تحقق دفع التجديد وتطبيقه.
- تعاد محاولة الطلب المدفوع الذي يتعذر تنفيذه بعد 5 و15 و60 دقيقة للأعطال القابلة لإعادة المحاولة. يصدر إشعار دائن بعد استنفاد المحاولات أو الرفض الدائم، ويقرأ العامل رصيد المبالغ المستردة لدى مزود الدفع قبل إعادة المبلغ. يحتاج التحويل البنكي إلى مسار التسوية البنكية القائم. اختبارات المحاكي لا تثبت سلوك Moyasar الحي.
- عرض الدفع غير القابل للتوجيه يظهر للبائع بوسم `billing_blocked` حتى يضبط ربط المضيف أو `LIWAN_PAYMENT_RETURN_ORIGINS`. تستمر معالجة الاشتراكات الأخرى.
- عند تسجيل استرداد أول دفعة للعميل (ضمان 14 يومًا) ينزل الاشتراك إلى القاعدة المجانية في معاملة التسجيل نفسها: صف في `free_base_locks` بسبب `refund`، وإبطال فواتير التجديد غير المسددة، وحدث تدقيق `subscription.refund_lock_armed`. يبقى ما اشتُري بدفعة ثانية لم تُسترد، ولا يتغير موعد التجديد إلا إن كانت التهيئة المقفلة تستحق مبلغًا. القواعد الكاملة ومتى لا ينزل الاشتراك في [refund-policy.md](../finance/refund-policy.md). يظهر القفل المتعطل في قائمة «اليوم» بوسم `free_base_blocked` أيًا كان سببه.
- **إلغاء الاشتراك من العميل (قرار المالك 2026-11-13).** يلغي مدير الاشتراك التجديد بنفسه (`POST /v1/customer/subscription/cancel`، وللتراجع `.../resume`)، ويفعل البائع الأمر نفسه نيابةً عنه بسبب مكتوب (`POST /v1/commercial/subscriptions/:id/cancel-renewal` و`resume-renewal`، بتأكيد step-up). الحقيقة المخزنة أعمدة `cancel_requested_at` و`cancel_requested_by` و`cancel_reason` في `subscriptions` (`schema_056.sql`)، وتاريخ السريان هو `renewal_at` نفسه. يُقبل الإلغاء لاشتراك `active` يدين بمال عند التجديد دون تعليق يدوي ولا قفل معلّق ولا تغيير قيد المعالجة؛ يُرفض في التجربة (`cancel_trial_unsupported`) وفي `past_due` (`subscription_past_due`، حتى لا تفلت فاتورة متأخرة من التحصيل). التكرار لا يغيّر شيئًا. أثناء الإلغاء: لا تُولَّد فاتورة تجديد ولا يُرسل إشعار «التجديد قريب»، ويُرفض أي تغيير مدفوع بـ`subscription_cancelling` (كان سيُحسب نسبيًا لفترة يغادرها العميل ويسقط بلا استرداد)، ويبقى الاستئناف متاحًا حتى تاريخ السريان. عند وصول `renewal_at` تسلّح `processFreeBaseLocks` قفلًا بسبب `cancelled` (بلا `trial_ended_at`) يبدأ الفترة الجديدة، وتُبطل فاتورة التجديد غير المسددة لتلك الفترة، ثم يمر الاشتراك في آلة القفل نفسها: القاعدة المجانية، `trial_outcome` دون تغيير، ومسح طلب الإلغاء، وإشعار `free_base.locked` بنص الإلغاء. يبقى ما دُفع حتى تاريخ لاحق (بنود `:delta` ذات `period_end` بعد بداية الفترة) إلى ذلك التاريخ، ويبقى الإلغاء مسلَّحًا ثم يعاد القفل عنده. في التحليلات يُحسب الانتقال تسرّبًا (`churned_mrr` وعدد العملاء ونسبتا التسرب) في تاريخ السريان، ويبقى الإيراد المدفوع قبله. لا يظهر في قائمة «اليوم» إلا إن تعطل تسليم القفل (`free_base_blocked`). إشعارات العميل في `commercial_outbox` بالنوع `cancellation.notice` (تأكيد الإلغاء، تأكيد الاستئناف، تذكير قبل النهاية بـ3 أيام)، من مهمة `cancellation-notices`، كل واحد مرة واحدة ويُعاد فحصه عند الإرسال. بعد النزول يشتري العميل من جديد بمسار التغيير العادي.
- قبل تفعيل المسار حدّث المضيف المتسامح ثم Odoo (بما فيه مفاتيح رصيد AI عند تشغيلها) ثم المضيف المطبّق للسياسة ثم وحدة التحكم فالواجهة. تحقّق من أن استعلام البوابة أدناه يعيد صفرًا. الدعم غير المعروف يؤجل الانتهاء. تحقق من كل تجربة قديمة بوصول سياسة الموعد الفعلية إلى Odoo، إلى جانب أعلام الدعم.
  ```sql
  SELECT count(*) FROM subscriptions s JOIN tenants t ON t.id=s.tenant_id
  WHERE (s.state='trialing' OR s.suspended_from='trialing')
    AND (t.post_trial_supported IS NOT TRUE OR t.excess_supported IS NOT TRUE);
  ```
- يوجد أيضًا `POST /v1/commercial/renewals/run`؛ يتطلب `vendor.billing.manage` وتأكيد step-up حديثًا، ويرفض تمرير `now` في production. وجود المسار لا يجيز تشغيلًا يدويًا؛ لا يُستخدم قبل قبول الإجراء في بيئته المقصودة.

### 4.4.1 حذف مساحة العميل بطلبه (قرار المالك B8/O6) [محلي جزئيًا]

تُحذف المساحة بطلب العميل نفسه فقط، بمهلة 90 يومًا يمكن سحب الطلب فيها. من يتوقف عن الدفع لا تُحذف مساحته أبدًا: يتعلق به التعليق والقاعدة المجانية فقط. المنفَّذ الآن هو الطلب وآلة الحالات والإشعارات والظهور. **لا شيء يحذف قاعدة البيانات ولا الملفات ولا النسخ الاحتياطية بعد**؛ ينتهي الطلب عند حالة `due` أمام البائع، وتنفيذ الحذف الفعلي مرحلة لاحقة.

- **الحقيقة المخزنة.** جدول `tenant_deletion_requests` (`schema_057.sql`): طلب مفتوح واحد لكل عميل (فهرس فريد جزئي على `requested/confirmed/due`). الحالات `requested` (أُرسل الرمز ولم يُؤكَّد) ثم `confirmed` (بدأت المهلة، `due_at = confirmed_at + 90 يومًا`) ثم `due`، أو `withdrawn` (سُحب). القيد `tenant_deletion_requests_state_check` اسمه ثابت لتضيف المرحلة اللاحقة `dropping/dropped/failed` باستبداله. كل انتقال يُسجَّل في `audit_events` (موضوعه معرّف العميل) بالفاعل وعنوان العميل (`client_address`: يوقّعه خادم الويب مع الطلب ويمرّره الحافة، `deploy/shared/Caddyfile` و`guard.mjs`، لمسارات الحذف الثلاثة فقط)، وكل الأزمنة (الاستحقاق، نافذة 90 يومًا، صلاحية الرمز، حدود المعدل) من ساعة قاعدة البيانات لا ساعة العملية، وكل العمليات تحت قفل استشاري لكل عميل فلا يتسابق مديران. مدة 90 يومًا ثابت مسمّى (`TENANT_DELETION_WINDOW_DAYS`) لا إعداد، ولا مسار يقصّرها.
- **من يطلب.** القدرة `tenant.delete`، وتُشتق في الواجهة من `settings.company.vat.manage` وحدها (فوق قدرات مدير الاشتراك)، وهي لدور مدير النظام فقط: لا يحملها دور مخصص ولا دور دعم البائع، بخلاف `subscription.manage` التي يحملها أي دور يملك `settings.branding.manage` أو `access.roles.manage`. المسارات عبر وكيل الواجهة: `GET /api/commercial/v1/deletion` (يكفي `subscription.read`)، و`POST .../deletion/request` و`confirm` و`withdraw` (تتطلب `tenant.delete`). واجهة العميل: قسم «حذف مساحة العمل» أسفل `/subscription` (`DeleteWorkspacePanel`). **قيد معروف:** `/me` يعيد قدرات الشركة العاملة ولا يعرّف الشركة الجذر، فمدير نظام معيَّن في فرع يرى القسم ويستطيع الطلب حتى يُضاف إلى `/me` ما يميّز الجذر. البائع لا ينشئ ولا يؤكد؛ يقرأ الطلبات (`GET /v1/commercial/deletion-requests` و`/customers/:id/deletion`) ويسحب نيابةً عن العميل بسبب مكتوب (`POST /v1/commercial/customers/:id/deletion/withdraw`، بتأكيد step-up وتدقيق).
- **الخطوتان.** (1) `request`: رمز من 6 أرقام يُرسل إلى `customers.admin_login` وحده، لا إلى عنوان في الطلب (الجسم لا يقبل أي حقل). يُخزَّن تجزئته HMAC فقط، وصلاحيته 15 دقيقة، وبحد 5 محاولات خاطئة، ويُستعمل مرة واحدة، وتُمسح قيمته من صف الصندوق الصادر بعد إرساله. الرسالة نفسها تُخبر عنوان السجل بالطلب وتطلب منه تجاهلها إن لم يطلبه أحد، وينبّه المالك (`deletion_requested`). رمز منتهي الصلاحية يُمسح من صف الصندوق ويُغلق فاشلًا (`code_expired`) ويُصفَّر `code_hash` وعدد المحاولات في الطلب بمهمة `tenant-deletion-due`، مهما كانت حالة البريد. (2) `confirm`: الرمز مع اسم الشركة كما هو مسجل حرفيًا (بلا تغيير حالة أحرف ولا مسافات)؛ أي رمز خاطئ أو منتهٍ أو مستعمل أو مستنفد يعطي `invalid_code` دون زيادة، والاسم الخاطئ `company_name_mismatch` ويبقى الرمز صالحًا. الحدود لكل عميل: رمز جديد كل 60 ثانية على الأقل وخمسة في الساعة بحد أقصى (`rate_limited` 429).
- **الاشتراك المدفوع.** لا تُفتح فترة مدفوعة جديدة أبدًا لعميل حذفه `confirmed` أو `due` (`generateRenewals`، الشرط `deletionClockRunningSql`): ما أُصدر من فواتير والمطالبة بالدين الحالي يستمران، وعند تاريخ التجديد يمر الاشتراك الملغى بقفل `cancelled` إلى القاعدة المجانية، وما لم يُلغَ تجديده لا يُجدَّد ببساطة ويظهر في «اليوم» تجديدًا فائتًا إلى أن يُعالج. ويقول إشعار التأكيد وتنبيه المالك صراحةً، بكلمات لا برمز، حين لم يُوقف التجديد ولماذا. التأكيد يلغي التجديد عند نهاية الفترة عبر مسار الإلغاء نفسه (`cancelRenewalOn`) في معاملة التأكيد، دون استرداد وبلا إشعار إلغاء مستقل (إشعار الحذف يقول ذلك). إن لم يكن قابلًا للإلغاء (تجربة، متأخر الدفع، قفل معلّق...) يُقبل الحذف ويُسجَّل السبب في `renewal_refusal`؛ والقاعدة المجانية أو العميل بلا اشتراك لا شيء فيه لإلغائه. السحب لا يستأنف الاشتراك: يستأنفه العميل من صفحة الاشتراك، والإشعار يقول ذلك.
- **السحب.** لأي حامل `tenant.delete` أو للبائع في أي وقت قبل `due`، دون رمز (السحب هو الاتجاه الآمن)، مدقَّق ومُخطَر به. بعد `due` يُرفض بـ`deletion_due` (409).
- **الإشعارات** (`commercial_outbox` بالنوع `tenant_deletion.notice`، عربي ثم إنجليزي، كل واحد مرة): الطلب (مع الرمز)، التأكيد (التاريخ، ما يُحذف: بيانات المساحة وملفاتها ونسخها الاحتياطية، وما يُحتفظ به: الفواتير وسجلات الدفع، وكيف يُسحب)، تذكير قبل 60 و30 و14 و7 ويوم واحد (`TENANT_DELETION_REMINDER_DAYS`، ولا تذكير قبل أول عتبة) (بعد توقف العامل يُرسل أقرب تذكير لم يفت فقط، لا دفعة)، السحب، و«انتهت المهلة» عند `due` (انتهت المهلة، لا سحب بعد الآن، سينفّذ فريق ليوان الحذف ويرسل تأكيدًا عند اكتماله). يُعاد فحص الصف عند الإرسال فلا يصل رمز لطلب تجاوزته حالته. المهمتان `tenant-deletion-due` و`tenant-deletion-notices` في المجدول.
- **المالك.** تنبيهات `deletion_requested` و`deletion_confirmed` و`deletion_withdrawn` من أحداث التدقيق، و`deletion_due` من عنصر الانتباه `tenant_deletion_due` وهو **يتطلب إجراءً** لأن لا شيء ينفّذ الحذف بعد؛ يبقى العنصر في قائمة «اليوم» حتى تعالجه المرحلة اللاحقة. صفحة العميل (تبويب الاشتراك) تعرض الطلب بتواريخه ونتيجة إلغاء التجديد وزر السحب.
- **ما لا يفعله هذا التسليم.** لا يغيّر حالة المساحة، ولا يجعلها للقراءة فقط، ولا يلمس Odoo، ولا يحذف شيئًا. كل نص للعميل يقول إن الحذف مجدول لا منفَّذ. إن غادر أول مدير فالرمز يذهب إلى بريد لا يقرؤه أحد؛ يغيّر البائع العنوان من صفحة العميل (القسم 4.1.3)، وتغييره يُلغي أي رمز حذف حيّ كان قد أُرسل إلى العنوان القديم.

### 4.5 past_due والتعليق وفق سياسة الباقة [قبول تشغيلي غير متحقق] [غير مختبر]

- قرار معتمد: `trial_days` و`grace_days` صريحان لكل باقة؛ التعليق الآلي بحسب سياسة الباقة فقط، ولا قيم ثابتة.
- `past_due`: في مهلة السماح؛ الخدمة تعمل. بعد انتهائها `suspended`. تحقق السياسة المنشورة للباقة (الإصدار المحفوظ للاشتراك) لا السعر العام.
- لا حذف بيانات عند التعليق/الإلغاء؛ الاستئناف بعد الدفع يتطلب تحقق Odoo قبل إعلان الفعالية.
- لا تعلّق يدويًا خارج السياسة؛ استثناء يحتاج قرارًا مسجلًا في `audit_events`.

**إشعارات الفوترة للعميل.** بريد إلى `customers.admin_login` عبر `commercial_outbox` (النوع `billing.notice`، والنوع الفرعي في `payload.type`)، تُرسل من مهمة `billing-notices` في المجدول (`commercial/billing-notices.ts`، والمواعيد في `notice-timings.ts`). كل إشعار مرة واحدة (مفتاح التكرار يحمل الفاتورة أو تاريخ التجديد أو نهاية المهلة والعتبة)، ويُعاد فحصه عند الإرسال فلا يخرج إن لم يعد صحيحًا (دُفع، أُلغي، قفل القاعدة المجانية). فشل البريد يترك الصف قابلًا لإعادة المحاولة بتأخير متزايد، وبلا عنوان يفشل الصف بـ `no_recipient`.

**الخصم من البطاقة المحفوظة (`commercial/saved-card-charges.ts`).** تُولَّد فاتورة التجديد ولا يُخصم شيء عند توليدها؛ مهمة `saved-card-charges` في المجدول (بعد `renewals` وقبل `dunning`) هي المسار الوحيد للخصم، للمحاولة الأولى وللإعادات. تحت قفل صف الاشتراك تعيد كل ما يفحصه `generateRenewals` (الحالة نشط أو متأخر، لا تعليق يدوي، لا إلغاء مجدول، لا تغيير باقة معلّق، لا قفل قاعدة مجانية، لا مهلة حذف جارية) وتضيف: التجديد التلقائي مفعّل، بطاقة افتراضية فعّالة لمزوّد الخصم ونمطه، غير منتهية في يوم الخصم (`cardExpired` في `packages/commercial-contracts`)، وطلب الفاتورة غير مقفول لتسوية جارية (`SKIP LOCKED`، وتُعاد المحاولة في الدورة التالية). فشل أي شرط يعني لا خصم وتبقى الفاتورة قابلة للدفع يدويًا. الجدول: يوم إصدار الفاتورة ثم +1 و+3 و+5 أيام عند رفض ناعم (`SAVED_CARD_CHARGE_DAYS` في `notice-timings.ts`، بتوقيت الرياض من تاريخ إنشاء الفاتورة)، والرفض الصلب يوقف الباقي فورًا ويجعل البطاقة `inactive`. التصنيف جدول رسائل صريح في `payment-decline.ts` مأخوذ من `docs/operations/moyasar-form-spike.md` (بطاقة مفقودة أو مسروقة أو منتهية وأخطاء مرحلة 3-D Secure صلبة؛ ما عداها ناعم، والرسالة المجهولة أو الغائبة ناعمة). تُعدّ المحاولات من صفوف `payment_attempts` بنوع `saved_card` للطلب، ولكل محاولة صفها ومعرّفها هو `given_id`. جواب ضاع يبقى على صفه: يُبحث عن الدفعة بمعرّف المحاولة أولًا ثم يُعاد الإرسال بالمعرّف نفسه بعد 5 دقائق (`SAVED_CARD_REDRIVE_MINUTES`). لا رابط فاتورة مستضافة للعميل بعد الآن: يدفع العميل الفاتورة المفتوحة عبر نموذج البطاقة (`POST /v1/customer/orders/:id/payment-attempts` بالجسم `{method:"form", save_card?, consent_text_version?}` ويُرفض `hosted_invoice`)، ويبقى الرابط للبائع وحده لعميل بلا مساحة. رفض الدفع لا ينهي الطلب: لا حالة دفع `failed` (`schema_063.sql`)، تُغلق المحاولة ويبقى الطلب `awaiting_payment` ليجرّب العميل بطاقة أخرى أو تحويلًا بنكيًا؛ لا ينهيه إلا الإلغاء. إشعارات جديدة بالنوع `billing.notice`: `card_charge_failed` (موعد المحاولة التالية أو أن لا محاولة أخرى)، و`card_expiring` قبل 30 و7 أيام (`CARD_EXPIRY_NOTICE_DAYS`) للبطاقة الافتراضية ما دام التجديد التلقائي مفعّلًا، و`renewal_upcoming` يذكر الآن البطاقة والمبلغ أو أن الفاتورة تُدفع يدويًا؛ لا شيء من رقم البطاقة غير الماركة وآخر أربعة أرقام. يُوقَف التجديد التلقائي (وتبقى البطاقة) عند تسليح قفل الاسترداد وعند تأكيد حذف المساحة. إزالة البطاقة: `POST /v1/customer/payment-methods/:id/remove` (وللبائع `POST /v1/commercial/subscriptions/:sid/payment-methods/:id/remove` بسبب وstep-up) تحذف الرمز عند المزوّد أولًا تحت قفل الاشتراك وتفشل بـ503 إن تعذّر ذلك فتبقى البطاقة فعّالة، ثم تعلّمها `removed` وتوقف التجديد التلقائي إن كانت الافتراضية؛ وللبائع أيضًا `POST /v1/commercial/subscriptions/:sid/disable-auto-renew`. تفعيل التجديد التلقائي (`POST /v1/customer/auto-renew` بالجسم `{enabled, consent_text_version}`) يحتاج بطاقة افتراضية فعّالة غير منتهية وباقة تسمح به، وكل اتجاه يكتب حدث تدقيق (`auto_renew.enabled` و`auto_renew.disabled`).

**الخصم من البطاقة: ما أُضيف بعد المراجعة.** (1) الخصم يتوقف أيضًا عند وجود محاولة نموذج بطاقة أُغلقت وقد تحمل نيّتها دفعة لم تُبلَّغ (`payment_attempts.payment_hold_until`، `schema_065.sql`): تحجز الفاتورة حتى 24 ساعة (`FORM_PAYMENT_HOLD_HOURS`) من إغلاقها، وتنتهي قبلها بتسوية الدفعة أو تسجيل رفضها أو دفع الطلب أو إلغائه؛ بند الانتباه `form_payment_review` يبقى للمشغّل ما دامت الدفعة بلا تسوية، فلا يبقى التجديد عالقًا بعد 24 ساعة. (2) باقة لا تتيح التجديد التلقائي (`plan_revisions.auto_renew_allowed`) لا يُخصم لها؛ وعند تطبيق مراجعة باقتها لا تتيحه يُوقَف التجديد التلقائي بحدث `auto_renew.disabled` (البطاقة تبقى). (3) كل فشل لمحاولة `saved_card`، سواء جاء من جواب الخصم أو من بحث بعد جواب ضائع أو من المُصالِح أو من webhook أو من دفعة كانت معلّقة ثم فشلت، يمر في دالة واحدة (`failSavedCardAttempt` في `saved-card-failure.ts`): تصنّف الرفض برسالة الدفعة، وتجعل البطاقة التي خُصمت `inactive` عند الرفض الصلب، وتعيد حالة التجديد إلى `invoiced`، وترسل إشعار `card_charge_failed` مرة واحدة. (4) الوقت الأخير للاتصال بالمزود محفوظ في `charge_sent_at` (ولا يحرّكه المُصالِح): يُعاد إرسال خصم ضائع بعد 5 دقائق من آخر إرسال، وإذا قال المزود إن لا دفعة بهذا المعرّف وانقضت 10 دقائق (`SAVED_CARD_MISSING_MINUTES`) تُغلق المحاولة فلا تحجب نموذج العميل. خطأ دائم من الطلب نفسه (غير مهلة وغير 5xx وغير 429) يغلق المحاولة ويظهر للبائع بندًا `renewal_failed` بتفصيل `card_charge_refused` ما دام الطلب غير مدفوع، ويُبلَّغ العميل بأن يدفع بنفسه؛ وتبقى الحدود 4 محاولات بالجدول. فاتورة أقل من 100 هللة (`MIN_CHARGE_MINOR`) لا تُخصم بالبطاقة. (5) رابط العودة غير الصالح لعميل: يُطلب فقط عند الحاجة لخصم، وإن تعذّر عُلِّم الاشتراك `billing_blocked_at` كما يفعل توليد التجديد؛ وتسوية خصم معلّق لا تعتمد عليه. (6) نص الإشعارات يُبنى عند الإرسال من الحالة الحية: «سنعيد المحاولة في…» لا تُكتب إلا مع تجديد تلقائي مفعّل وبطاقة صالحة ويوم محاولة يسبق تعليق الاشتراك بالمتابعة؛ وإن تعذّر خصم وُعد به (باقة لا تتيحه، بطاقة لمزود آخر أو نمط آخر أو منتهية أو غير فعّالة، مبلغ دون الحد) أُرسل للعميل إشعار `card_charge_skipped` واحد لكل فاتورة يقول إنه يدفعها بنفسه وسبب ذلك، و`renewal_upcoming` لا يعد بخصم لا يمكن أن يحدث. رفض صلب بعد رفض ناعم يستبدل الإشعار المعلّق بإشعار واحد «لا محاولات أخرى». (7) جدول التصنيف في `payment-decline.ts`: رسالة «3DS: authentication is unavailable، please try again later» ناعمة، وأُضيفت عبارات مصدري البطاقات المعروفة (`RESTRICTED CARD` و`SUSPECTED FRAUD` و`CARD NOT PERMITTED` و`INVALID CARD NUMBER` و`CLOSED ACCOUNT`) إلى الصلب وهي غير مرصودة في الاختبار الرملي؛ و`DO NOT HONOR` و`PICK UP CARD` ناعمتان. المحاولات الناعمة المعادة (+1 و+3 و+5) لم تُجرَّب على المزود الحي، وتنتظر التحقق قبل الإطلاق. (8) ترتيب الأقفال الواحد في كل مسار: عميل ثم اشتراك ثم طلب ثم محاولة ثم صف طريقة الدفع (`lockSettlement`)، ومسار التسوية يأخذ العميل والاشتراك أولًا دائمًا؛ مهمة الخصم تأخذ الاشتراك ثم الطلب بـ`SKIP LOCKED` فلا تنتظر تسوية جارية. حفظ بطاقة جديدة لا يشغّل التجديد التلقائي أثناء قفل القاعدة المجانية أو مهلة الحذف (يُسجَّل `auto_renew.not_enabled`). حذف بطاقة قديمة غير فعّالة ما زالت علّمة افتراضية لا يوقف التجديد، وبطاقة لمزود آخر أو نمط آخر تُعلَّم محذوفة محليًا بلا نداء للمزود ويُطلب حذف رمزها عندما يكون ذلك المزود مهيّأً.

**مراجعة مسار نموذج البطاقة.** ميزانية الرفض لا تمنع قراءة المزوّد ولا التسوية أبدًا: تحدّ فقط من كتابة صفوف التدقيق (20 في الساعة لكل طلب، و200 للرفض `bad_shape` وحده) ويكتب أول تجاوز صفًا واحدًا `payment.form_rejection_suppressed` يصل البائع تنبيهًا. أسباب قد تتغير وحدها (`intent_not_fulfilled` و`payment_not_found`) يُجاب عنها ليعيد المزوّد المحاولة ولا يُكتب شيء ولا يُحفظ في الذاكرة؛ الدائمة فقط تُكتب وتُحفظ خمس دقائق. الربط والتسوية معاملة واحدة، وترتيب الأقفال عميل ثم اشتراك ثم طلب ثم محاولة ثم صف طريقة الدفع في كل مسار (التفاصيل أدناه). كل نموذج يُفتح لشخص (`payment_attempts.opened_by`، `schema_064.sql`) وهو من يوافق على حفظ البطاقة ويُسجَّل `created_by` للبطاقة؛ لا يُسلَّم سرّ نية حي لشخص آخر بل تُلغى النية غير المستعملة وتُفتح نية جديدة بخياره، وإن قد تحمل النية دفعة يُرفض الطلب بـ`payment_in_progress`. النية المنتهية (`created` بعد `expires_at`، الحالة المشتقة `expired`) لا تحمل دفعة. بنود الانتباه `form_payment_review` تبقى حتى تُسوّى الدفعة أو تُردّ (لا حدّ 14 يومًا) وبلا عميل إن لم تحمل سرّ أي محاولة.

### 4.5.1 عمل مشترك عالق في `needs_intervention` (#446)

- العمل العالق يحجب كل أمر جديد على مساحة العميل. الإجراءان يتطلبان `vendor.operations.run` وتأكيد step-up، والعامل المشترك وحده يصل إلى Odoo فيفحص الأثر ثم يسجّل النتيجة ويدقّق.
- **الاستعادة** `POST /v1/shared/tenants/:tenant/jobs/:job/recover` (`provision` و`backup` و`restore`): إن وُجد الأثر وثبت يُغلق العمل `verified`. لا يُعاد تنفيذ شيء.
- **التخلي** `POST /v1/shared/tenants/:tenant/jobs/:job/abandon` بجسم `{reason, confirm_job_id}` حيث `confirm_job_id` معرّف العمل نفسه (وإلا 422 `confirmation_mismatch`): يفحص العامل الأثر من جديد. إن كان غائبًا بيقين يُغلق العمل `failed` فيزول الحجب، وإن كان موجودًا يُرفض الطلب (`effect_present`) فيُستعمل زر الاستعادة، وإن كان الفحص `partial` أو `unknown` فلا يُغلق شيء (`failed` مع `effect_not_proven_absent`). لا إعادة جدولة تلقائية ولا يُعاد تشغيل العمل المغلق.
- **المسموح بالتخلي**: `backup` (لا أثر ولا شيء يشير إليه) و`restore` (لكل موافقة قاعدة هدف جديدة، فالموافقة التالية عمل جديد). **غير مسموح**: `provision` (صف الإعداد وطلب العميل مربوطان بذلك العمل وحده، ولا مسار يبدأ ثانيًا فيبقيان معلّقين) و`reconfigure` (بروتوكول إيصاله يكتب في Odoo ويُستأنف من المجدوِل وطلبه يفشل عبر المسار التجاري). القائمة في `ABANDONABLE_OPERATIONS` بحزمة العقود.
- **العدّاد والقائمة**: عدّاد «العمليات الفاشلة» في نظرة عامة وقائمة `/operations?status=attention` يستعملان تعريفًا واحدًا (`failed` و`needs_intervention`). العمل المتخلَّى عنه يبقى `failed` فيظهر في العدّاد والقائمة معًا، إذ لا يوجد في النموذج حاليًا تمييز «تمت المعالجة» لعملية. سؤال مفتوح للمالك: هل يخرج العمل المتخلَّى عنه من «يحتاج انتباهًا» بعد معالجته؟
- **قبل التخلي**: تأكد على مضيف العامل أن لا عملية نسخ أو استعادة حية ما زالت تعمل لهذا العمل (حاوية أو عملية)؛ أثر متأخر بعد الإغلاق يترك ملفًا أو قاعدة يتيمة لا يعرفها النظام. فحص العامل لا يُثبت غياب عملية ما زالت تكتب.
- `provision` غير مسموح لسبب إضافي: مفتاحه التجاري ثابت بالتصميم (`initial` لكل مساحة) فلا يتولد عمل ثانٍ، وجهاز التنفيذ يحجز على المضيف ملفات `reservations/` و`credentials/` و`classifications/` بـ`O_EXCL` لكل قاعدة (`tools/shared_saas_lifecycle/odoo_effect.py`)، فلا تنجح محاولة ثانية قبل أن يحذفها مشغّل المضيف. لا مسار داخل لوحة التحكم يعالج هذا.
- في لوحة المشغّل: صفحة العملية تعرض قسم «التخلي عن هذه العملية» للعمل العالق المسموح، مع تأكيد وسبب، وآخر حالة طلب.

### 4.6 استعادة ثم مصالحة الاستحقاق التجاري قبل الفتح [قبول تشغيلي غير متحقق] [محلي جزئيًا]

- **[محلي]** نسخ/استعادة Odoo الحقيقيين (قاعدة + filestore) لعميلين وعزلهما: `docs/verification/shared-restore-acceptance.md` (2026-10-01، scratch فقط). أداة التشغيل: `tools/shared_saas_lifecycle` (انظر README)؛ الموافقة عبر `admin approve-restore`.
- في Compose أحادي المجموعة، يقرأ العامل الاشتراك من هدف الاستعادة المعزول ويطبّق عليه المراجعة التجارية الحالية إذا لزم. اختلاف حالة الاشتراك أو تاريخ صلاحيته، أو تعذر رصد الهدف، يبقي المسار خلف `commercial_reconciliation_pending`. إذا استمر اختلاف القراءة بعد إصلاح متحقق ينتقل العمل للتدخل اليدوي. عند تشغيل توجيه الإصدارات تبقى المصالحة محجوبة حتى يدعم فاحص المجموعة هدف الاستعادة. راجع [دليل إصدارات النشر](../../deploy/releases/README.md) و[سجل القبول](../verification/2026-11-09-saas-commercial-acceptance.md).
- لا تُفتح المساحة المستعادة للعميل قبل نجاح المصالحة وتسجيل نتيجتها؛ لا تُعدّل الاستحقاقات أو الفروع يدويًا لتجاوز الحاجز.
- أثر النسخ على بقية العملاء: النسخ المحلي قد يوقف Odoo المشترك لفترة قصيرة؛ غير مقاس على staging **[محجوب]**.

## 5. التنبيهات والإجراء لكل منها

**المراقبة موجودة في المصدر فقط، ولم تُجرَّب على قناة إنتاج.** المُصدِّر هو `deploy/alerts.py`: خمسة أحداث ثابتة، قناتان فقط (بريد إلى المالك وTelegram)، ولا واجهة لإرسال نص حر. الشيفرة ومحاكيها الآلي (بلا شبكة) موجودان، ولم يُسلَّم تنبيه واحد عبر SMTP أو Bot API حقيقي؛ لذلك حالة هذا القسم **[محلي جزئيًا]** للشيفرة و**[غير مختبر]** لكل مسار تسليم فعلي. لا يعني وجود الملف وجود مراقبة تعمل في الإنتاج.

**ما لا يفعله هذا التعديل:** لا تستدعي `deploy/backup.py` ولا `deploy/restore_verify.py` التنبيه بنفسيهما. المُشغِّل أو مهمة cron يشغّل الأمر المقابل في الجدول عند فشل الأداة أو تجاوز العتبة، والربط الآلي بين الأداة والتنبيه خطوة تالية غير منجزة. المستلم هو المالك عبر قناتي البريد وTelegram أدناه؛ ولا مسؤول مناوب مسمّى بعد، ويُحدَّد قبل الإطلاق.

**متغيرات البيئة (أسماء فقط، ولا قيم في هذا الملف).** كل سر يُحقن من مدير الأسرار ولا يُسجَّل ولا يُمرَّر في سطر الأوامر، ولا يظهر في أي موضوع أو نص يُرسل.

| المتغير | الاستخدام |
|---|---|
| `LIWAN_ALERT_SMTP_HOST`, `LIWAN_ALERT_SMTP_PORT` | مضيف SMTP ومنفذه (الافتراضي 587) |
| `LIWAN_ALERT_SMTP_FROM`, `LIWAN_ALERT_SMTP_TO` | المرسِل ومستلمو المالك (مفصولون بفواصل) |
| `LIWAN_ALERT_SMTP_USER`, `LIWAN_ALERT_SMTP_PASSWORD` | اعتماد SMTP اختياري (سر)؛ يُضبطان معًا أو لا يُضبطان |
| `LIWAN_ALERT_SMTP_STARTTLS` | STARTTLS مفعّل افتراضيًا؛ `false` يلغيه صراحة |
| `LIWAN_ALERT_TELEGRAM_BOT_TOKEN` | رمز البوت (سر) |
| `LIWAN_ALERT_TELEGRAM_CHAT_ID` | محادثة المالك |

قناة لم يضبط المشغّل أي متغير منها تبقى معطّلة بسبب مسجّل في المخرجات، أما قناة نصف مضبوطة (رمز بلا محادثة، أو مضيف بريد بلا مرسل) فتُرفض ولا تُعطَّل بصمت. وإن لم تُضبط أي قناة يخرج الأمر بالرمز 2 ولا يرسل شيئًا: التنبيه المهمَل عيب، لا سلوك افتراضي.

**تشغيل تنبيه واحد** (من جذر المستودع؛ يطبع JSON على stdout بلا أي سر):

```sh
python3 -B deploy/alerts.py backup_failed --database <db> --reason "<سبب قصير بلا مسار سري>"
python3 -B deploy/alerts.py backup_stale --database <db> --age-seconds <ثوانٍ> [--rpo-seconds 3600]
python3 -B deploy/alerts.py disk_high --host <host> --used-percent <نسبة> [--threshold-percent 85]
python3 -B deploy/alerts.py container_unhealthy --container <اسم الحاوية>
python3 -B deploy/alerts.py restore_drill_failed --database <db> --reason "<سبب قصير>"
```

`container_unhealthy` يُشغَّل بعد قراءة الحالة من Docker: الحالة `starting` لا تُنبّه، و`healthy` تُطبع `"alerted": false`، وأي حالة أخرى تُرفض (الرمز 2) ولا تُقرأ كسليمة. رموز الخروج: `0` أُرسل أو لم تُتجاوز العتبة (`"alerted": false`)، `1` فشلت قناة واحدة على الأقل ويُسمّى اسمها في stderr وفي حقل `channels`، `2` تهيئة أو مدخل مرفوض، ولم يُرسل شيء. فشل قناة لا يمنع الأخرى، ولا يُغلق الأمر بنجاح إذا بقي تنبيه غير مسلَّم.

| التنبيه | المُصدِّر | الإشارة | الإجراء الأول | الإجراء اللاحق |
|---|---|---|---|---|
| رفض webhook الدفع | يدوي (بلا مُصدِّر آلي) | ارتفاع رموز `signature_invalid/merchant_mismatch/mode_mismatch` | 4.2: تحقق الأسرار/الحساب/الوضع | إن كان تزويرًا: حافظ على الرفض وراجع المصدر |
| فحص تكرار الفاتورة | يدوي | أكثر من فاتورة للاشتراك/الفترة/النوع، أو دفعتان ناجحتان لطلب واحد | أوقف التجديد الجماعي؛ افحص `renewals` و`payment_events` | تسوية عبر `invoice_adjustments` (لا تعدّل الفاتورة)، قرار رد يدوي |
| تجهيز متعثر | يدوي | طلب `paid` بلا `applied` بعد مهلة، أو مهمة بلا تقدّم/lease منتهٍ | 4.1 | تصعيد `needs_intervention` |
| عدم تطابق desired/observed | يدوي | `observed_digest` ≠ مقصود الاتفاق، أو فروع/حدود Odoo تخالف الاشتراك | قارن readback بإصدار الاشتراك | أعد reconfigure؛ لا تعلن النجاح قبل التطابق |
| تقادم الاستخدام | يدوي | `usage_snapshots.freshness` = `stale/unavailable` لأكثر من المهلة | تحقق وصول العامل إلى Odoo | لا تفرض حدودًا/فوترة اعتمادًا على قراءة قديمة بلا قرار |
| فشل تسليم الدعوة | يدوي | فشل SMTP/ارتداد/دعوة غير مفتوحة | تحقق `LIWAN_MAIL_*` وTLS | أعد إرسال دعوة جديدة (رموز الدعوة محدودة)؛ لا تُرسل كلمة مرور مباشرة |
| فشل النسخ الاحتياطي | `backup_failed` | أداة النسخ خرجت بخطأ أو `pg_dump` فشل | اقرأ سجل الأداة، ثم أعد النسخة بعد إصلاح السبب | افحص المساحة والصلاحيات على مضيف النسخ |
| تقادم النسخة الاحتياطية | `backup_stale` | عمر آخر نسخة ناجحة يتجاوز RPO (ساعة) | شغّل نسخة احتياطية الآن | افحص مجدول النسخ والمساحة الحرة؛ لا تعلن RPO متحققًا قبل قياسه |
| فشل تمرين الاستعادة | `restore_drill_failed` | `deploy/restore_verify.py` أو تمرين RPO/RTO لم يعد النسخة قابلة للاستخدام | لا تعتبر النسخة قابلة للاستعادة؛ أعد التمرين على قاعدة scratch | أصلح سبب الفشل وحدّث تقرير التحقق |
| امتلاء قرص المضيف | `disk_high` | نسبة الاستخدام ≥ العتبة المضبوطة | حرّر مساحة (سجلات أو نسخ قديمة) أو وسّع القرص | راجع النمو وأضف عتبة أدق بعد قياس |
| حاوية غير سليمة | `container_unhealthy` | Docker health = `unhealthy` | `docker inspect` ثم `docker logs`، وأعد التشغيل بعد تحديد السبب | افحص `LIWAN_ODOO_*` وحدود الذاكرة إن تكرر |

**تنبيهات المالك التجارية (بريد وTelegram).** العامل المشترك يشغّل مهمة `vendor-alerts` التي تُبلغ المالك بأحداث الاشتراكات دون فتح قائمة الانتباه: تسجيل عميل جديد، تأخر تسليم المساحة 30 دقيقة، تحويل بنكي بانتظار التأكيد (الخطوة اليدوية الوحيدة المقصودة)، الدفعات، تعثر السداد والتعليق، الإلغاء والتراجع، الاسترداد (طلبه واكتماله، وفشله أو تعثر تسجيله وهما يتطلبان إجراء)، نهاية التجربة، وأي بند جديد يدخل قائمة الانتباه. لكل واقعة مفتاح يمنع التكرار، وأكثر من 5 تنبيهات من نوع واحد خلال ساعة تُجمع في سطر ملخص واحد؛ والأنواع التي تتطلب إجراء لا تُجمع. المتغيرات: `LIWAN_VENDOR_ALERT_EMAIL_TO` وهي نفسها `LIWAN_ALERT_TELEGRAM_BOT_TOKEN` و`LIWAN_ALERT_TELEGRAM_CHAT_ID` التي تقرأها `deploy/alerts.py`، ومفتاحا الإيقاف `LIWAN_VENDOR_ALERT_EMAIL` و`LIWAN_VENDOR_ALERT_TELEGRAM`؛ التفاصيل في `deploy/control-plane/OPERATIONS.md`. الحالة **[محلي جزئيًا]**: اختبارات حية بمرسِلات محقونة، ولم يُسلَّم تنبيه عبر SMTP أو Bot API حقيقي **[غير مختبر]**.

**دعوة المسؤول الأول: طلب العميل لدعوة جديدة.** المسؤول الذي ضاعت دعوته أو انتهت (72 ساعة) يطلب دعوة جديدة بنفسه من صفحة الدعوة (`/invite/accept`، وتصله من رابط «لم تصلك دعوة التفعيل؟» في صفحة الدخول)، دون خطوة من البائع؛ زر «إعادة الإرسال» في صفحة العميل يبقى كما هو. المسار `POST /api/invitations/reissue` ثم `POST /v1/invitations/reissue` في لوحة التحكم، وكلاهما يعيد 202 `{ok:true}` سواء طابق العنوان أم لا. القواعد: المستأجر يُؤخذ من المضيف الذي وقّعه خادم Nuxt ولا يأتي من الجسم؛ البريد يُرسل دائمًا إلى `customers.admin_login` وليس إلى العنوان المكتوب؛ لا تُصدَر دعوة إن قُبلت الدعوة من قبل (الحالة حينها «نسيت كلمة المرور؟»)؛ كل دعوة جديدة تُلغي السابقة (`issueInvitation` دالة الإصدار الوحيدة للمسارين)؛ حدّ المستأجر دعوة كل 60 ثانية و5 دعوات في الساعة (تُحسب كل الدعوات الصادرة له)، وحدّ الزائر 5 طلبات كل 10 دقائق لكل مساحة (429)، والعنوان يأتي موقّعًا من الحافة (`X-Liwan-Client-Ip` في `deploy/shared/Caddyfile`)؛ طلب بلا عنوان موقّع يُرفض ولا يقع في سلة مشتركة. الطلب يُسجَّل فقط في `commercial_outbox` بالنوع `invitation.reissue` ويجيب 202 فورًا، والعامل (المجدول) هو من يبحث ويُصدر، فلا يختلف زمن الجواب بحسب العنوان؛ ويجري الفحص والإصدار تحت قفل المستأجر فلا يتجاوز طلبان متوازيان الحدّ. يُسجَّل كل إصدار في `audit_events` بالإجراء `invitation.reissued`: الفاعل `customer:self_request` وفي `metadata` المصدر `customer_request` وعنوان الزائر، أو الفاعل حساب البائع والمصدر `vendor`. إن شكا عميل أن الدعوة لا تصل، فابحث عن `invitation.reissued` لمستأجره قبل إرسال دعوة يدوية: قد يكون حدّ الساعة قد بلغ.

**البحث عن مساحة العمل (`/find-workspace` على المضيف المشترك).** المدير الذي ضاع منه عنوان مساحته يكتب بريده في صفحة `/find-workspace` ويجتاز التحقق الأمني نفسه الخاص بالتسجيل؛ ويحوّل المضيف المشترك `/login` إليها (تحويل 302، وصفحة الدخول في مضيفات المستأجرين كما هي). الجواب دائمًا الجملة نفسها: «إن كان هذا البريد يدير مساحة عمل، أرسلنا عنوانها إليه». المسار `POST /api/invitations/find-workspace` ثم `POST /v1/customer/find-workspace` في لوحة التحكم، ولا يُخدم إلا من المضيف المشترك مع تفعيل التسجيل العام. لا يوجد مستأجر في المضيف المشترك، فيوقّع خادم Nuxt عنوان الزائر مع الجسم (`liwan-find-workspace:<عنوان>\n<جسم>`) بمفتاح خدمة العميل نفسه وتُستهلك البصمة مرة واحدة كما في التسجيل؛ والعنوان يأتي من الحافة (`X-Liwan-Client-Ip` لهذا المسار فقط في `deploy/shared/Caddyfile`، ويمرره `guard.mjs` لمضيف الزوار)، وطلب بلا عنوان موقّع يُرفض. لوحة التحكم هي من يتحقق من رمز Turnstile (يفشل مغلقًا ومطلوب في كل طلب) ثم تسجّل الطلب فقط في `commercial_outbox` بالنوع `workspace.lookup` وتجيب 202 فورًا، والمجدول (`workspace-lookup`) هو من يبحث: `lower(customers.admin_login)` يساوي العنوان المكتوب، بشرط ربط مفعّل في `shared_registry_bindings` وأول باقة مطبّقة، ثم يضع رسالة واحدة في `workspace.lookup.notice` تسرد كل مساحات العنوان وتُرسل إلى `admin_login` فقط (عربي ثم إنجليزي، بلا رمز ولا دخول). لا يطابق شيء فلا يُرسل شيء، ويُحذف العنوان المكتوب من الصف بعد المعالجة أو عند الفشل النهائي. المساحة الموقوفة بسبب الدفع أو التي عليها طلب حذف مؤكد أو مستحق تُرسل كغيرها (المساحة موجودة حتى يزيلها البائع، ومديرها يحتاج إليها للدفع أو لسحب الطلب)؛ والمساحة التي لم تُسلَّم بعد أو ربطها معطّل لا تُرسل. الحدود: 5 طلبات كل 10 دقائق لكل عنوان زائر موقّع (429)، ورسالة كل 60 ثانية و3 رسائل في الساعة لكل عنوان مسجّل (تُحسب من `audit_events` بالإجراء `workspace.lookup.mailed`)، وحدّ يومي عام 200 رسالة؛ وتُتخذ القرارات تحت قفل استشاري واحد فلا يتجاوز طلبان متوازيان الحدّ، ويبقى الجواب للزائر واحدًا عند بلوغ أي حدّ من الثلاثة الأخيرة. إن شكا عميل أن الرسالة لا تصل فابحث عن `workspace.lookup.mailed` لمساحته قبل إرسال العنوان يدويًا: قد يكون حدّ الساعة أو الحدّ اليومي قد بلغ.

**العتبات.** RPO **ساعة واحدة** وRTO **أربع ساعات** معتمدان (قرار المالك 2026-11-06). عتبة القرص (الافتراضي 85%) وفترة فحص صحة الحاويات يضبطهما المشغّل، وفترة الفحص لم تُقنَّن بعد. جملة أعلى هذا الملف («لا يقدّم هذا الدليل أي وعد SLA أو RPO/RTO؛ أهداف السعة وSLA مفتوحة») سبقت هذا القرار ولم تُحدَّث في هذا التعديل؛ المرجع لأهداف RPO/RTO هو هذه الفقرة. ولا يمنح هذا القسم وعد SLA أو دليل استيفاء RPO/RTO في الإنتاج.

## 6. ما لم يُتحقق منه

- لا يثبت هذا الدليل وجود عامل مشترك نشط أو قبولًا على staging. سجل 2026-10-04 يثبت اختبار إنشاء فاتورة Moyasar وقراءتها في الوضع التجريبي فقط؛ لا يثبت دفعًا مكتملًا أو webhook عامًا أو 3DS أو استردادًا أو مصالحة مزود end-to-end. توفر إعدادات SMTP وstaging الحالي غير متحقق؛ تبقى إجراءات الدفع والبريد **[محجوب]** حتى فحص البيئة وإتمام قبولها.
- الاختبارات المحلية لا تثبت الدفع الحقيقي أو السعة أو الإنتاج؛ لا commit/merge/deploy مأذون.
- تنبيهات §5 لم تُسلَّم عبر قناة حقيقية بعد: لا SMTP ولا Bot API مُجرَّبان، ولا مهمة cron مربوطة بأداة النسخ أو الاستعادة، ولا عتبة قرص مقيسة. دليلها محاكٍ آلي بلا شبكة **[محلي جزئيًا]**، وكل مسار تسليم فعلي **[غير مختبر]**. ولا يعني وجود `deploy/alerts.py` أن المراقبة قائمة في بيئة منشورة.
- فاتورة ZATCA الرسمية خارج النطاق؛ الضريبة 15% حصرية كبند مستقل، وتحتاج مراجعة تاجر/قانونية.
- الأقسام الموسومة **[قبول تشغيلي غير متحقق]** أو **[غير مختبر]** لا تُستخدم كإجراء إنتاج معتمد حتى يثبت قبولها في البيئة المقصودة. لا تعني هذه المراجعة اعتماد staging أو merge أو deploy.

## 7. قائمة التحقق قبل استعمال مفاتيح حية للدفع بالبطاقة [قبول تشغيلي غير متحقق]

لا تُستعمل مفاتيح Moyasar الحية قبل إكمال هذه البنود وتسجيل نتيجة كل بند:

1. **الدفع بدون 3-D Secure.** كائن الدفع لا يكشف هل مرّ الدافع بـ3-D Secure (الحقل `authenticated` يبقى `null` ويُسجَّل في حدث التدقيق `payment.form_settled`)، والمتصفح قادر على طلب `3ds: false` عند إتمام النية. يجب أن يؤكد المشغّل في لوحة Moyasar، وعلى الحساب الحي نفسه، أن مفتاح السماح بالمدفوعات بلا 3-D Secure (MOTO) مغلق للمدفوعات التي يبدأها العميل، وأن يسجّل تاريخ التأكيد واسم المؤكِّد. المرجع: `docs/operations/moyasar-form-spike.md`، السؤال 2.
2. **مفتاح النشر.** `MOYASAR_PUBLISHABLE_KEY` من الحساب نفسه ونمط `pk_live_` عند `MOYASAR_MODE=live`؛ يرفض المحوّل التقاطع بين نمطي المفتاحين.
3. **حذف الرموز.** مهمة `payment-tokens` في المجدول تعيد محاولة حذف رمز بطاقة استُبدلت أو لم تُطلب. صف `payment_token.delete` معلّق في `commercial_outbox` يعني رمزًا ما زال عند المزود.
4. **دفعة وصلت بلا تطابق.** حدث التدقيق `payment.form_payment_rejected` أو `payment.form_hint_rejected` يعني مالًا قد يكون وصل ولم يُسوَّ (مبلغ أو رابط عودة لا يطابق المحاولة). يُراجع المشغّل معرّف الدفع في الحدث ويستردّه عند المزود إن كان حقيقيًا.
