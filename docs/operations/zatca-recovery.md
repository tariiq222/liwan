# ZATCA readiness and recovery

LiwanOS currently permits ZATCA onboarding and submission in the developer sandbox. The simulation and production environments remain closed. An authorized user can read the current mode, pending work and journal expiry on the finance ZATCA page. The scheduler runs the stock EDI fallback hourly and preserves its immediate triggers and error handling.

## Before a release can enable a new environment

- Confirm the reference taxpayer's written consent, portal access and simulation terms. The taxpayer supplies the OTP through the authorized UI and retains control of portal credentials. Collect the requested document and correction outcomes, including reference simulation evidence and accounting sign-off. [ZATCA educational library](https://zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Pages/default.aspx)
- Record the certificate validity from the certificate and plan against the 30, 7 and 1 day warnings. ZATCA describes renewal before expiry. The pinned Odoo journal rejects renewal before expiry through its existing workflow. Record how the reference release addresses this gap and the resulting outage risk before authorizing real use. [ZATCA detailed technical guideline](https://www.zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Documents/E-invoicing-Detailed-Technical-Guideline.pdf)
- Confirm the published responsibility split, exact reviewed commit and separate owner release approval. The customer owns portal access, OTPs, revocation and invoice data. LiwanOS owns signing, chaining, XML generation and submission behavior. Do not treat a local fake gateway, a sandbox result or the mode endpoint as release authorization.

## Recover a tenant after data loss

1. Freeze ZATCA submissions and document generation for the affected EGS units while preserving the current database, filestore and incident logs. Identify the exact tenant, company and sales journal. Keep the original backup read-only. A restored copy must have network submissions disabled.
2. On the isolated restored copy, record the backup boundary and the latest available original UUID, invoice counter, document hash and chain link for each affected journal. Compare against accepted, rejected and unresolved documents from the incident period using the taxpayer's FATOORA evidence and retained original XML. A rejection still matters to chain continuity. Keep private keys, OTPs, tokens and raw credential material out of incident records. [ZATCA detailed technical guideline, chain examples](https://www.zatca.gov.sa/en/E-Invoicing/Introduction/Guidelines/Documents/E-invoicing-Detailed-Technical-Guideline.pdf)
3. Have accounting and the operator reconcile each document and its external outcome before proposing recovery. Preserve original evidence for uncertain outcomes and seek the taxpayer's ZATCA guidance where necessary. A corrected rejection and a timed-out submission are separate cases. Do not overwrite hash heads, renumber or blindly resend.
4. Approve a recovery plan specific to the affected EGS and document sequence. Confirm certificate state and current gateway rules before resuming. If data loss interrupted e-invoice generation, the taxpayer follows the applicable failure notification procedure. [ZATCA failure notification](https://zatca.gov.sa/en/E-Invoicing/FailureNotifications/Pages/VerifyTaxpayer.aspx)
5. Record reconciliation, approvals, exact restore identity and the first verified post-recovery state before restoring normal operation. Customer-hosted operators follow the same controls locally without a LiwanOS vendor connection.
