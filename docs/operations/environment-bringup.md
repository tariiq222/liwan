# Environment bring-up: staging and production

How to bring up one LiwanOS server so that a release tag reaches it with no manual step. There are two server environments:
staging on the Oracle Arm host `liwanos-staging` and production on the Oracle Jeddah Arm host `liwanos-prod`. The owner
cancelled the development environment on 2026-11-21 (decision in
[integration-rules.md](../agents/integration-rules.md#from-task-branch-to-each-environment-owner-decision-2026-11-21)):
local machines are development and no server follows `main`. This page states what to create and how to see that it works;
it is not a release or deployment approval. Section A was written for staging and corrected on its first bring-up; section C
(production) has not been run on a real host. No secret value belongs on this page or in the checklists: record where a
value lives, never the value. The Contabo host now holds only Sentry and the Openship panel that manages it, and reaches
neither Oracle host; see [tooling-server.md](tooling-server.md).

Related files: [environments/README.md](../../deploy/environments/README.md) (the env templates and every variable),
[release/README.md](../../deploy/release/README.md) (the release command), [tooling-server.md](tooling-server.md) (the
tooling host), [control-plane-deployment.md](control-plane-deployment.md) (control plane and shared worker),
[edge-rate-limit.md](../../deploy/security/edge-rate-limit.md#shared-edge-behind-an-outer-edge) (the trusted proxy).

## How it fits together

```
client --HTTPS--> Openship edge (host network, 80/443; wildcard certificate by DNS-01, apex by HTTP-01)
                    --HTTP, Host unchanged, X-Forwarded-For appended--> 127.0.0.1:18080
                       Caddy `proxy` (published on loopback only, trusts the edge gateway 172.29.50.1)
                          --> guard:8080 --> web / odoo
GitHub Actions (publish.yml, release tag only) --POST hook--> Openship job `liwan-staging-release`
                                           --> deploy/release/release.py run --environment staging
```

- Openship owns TLS and the public ports. The stack's Caddy owns rate limits and the guard hop. The release command
  owns compose: nobody runs `docker compose up` by hand next to the job.
- The staging host runs the Openship panel (`openship.liwanos.com`) and its edge itself. Production is registered as a
  server in that panel.
- Staging follows the highest `release/19.0.X.Y.Z` tag, arm64 required, and is updated only when the owner says to
  publish to staging: that creates the release tag; the tag run builds the nine arm64 images on `ubuntu-24.04-arm` (17 to
  23 minutes), publishes the release document and calls the staging hook. Staging waits for that build. A push to `main`
  builds and publishes nothing and reaches no server. Only arm64 is built.
- Production job has no hook: the owner starts it from Openship with an explicit `--tag <tag>` and it never picks the highest tag by itself. It takes
  only a tag that staging already served and passed; the coordinator checks this by hand until the enforced gate of
  plan part P7 exists.

## How to use the checklists

Run each command, paste the observed result in the last column and sign the row. A row without an observed result is
not done. A secret never goes in the result column: write where it was stored.

## A. Staging on the Oracle `liwanos-staging` host

Order on a fresh host:

1. Before the first `release.py run`: A1 (DNS), A2 (edge route), A3.1 and A3.3 to A3.6 (account, directories, bootstrap
   checkout, host packages, firewall), A4.1 to A4.5 (shared env file and release config), then A3.2 (`init-host.sh`,
   which needs the checkout and the shared env file, and creates the control database password file that the control env
   file of A4.6 needs), then A4.6 to A4.12 (the other env files), A5 (read token), A6 (unit installed and enabled, not
   started), A7 (job and hook).
2. The first run itself: A8 (`release.py run`). Its `commit` step starts the shared worker.
3. After the first run: the owner bootstrap, the catalog import and the Moyasar webhook, from
   [control-plane-deployment.md](control-plane-deployment.md) "First deployment"; also section D (the vendor console and
   webhook hosts); then A9 (acceptance).

#### Moving an existing host to the effect boundary

A host prepared before the effect account existed has `liwan-worker` in the `docker` group and worker-owned state directories. Do these as root, in this order, on a host without tenants (a host with tenants needs the owner's go first).

1. Release the version that carries the gate. While `LIWAN_EFFECT_SOCKET` is unset the worker starts the gate directly as a child, so the old host keeps working.
2. `systemctl stop liwan-shared-worker`. Create `liwan-effect` and add it to `docker` (A3.1), then `gpasswd -d liwan-worker docker`.
3. Set `shared.env` to `root:docker` 0640 and do the same for the rendered compose file named by `composeFile` (`chown root:docker`, `chmod 0640`). Create `/etc/liwan/docker` with a root-owned `config.json` holding `{}`.
4. Change the state directory to `root:liwan-worker` 3770 and `control/config` and its JSON files to `root:liwan-worker` 0750 and 0640. Then change the old state subdirectories by hand, once: `chown -R liwan-effect:liwan-worker` on `reservations credentials classifications restore-effects reconfigure runtime-gate-history tenant-storage backups`, followed by `chmod 0700` on each (0755 on `classifications`, 0750 on `backups`). Do not run one blanket `chmod` or `chown` over the state directory: containers read `classifications` as another uid, and a recursive change would also follow content the worker wrote. `init-host.sh` refuses a subdirectory that the worker owns or can write, because that content may have been planted by a less trusted account: review it, then change the owner as above and run the script again. Look at the files inside before keeping them.
5. Run `init-host.sh` (A3.2) again; it must report every path as settled or kept and stop at nothing.
6. Install the three units (A6.1), `systemctl daemon-reload`, enable the socket, start the worker.
7. Prove it: a scheduler tick and a usage observation work; an invitation password set works (A9.1); one backup from the vendor console works and the control plane reads the manifest; stop the worker during a backup and, after 90 seconds (the unit's `TimeoutStopSec`), no `liwan-effect@` instance is active and `docker ps --filter name=-effect-` is empty.

Things the gate and `init-host.sh` refuse, and what to do:

- A directory that holds a trusted path (the config, the compose file, the shared env file, `/etc/liwan/docker`, the config directory) must be owned by root and closed to group and other. `init-host.sh` stops with "Refusing: ... must be owned by root and not writable by group or other" when its `trusted_parent` rule fails, and the gate answers `runtime_untrusted`. A directory the worker owns or can write is refused: change its owner to root and its mode to 0755 or 0750, then run again. The state directory is the one deliberate exception (`root:liwan-worker` 3770).
- `/opt/liwan/current` must be root-owned (and so must its parent directories and the release checkout it points to): the gate runs with it as its working directory and imports `tools.shared_saas_lifecycle` from there, so a checkout the worker can write would let it run code as `liwan-effect`.
- `/etc/liwan/effect.env` is optional and `init-host.sh` does not create it. It is the operator's file (root-owned, mode 0600, plain `KEY=value` lines); without it a tenant drop stays a dry run.
- `restore-registry` on a host from before this change is worker-owned: `chown liwan-effect:liwan-worker` and `chmod 0775` it (look at its content first), then run `init-host.sh` again. The control plane must not `chmod` it (it cannot: it is not the owner).

To go back: add `liwan-worker` to `docker` again, remove the `Environment=LIWAN_EFFECT_SOCKET` line from the worker unit, and, so that a gate the worker starts directly (as the old host did) is not refused with `runtime_untrusted`, give the effect subdirectories back to the worker: `chown liwan-worker:liwan-worker` on `reservations credentials classifications restore-effects reconfigure runtime-gate-history backups restore-registry`, `chmod 0700` on each (0755 on `classifications` and `restore-registry`, 0750 on `backups`), and restore `/opt/liwan/current` and the config directory to the owners the old gate expected (the gate accepts root or its own uid, so a worker-run gate needs `liwan-worker` ownership of the files it reads or root-owned files).

An interrupted backup and the shared Odoo service. A capture stops the shared `odoo` service for every tenant and starts it again at the end or when it fails. On a termination signal the effect cancels its running command, then starts `odoo` once more in its own session with the termination signals ignored, so a second signal (systemd's control-group kill and the gate's group SIGTERM arrive together) does not cut the restart. The numbers are consistent: effect cancel at most 25 s (docker kill 15 s, wait 10 s) plus restart at most 30 s (`RESTART_TIMEOUT` in `odoo_backup.py`) is 55 s, inside the gate's `KILL_GRACE` of 60 s and the unit's `TimeoutStopSec` of 90 s. There is no `ExecStopPost=` recovery script: a `runtime-gate` marker also means "an operator must look" after other failures, so starting `odoo` from it automatically is not safe. If Odoo is still down after an interrupted backup (`docker compose -p <project> ps odoo` shows it stopped, tenants answer 502), as root: `docker compose -p <project> -f <composeFile> --env-file <envFile> start odoo`, wait until `ps` shows it healthy, then look at `<stateDir>/runtime-gate` (do not delete it before you know why the capture stopped) and at the newest directory in `<stateDir>/backups`.

Three things only a real Linux host proves, and none is verified yet: the effect unit's `IPAddressDeny=any` with `IPAddressAllow=localhost` and `MemoryDenyWriteExecute=true` against the S3 upload of an effect (the off-site purge stays a direct child of the worker, but any effect that reaches S3 from the gate would fail under them); `docker compose` run with a read-only `DOCKER_CONFIG` (`/etc/liwan/docker`) and `HOME=/nonexistent`; and the ownership of the state subdirectories that an older host left behind (step 4). Record what each one does on the first staging run.

When the operator's address changes: edit `LIWAN_ADMIN_ALLOW` in the shared env file and recreate `proxy` with the command of D4. That is the one supported method. A Caddy reload is not enough, because the value is in the container environment. Write the value space separated, never with commas, and run the validation of D4 before the recreate: a malformed value stops Caddy from loading, which takes the edge down for every tenant. The recreate interrupts the whole edge for a few seconds for every tenant, so prefer a stable CIDR (a VPN or an office range) in the list over frequent edits. Until it is done the console answers 404 from the new address.

An SSH tunnel is not a supported method. It would pass the allowlist only if the `edge` network's gateway address were added to the list, which also lets any host-local process through. For the same reason never put the gateway address or `private_ranges` in `LIWAN_ADMIN_ALLOW`: behind the outer edge a request without `X-Forwarded-For` is seen as the gateway, a private address, so it would pass the list. The console also requires its `Origin` to be `https://<ADMIN_DOMAIN>` with `Secure` cookies, which a plain tunnel to the proxy's loopback port behind the outer edge does not provide.
