## Current policy invariants

- `odoo-addons/nasq_platform/models/entitlement_service.py:54-61,83-120,190-203` defines expiry and suspension as distinct. Expiry starts only after `valid_until` (UTC date) and preserves login/read access while blocking ordinary writes with `tenant_read_only`; password/TOTP remain exceptions. Suspension blocks customer login/session and logs out sessions, except enabled support access.
- `odoo-addons/nasq_platform/models/tenant_profile.py:21-35,180-186,211-255` and `commercial_config.py:8-13,29-72` bind SaaS to `control_plane`, non-SaaS to `local_policy`, forbid non-SaaS expiry, and make commercial classification immutable. `apps/control-plane/src/http.ts:114-120` rejects `tenant.entitle` for non-SaaS. Preserve these rules; do not reinterpret a policy change as automatic suspension or billing lifecycle.
- Feature availability and installed modules are separate: feature owners are checked against installed module ids in `odoo-addons/nasq_platform/models/entitlement_service.py:147-187`; module installation/composition is separately declared by `deploy/catalog/solutions/platform.json:7-40`, then verified by the provisioning path in `tools/nasq_cli/operator.py:630-690`. Withdrawing a feature must not remove a module or customer data.

## Required P3 design decisions and candidate checks

1. **Administrative renewal is a real roadmap requirement, not a deferral.** Grok confirmed the missing contract and execution path: `packages/commercial-contracts/src/index.ts:26-33` defines `tenant.entitle` with only expected revision and features (no `valid_until`); `apps/control-plane/src/worker.ts:140-155` only prepares feature policy; and the Odoo shell transaction in `tools/nasq_cli/operator.py:83-89` writes `{'features': policy['features']}` only. Therefore no current public entitlement operation can renew an expired SaaS cutoff. A later scoped implementation must add an explicitly authorized, audited administrative SaaS renewal contract/action carrying target, reason, `expected_revision`, and a UTC calendar date, and apply it under the same profile row lock and transaction. It must reject non-SaaS, preserve immutable commercial mode/source, and not invent billing. A renewal date control implements the roadmap; it is not a new billing lifecycle. No source or contract changes were made in this review.
2. **Confirmed source-level observed-policy gap; not proof of live failure.** Grok independently confirmed `apps/control-plane/src/worker.ts:227-230` synthesizes `observedPolicy` from the requested entitlement payload on successful operation rather than requiring the actual resulting profile snapshot. `finishClaim` stores it as `observed_policy` (`:167-185`); the durable receipt includes status/change/revision only (`tools/nasq_cli/operator.py:83-89,475-477`), not feature readback. The operator does perform the row-lock and expected-revision check before applying (`tools/nasq_cli/operator.py:58-94,435-479`), but that is not independent verification of resulting state. The bounded implementation contract must require actual readback of policy revision and feature map before observed policy is marked current/healthy. Add a negative test: successful operation receipt with missing or mismatched actual revision/features must fail or quarantine observation and must not mark requested policy observed. This is source-backed risk, not a demonstrated live failure.
3. Preserve the two-stage stale-policy protection: early snapshot rejection plus authoritative `SELECT ... FOR UPDATE`/cache invalidation and revision comparison in the same Odoo transaction (`tools/nasq_cli/operator.py:58-94,435-479`). The renewal action must use the same concurrency invariant. A pure unit test cannot prove the DB lock; exercise stale revision in adapter integration.
4. Health and policy evidence remain distinct. `tools/nasq_cli/operator.py:770-782` performs inspect/health reads and checks unsettled module state; `apps/control-plane/src/worker.ts:167-185,190-231` commits operation and observed state. Only verified actual readback advances `observed_policy`/revision; neither requested payload, successful HTTP enqueue, nor generic health timestamp is policy verification.
5. Preserve lifecycle semantics precisely: valid-through date remains active because expiry is only when `valid_until < UTC today` (`entitlement_service.py:54-61`); after expiry, login/read/password/TOTP behavior remains as existing tests define while ordinary writes are read-only (`tests/test_entitlements.py:89-97`, `tests/test_lifecycle.py:55-74`). Suspension is a separate administrative state that blocks customer login/session (`tests/test_lifecycle.py:44-53`). Renewal changes only the approved cutoff and revision; it must not silently suspend/activate, disable service due to control-plane outage, remove modules, or delete data. Preserve non-SaaS rejection (`http.ts:114-120`; platform constraints above).
