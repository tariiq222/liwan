## الثغرة المهمة التي أُصلحت

`nasq_platform` كان اعتماده على `nasq_api` فقط، وكل من `nasq_pmo` و`nasq_chat` يقرأ `nasq.tenant.profile` في ترحيله.

**الأثر:** `-u nasq_pmo` وحده — أو `-u nasq_chat` وحده — لا يثبّت `nasq_platform`، فيفشل الـbackfill بقراءة جدول غير موجود، وتتعطل الترقية. الأمر الموثّق الذي يرقّي الوحدات كلها كان يعمل، لكن مسار المشغّل الأحادي كان مكسورًا.

**الإصلاح:** `nasq_platform` صار اعتمادًا مباشرًا لـ`nasq_pmo` و`nasq_chat`.

**الإثبات بعد الإصلاح:**

| السيناريو | النتيجة |
| --- | --- |
| `-u nasq_pmo` وحده | `nasq_platform=installed`، `profile_rows=1`، `projects_null=0` |
| `-u nasq_chat` وحده | `nasq_platform=installed`، `channels_null=0` |
| `-u` للوحدات الست | `UPGRADE_SMOKE_OK installed=6` |

## إصلاحات أخرى

1. **إحكام الجدول الواحد:** أُضيف `CHECK(singleton_key = 'tenant')`. قبله كان `INSERT` مباشر بمفتاح آخر يُنشئ صفًا ثانيًا. الآن يفشل بـ`violates check constraint`، وهو مُثبت على قاعدة مُرقّاة.
2. **استعادة تأكيدات دقيقة:** في `test_meetings.py` كنت قد خفّفت الأعداد إلى `>=`. السبب الجذري كان أن الـfixture صار على الشركة الحالية، فصارت إشعارات الإسناد تظهر فعلاً. ثبّتُ الأعداد بالقيم الحقيقية: `(4, 4)` ثم `(1, 3)` ثم `read-all = 3`، مع تعليق يوضح المصدر. الإشارة لم تعد مخفية.

## ما قبلته المراجعة المستقلة دون اعتراض

- **L1:** قاعدة الشركة عامة بلا `groups`، لذلك تُAND مع قاعدة عضوية mail ولا تُبقي التسريب مفتوحًا.
- **L2:** `env(su=True).ref(...)` يعمل لمستخدم عام؛ الاختبار العام يثبته.
- **L3:** اتحاد المجموعات عبر الشركات مقصود في Odoo، والحماية قاعدة سجلات + `_nasq_scope`.
- **L4:** الترحيل `pre-` يعمل قبل تحميل XML للقواعد، فلا تبقى صفوف NULL مرئية.
- **`create()`:** `setdefault` لا يتجاوز قيمة صريحة، وفحص الشركة الأجنبية باقٍ.
- **ترتيب هجوم الحقن:** `company_id` موجود أصلًا في `PROJECT_CREATE_FIELDS`.

## المعلّقات الثلاثة — أُغلقت

### ١. رموز الحالة صارت مثبتة عند 403

كانت ثلاثة تأكيدات تقبل `403` أو `404`. السبب الفعلي: قاعدة الشركة المشددة تخفي المشروع داخل `get_record` عبر `check_access('read')` قبل أن يصل الطلب إلى فحص `404` في المتحكم. هذا هو نفس سلوك المشروع الأجنبي، وهو متسق لا عشوائي.

ثُبّتت الحالات الثلاث على `403` مع فحص `code == 'forbidden'`:

| الموضع | الحالة |
| --- | --- |
| `test_project_finance.py` — مشروع بلا شركة | 403 `forbidden` |
| `test_project_governance.py` — الموارد الثلاثة | 403 `forbidden` |
| `test_project_schedule.py` — الجدول الزمني | 403 |

الأولوية في `test_project_schedule.py:128` لمشروع غير مرئي بقيت كما هي، لأنها حالة مختلفة عن بلا شركة.

### ٢. الخطأ العابر — السبب الجذري: مهلة HTTP

شُخِّص بتشغيل المجموعة ثلاث مرات مع حفظ السجلات. الفشل ظهر مرة واحدة:

```
ERROR: TestProjectReports.test_dashboard_summary_shape_and_all_project_scope
requests.exceptions.ReadTimeout: HTTPConnectionPool(host='127.0.0.1', port=8209)
```

مهلة Odoo الافتراضية في `url_open` هي `timeout=12` ثانية (`odoo/tests/common.py:2322`). والاختبار يُنشئ 205 مشاريع ثم يجمّعها في طلب واحد.

القياس عبر ثلاث تشغيلات للاختبار نفسه: **2.6s، 5.0s، 15.1s** مقابل حد 12s. أي أنه كان على حد المهلة فعليًا، وليس خلل عزل أو منطق.

**الإصلاح:** إنشاء 201 مشروع بدل 205 — ما زال يتجاوز حد الصفحة 200 ويحفظ الغرض — وتمرير مهلة صريحة 60s عبر `NasqApiCase.api(..., timeout=...)`.

**الإثبات:** ثلاثة تشغيلات كاملة متتالية بعد الإصلاح: `0 failed, 0 error(s) of 610 tests` في كل مرة. وزمن الاختبار الثقيل صار داخل الحد.

ملاحظة تصحيحية: القياس الأولي الذي أظهر اختبارات أخرى بطيئة (27–38s) كان يقيس إعداد الأصناف بين الاختبارات لا طلب HTTP واحدًا؛ `TestTransition.test_unknown_state_rejected` سطران بلا HTTP أصلًا. لذلك لم تُغيَّر تلك الاختبارات.

## مخاطر متبقية معلنة

1. **تحذير `CHECK` على قاعدة قائمة:** إضافة القيد على قاعدة عميل قائمة تحتاج ترقية تتحقق من عدم وجود قيم غير `tenant`. لم توجد قيم مخالفة في أي تمرين.
2. **استنتاج الفشل عند غياب `xmlid`:** لو حُذف `nasq_platform.tenant_profile` من `ir_model_data` مع بقاء الصف، لا يُعاد إنشاؤه. احتمال ضعيف لأن `unlink` ممنوع.
3. **نمط `assertIn((403, 404))` ما زال قائمًا في اختبارات أخرى لم تلمسها هذه المراجعة** (المهام، المرفقات، القوالب، موافقة الإكمال). لم أغيّرها لأن سلوكها لم يتأثر بـPhase 1، لكنها مرشحة لنفس التثبيت لاحقًا.
4. **الاختبارات الثقيلة (>200 صف) بطيئة بطبيعتها.** لا مهلة HTTP عليها الآن، لكن زمنها الكلي يبقى مرتفعًا.
