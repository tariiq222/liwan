## Existing trust, refresh, and response path

- Pages call `useVendorApi().request()` → `/api/vendor/v1/**` (`apps/web/app/composables/useVendorApi.ts:1-11`); catch-all calls `forwardVendorRequest` (`apps/web/server/api/vendor/v1/[...path].ts:1-3`). BFF requires enabled config and GET/POST, validates mutation Origin/JSON, resolves the actor from Odoo `/api/v1/me` using the current session cookie, signs the request, and forwards no browser cookie (`apps/web/server/utils/vendor-control.ts:32-94`).
- UI capability state comes from `/api/vendor/v1/context`; actor changes clear old capabilities and refresh, and failed refresh clears capabilities (`apps/web/app/composables/useVendorContext.ts:37-65,75-86`). A displayed permission can be stale until refresh, but each server request independently checks active membership/capability and nonce (`apps/control-plane/src/http.ts:63-73`); queued worker mutations recheck grant before executing (`apps/control-plane/src/worker.ts:77-79,190-203`). Therefore a stale button is not authorization; it should surface the server denial and refresh context/data.
- Ordinary API path is separate: `apps/web/server/routes/api/v1/[...path].ts:3-9` proxies directly to Odoo. Control-plane outage must not couple ordinary PMO/HR; BFF unit test evidence is documented separately, not a live outage proof.
- The trust chain is **Nuxt UI → same-origin BFF using session-derived Odoo actor → independently authorized control plane membership/capability**; control-plane actor comes from the signed assertion and is checked against active membership on requests (`apps/web/server/utils/vendor-control.ts:44-58,60-94`; `apps/control-plane/src/http.ts:63-78`). Queued mutations recheck `vendor.operations.run` before execution (`apps/control-plane/src/worker.ts:77-79,190-203`). Tenant `operations_enabled` is only a per-target operations gate (`http.ts:210-220,114-120`), never a vendor membership or user grant.
- Durable mutations enqueue receipts/status and operation event history. UI generally navigates to or polls operation detail (`http.ts:222-247`; `operationDetail`/events `:93-97`; `operations/[id].vue:23-53`). **HTTP 202/enqueue, desired policy payload, old `health_checked_at`, or a receipt with `deployment_ready:false` is not successful service completion.** Worker create explicitly routes deployment-not-ready to intervention (`worker.ts:213-231`); policy success needs actual readback (P3 requirement); health timestamp must be treated as historical evidence. Completion requires the package 0–5 adapter/readiness/receipt contracts.

## Cross-action acceptance mapping for Package 6

1. **Real contracts only, with no unnecessary deferral:** render each roadmap-required action as soon as its prerequisite package supplies a real capability-guarded server path and truthful receipt semantics; do not add UI ahead of its contract or keep it hidden after that dependency is ready. Restore waits for P4 recovery, upgrade/rollback for P5, renewal for P3, and reconciliation for its P5 evidence-backed contract. Membership grant/revoke remains the existing out-of-band CLI and is not a new P6 UI scope.
2. **Present truthful intent and impact:** before consequential or destructive actions, show the opaque target and the operation's actual effect/receipt meaning; collect reason where the existing contract requires it and use the product's inline confirmation for destructive actions. Do not introduce an extra approval policy beyond existing contracts. Preserve DESIGN.md rules: pages, `/new` via `SharedCreatePanel`, no stacked business dialogs, Arabic RTL + English LTR, keyboard and direct URL/refresh/back/filter/draft behavior (`DESIGN.md:25-36,187-221`).
3. **Show truthful state:** distinguish registration/tenant health/operation lifecycle/policy and last health timestamp; display queued/running/failed/intervention receipts/events; no fabricated progress, and never treat HTTP 202 or desired payload as completion (`roadmap:50,137-143`).
4. **Least privilege and stale actor handling:** read-only vendor members can inspect but cannot mutate; session-derived actor and independent control-plane membership/capability remain authoritative. On server denial after actor/grant change, refresh vendor context and resource data, clear stale displayed authority, and show an actionable error. Tenant `operations_enabled` only gates that tenant's operations and is not a vendor membership grant. Customer users and role=vendor/PMO/HR admins do not inherit vendor access (`roadmap:44-46`; BFF `vendor-control.ts:44-69`; control `http.ts:63-78`).
5. **Safe errors/uncertain outcomes:** preserve API error code/status, refresh authoritative state after conflict, do not retry uncertain mutations automatically. Use only durable receipts and reconciliation; do not expose private paths, raw logs or secrets (`roadmap:51`; `apps/control-plane/src/worker.ts:99-123`; P2/P5 dependencies).
6. **Destructive boundary:** no automatic customer data deletion, module removal, unverified restore/overwrite, or repeated mutation. Restore requires proven backup and explicit approval; upgrade/rollback require tested version/backout evidence; administrative expiry never silently becomes suspension (`roadmap:23-27,116-131`).
7. **UI acceptance:** after runtime prerequisites, verify Arabic RTL, English LTR, direct route/refresh/back, list filters, permission denial, empty/loading/error states and 390/768/1440 widths as package 6 specifies; acceptance needs real authorized end-to-end scenarios, not button snapshots (`roadmap:137-143`; `docs/superpowers/specs/2026-09-23-company-vendor-workspace-design.md:72-79`).
