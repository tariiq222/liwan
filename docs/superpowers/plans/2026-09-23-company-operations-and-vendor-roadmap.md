# خطة إكمال تشغيل وإدارة SaaS في نسق

> **سياق تاريخي لنشر العميل المستقل:** سطر «لكل عميل قاعدة وخدمات وملفات مستقلة» أدناه يصف نطاق هذه الخطة وقت كتابتها، لا نموذج SaaS الأساسي بعد اعتماد الخدمات المشتركة. قبل تنفيذ أي بند راجع [عقد SaaS المشترك والحكومة الحالي](../specs/nasq-shared-saas-and-sovereign-deployment.md). لا تُعاد تسمية `compose-local` مشتركًا ولا يُعد قبول هذه الخطة قبولًا للتسجيل والدفع والعزل المشترك.

> **للتنفيذ:** تطبيق `superpowers:executing-plans` أو `superpowers:subagent-driven-development` لكل حزمة بحسب استقلالها، مع قراءة تعليمات المشروع والمواصفة قبل التعديل. هذه خطة عمل وقبول، وليست إثبات جاهزية أو تفويض نشر.

**الهدف:** إدارة دورة حياة نسخة SaaS فعلية من داخل نسق: تسجيلها، تشغيلها، ضبط وحداتها وسياساتها، متابعة صحتها، نسخها واستعادتها وتحديثها، مع صلاحيات وتدقيق وعزل مثبت.

**معمارية شريحة النشر المستقل التاريخية `compose-local`:** نسق منتج واحد يستخدم Odoo لمحرك الأعمال وNuxt للواجهة. قسم إدارة المنصة في بيئة إدارة نسق فقط، وخلفه خدمة PostgreSQL وعامل تشغيل مستقلان. لهذا المسار لكل عميل قاعدة وخدمات وملفات مستقلة؛ **أما SaaS الأساسي المستهدف فخدمات التطبيق مشتركة وقاعدة/ملفات منفصلة**. لا اعتماد لحظي على خدمة الإدارة لتنفيذ أعمال العميل غير SaaS.

**المرجع:** [التصميم المعتمد](../specs/2026-09-23-company-vendor-workspace-design.md) و[دليل الدمج السابق](../../verification/2026-09-23-vendor-local-integration.md). توجيه المستخدم الحالي يجعل الخطة لنسق فقط، دون ربطها باسم شركة، مع تصميم يسمح بإضافة وحدات Odoo لاحقًا.

**خط الأساس المتحقق:** `main` عند `abde67b6` بتاريخ 2026-09-23. الخطة السابقة غير ملتزمة؛ هذه الوثيقة تستبدل نطاقها. قبل التنفيذ تُراجع الحالة الحية مجددًا.

## 1. نطاق التسليم

### داخل النطاق

- نشر قابل للتكرار لبيئة إدارة نسق وخدمتها وعاملها، ولنسخ العملاء على نموذج استضافة مُدار واحد.
- استخدام صفحات الإدارة الحالية: الملخص، النسخ، الكتالوج، العمليات، التدقيق؛ استكمال الإجراءات الناقصة فقط.
- إدارة وحدات وحدود وصلاحية SaaS عبر سياسة واضحة وإصدار سياسة، دون ربط مالي الآن.
- إنشاء نسخة كاملة، صحة موثقة، تحديث، نسخة احتياطية متسقة، استعادة، ومصالحة العمليات مجهولة النتيجة.
- دليل تشغيل واختبارات أعطال وعزل وقبول متصفح.

### خارج التنفيذ الحالي

CRM والمبيعات والفواتير والمدفوعات وبوابة العميل ونظام التذاكر، والتخصيصات القطاعية، وإعادة بناء الوحدات الحالية، والحذف الآلي لبيانات العملاء. تصنيف non_saas وحماياته محفوظان؛ لا تحويل تلقائي ولا انتهاء بسبب دعم أو فوترة.

التكامل المستقبلي يُراعى بتحديد مصدر الحقيقة ومعرّفات الربط، دون تركيب وحدات مؤجلة أو إنشاء واجهات وجداول وهمية لها.

## 2. فجوات المصدر التي يجب إغلاقها

| الفجوة المثبتة | موضعها | المطلوب |
| --- | --- | --- |
| السماح بـ scratch فقط | `tools/nasq_cli/operator.py` و`apps/control-plane/src/worker.ts` | محوّل تشغيل مُدار منفصل ومختبر؛ لا حذف الحارس العام لتشغيل العملاء |
| إنشاء قاعدة دون خدمة عميل مكتملة | نتيجة create الحالية وworker | دليل خدمة ونطاق ودخول ووظائف؛ active بعد اكتمال الدليل فقط |
| backup يحمل UNVERIFIED | operator وأدوات deploy | التقاط متسق وتحقق مستقل من الاستعادة |
| ترقية وحدات لا تثبت صحة التطبيق | مسار upgrade | إصدار مثبت، فحص وظيفي، وتجربة رجوع متوافقة |
| عمليات عالقة تتطلب تدخلًا | الطابور والسجل الدائم | مصالحة مدققة مبنية على الواقع دون إعادة عمياء |
| تشغيل دائم وقبول واجهة غير مكتملين | إعدادات التشغيل وصفحات vendor | تجهيز دائم قابل للتكرار وRTL/LTR واختبار الصلاحيات والأعطال |

الكود المدمج يتضمن بالفعل سجل العمليات والأقفال وتوقيع الطلبات والمنح والكتالوج؛ تُمدد هذه الأسس ولا تُبنى نسخ موازية لها. المعاينة المؤقتة أوقفت ونسخ العمل السابقة حذفت؛ لا تعتمد الخطة عليها.

## 3. ثوابت التصميم والعقود

1. أعلام لوحة البائع false افتراضيًا؛ تُفعّل في بيئة إدارة نسق فقط. مفاتيح الخدمة لدى الخادم فقط، ولا تُنسخ إلى العملاء.
2. صلاحيات الإدارة منفصلة عن PMO/HR و`role=vendor`؛ كل API وعملية تتحقق من الهوية والمنحة والهدف.
3. قاعدة العميل مصدر بيانات أعماله؛ قاعدة الإدارة مصدر سجل نسخه وعملياته. واجهة الإدارة لا تسحب أعمال العملاء إلى قاعدة مركزية.
4. هوية العميل التجاري مختلفة عن معرّف النسخة؛ عميل واحد يمكنه امتلاك عدة نسخ. رقم مستخدم Odoo ليس معرّف عميل تجاري.
5. الربط المستقبلي بـ Odoo يكون بمعرّف ثابت مع معرّف بيئة المصدر ونوع السجل؛ لا مطابقة بالبريد ولا نسخة مكررة من دفتر الفواتير. يُوثق العقد الآن ويُنفذ عند إضافة الموصل.
6. الكتالوج التقني يحدد الوحدات والحدود، ولا يُعامل كفاتورة أو اشتراك مدفوع. مرجع المنتج التجاري سيُربط بإصدار كتالوج لاحقًا.
7. حالة التشغيل منفصلة عن السياسة التجارية وعن نتائج العمليات. لا يعني نجاح تسجيل النسخة أنها شغالة، ولا تعني نتيجة دفع مستقبلية أن النشر نجح.
8. لكل mutation: معرّف طلب، بصمة محتوى وهدف، قفل، مراحل وإيصال دائم. النتيجة غير المؤكدة تحتاج مصالحة قبل أي mutation جديدة.
9. Odoo الأصلي دون تعديل؛ امتدادات نسق فوق وحداته. لا اختبارات على `odoo19` ولا قواعد العملاء.
10. الواجهة حسب DESIGN.md وStorybook؛ المحافظة على المسارات والفلاتر والمسودات وصلاحيات الوحدات الحالية.

## 4. حزم التنفيذ وبوابات قبولها

### الحزمة 0 — تثبيت قرار التشغيل وعقود التسليم

**الاعتماد:** لا شيء. **الملفات:** دليل جديد `docs/operations/saas-runtime.md` ومواصفة `docs/superpowers/specs/2026-09-23-saas-runtime-contracts.md`.

- [ ] جرد إعدادات deploy والموارد المتاحة فعليًا، وتحديد بيئة إدارة وبيئة عميلين تجريبيين بأسماء وقواعد ومنافذ منفصلة.
- [ ] اعتماد محوّل استضافة أول واحد. نقطة البداية المقترحة هي أدوات Docker/Compose الحالية إذا كانت بيئة التشغيل تدعمها؛ لا يُفرض مزود أو خادم غير متحقق منه.
- [ ] تثبيت عقد الهدف: معرّف opaque، نوع المحوّل، نطاق البيئة، مرجع الأسرار، مرجع الإصدار، وموارد مسموح بها. المتصفح لا يرسل SQL أو أوامر أو مسارات.
- [ ] تثبيت دليل الجاهزية: فحص القاعدة والوحدات والسياسة والخدمات والنطاق وTLS حيث يلزم والدخول والمرفقات؛ يحوي الدليل الهدف والإصدار والتوقيت والنتيجة دون أسرار.
- [ ] تحديد أهداف فقد البيانات وزمن الاستعادة والاحتفاظ ونافذة الصيانة المطلوبة قبل الالتزام بها؛ تدوين المقاس فعليًا مقابل الهدف.

**القبول:** عقد واحد متفق عليه بين العامل والمحوّل والواجهة، وبيئة تجربة محددة. إذا لم يُعرف خادم التسليم، تستمر الاختبارات المحلية ولا يُدّعى النشر.

### الحزمة 1 — تشغيل إدارة نسق وصلاحياتها

**الاعتماد:** 0. **الملفات:** `apps/control-plane/src/config.ts`، `admin.ts`، إعدادات Nuxt وBFF واختباراتها؛ ملفات نشر جديدة تحت `deploy/control-plane/`.

- [ ] إعداد تشغيل دائم للخدمة وقاعدتها وعاملها، مع فحوص بدء وتشغيل ومهاجرات قابلة للتتبع وتدوير الأسرار.
- [ ] ربط جلسة نسق والمنح الحالية بالهوية الموثوقة؛ لا حسابات تطبيق موازية ولا صلاحيات من البريد.
- [ ] ضبط القراءة وإدارة النسخ والكتالوج والتنفيذ والتدقيق بالمنح الحالية؛ إبقاء التوسع في المنح مرتبطًا بحاجات إجراءات فعلية.
- [ ] اختبار default-off، والوصول المباشر، والأصل غير المسموح، وتزوير الهوية، وإعادة الطلب الموقع، وسحب المنحة وتبديل المستخدم.
- [ ] توثيق bootstrap واستعادة وصول المشغل خارج الواجهة، دون تجاوز التدقيق أو تسجيل المفاتيح.

**القبول:** إدارة تعمل للمخول فقط، وعميل أو مستخدم عادي يُرفض من الخادم؛ المشاريع والموظفون يعملون مع تعطل خدمة الإدارة.

### الحزمة 2 — إنشاء نسخة SaaS قابلة للاستخدام

**الاعتماد:** 0 و1. **الملفات:** محوّل جديد `tools/nasq_cli/managed_runtime.py` واختباره `tools/test_managed_runtime.py`؛ `operator.py` و`journal.py` و`worker.ts`؛ ملفات deploy الحالية بحسب المحوّل.

- [ ] إنشاء اختبارات التعارض: قاعدة موجودة، هدف غير مسموح، مورد مشترك، إصدار غير موثوق، صلاحيات غير كافية؛ جميعها تفشل قبل أثر غير مقصود.
- [ ] تنفيذ preflight ثم الحجز ثم القاعدة والملفات ثم تركيب الوحدات والسياسة ثم الخدمات والنطاق والتحقق، مع نقاط تقدم وإيصالات.
- [ ] توفير إعداد مسؤول العميل وتسليم الوصول بطريقة لا تعرض كلمة المرور في سجل العملية أو المتصفح الإداري.
- [ ] تنفيذ طلب create مرة واحدة؛ إعادة الطلب تعيد الإيصال، وتغيير محتواه بنفس المعرّف يرفض.
- [ ] تعطل منتصف النشر يحفظ الموارد ومرحلة التعثر؛ لا تنظيف تدميري تلقائي ولا active كاذبة.
- [ ] رفع السماح فقط للأهداف المصرح بها عبر المحوّل المعتمد؛ الحفاظ على منع الأهداف غير المعروفة وnon_saas غير المفوضة.

**القبول:** عميلان تجريبيان يستطيعان الدخول وإنشاء سجل عمل ورفع مرفق وقراءته دون تداخل. `deployment_ready:true` ينتج فقط عن تحقق كامل، لا تغيير ثابت في JSON.

### الحزمة 3 — إدارة سياسات SaaS والصحة

**الاعتماد:** 2. **الملفات:** `http.ts` و`worker.ts` والعقود التجارية وصفحة تفاصيل النسخة وأدوات inspect/health.

- [ ] إدارة الوحدات والحدود ومدة الصلاحية والتجديد الإداري المصرح به عبر السياسة الموجودة، دون فوترة أو تحصيل.
- [ ] توثيق سياسة الانتهاء والتقييد الحالية واختبارها؛ لا اختراع إيقاف جديد أو تغييرها ضمنيًا. أي سلوك تجاري جديد يحتاج قرارًا محددًا.
- [ ] التفريق بين إتاحة الوحدة في السياسة وتركيبها فعليًا؛ لا تفعيل وحدة غير مركبة وكأنها جاهزة، ولا إزالة بيانات عند سحب الإتاحة.
- [ ] القراءة الفعلية للسياسة ورقمها وتوقيت صحتها؛ السياسة المطلوبة لا تصبح observed قبل إثبات تنفيذها.
- [ ] رفض تعارض الإصدار تحت القفل؛ القراءة القديمة تُعرض قديمة. تعرض الصحة عناصر الخدمة وآخر فحص، دون خلطها بتاريخ انتهاء الاشتراك.
- [ ] عند انقطاع الإدارة تظل السياسة المحلية المعتمدة هي المرجع؛ لا تمديد أو إنهاء تلقائي سببه الانقطاع وحده.

**القبول:** تغيير فعلي للحد يظهر داخل العميل، وطلب قديم يرفض دون تعديل؛ التجديد الإداري مدقق، وتعطل الإدارة لا يكسر أعمال العملاء.

### الحزمة 4 — النسخ الاحتياطي والاستعادة الموثوقة

**الاعتماد:** 2. **الملفات:** أدوات backup/restore في `deploy/`، محوّل التشغيل، operator، وعقود الإيصالات واختباراتها.

- [ ] تحديد وتنفيذ نقطة اتساق للقاعدة والملفات؛ إيقاف الكتابات مؤقتًا عند الحاجة وفق نافذة واضحة.
- [ ] تسجيل manifest بالإصدار وتكوين الوحدات وبصمات الملفات، وتشفير النسخة وتخزينها خارج نطاق فشل بيئة العميل بمفاتيح مستقلة مناسبة.
- [ ] التمييز بين captured وverified: التقاط سليم شكليًا لا يكفي. إبقاء UNVERIFIED للنسخ القديمة وغير المثبتة.
- [ ] استعادة إلى بيئة جديدة، والتحقق من الدخول والسجلات والمرفقات وعلاقاتها وسياسة النسخة، مع توقيت النتائج.
- [ ] التحويل إلى البيئة المستعادة إجراء مستقل مع موافقة محددة ونافذة ورجوع؛ لا استبدال قاعدة قائمة ضمن اختبار الاستعادة.
- [ ] اختبار ملف مفقود وبصمة خاطئة ونسخة ناقصة ومفتاح غير متاح؛ رفض آمن دون ادعاء نجاح.

**القبول:** استعادة عملية من نسخة متسقة مع قياس فقد البيانات والزمن، وإظهار فجوة الأهداف إن وجدت. لا مساس ببيانات عميل فعلي.

### الحزمة 5 — التحديث والرجوع ومصالحة العمليات

**الاعتماد:** 2 و4. **الملفات:** محوّل التشغيل وoperator وjournal وworker، وإضافة مسار مصالحة وعقده واختباراته عند الحاجة؛ مهاجرة جديدة لأي تغيير مخطط.

- [ ] اختبار إصدار جديد على نسخة معزولة من بيانات التجربة، ثم تشغيل مهاجرات ووحدات وفحوص وظيفية.
- [ ] حفظ إصدار وبيانات متوافقين للرجوع؛ رجوع التطبيق وحده لا يعكس مهاجرة بيانات غير قابلة للعكس.
- [ ] حقن سقوط العامل بعد تنفيذ أثر وقبل تسجيل النتيجة؛ تحويل العملية إلى تدخل ومنع بدء تعديل آخر على الهدف.
- [ ] تنفيذ مصالحة تقارن هوية الموارد والإيصال والحالة الفعلية؛ إما اعتماد النتيجة المثبتة أو استمرار الحجر. لا زر يمسح حالة الخطأ دون دليل.
- [ ] اختبار عاملين وقفل هدف واحد وانتهاء lease ووصول إكمال متأخر؛ لا كتابة من عامل فقد ملكية العملية.
- [ ] إعادة فحص التفويض قبل الخطوة الحساسة؛ سحب منحة لا يقتل عملية مدمرة في منتصفها دون مسار آمن، ويُوثق ما بدأ قبل السحب.

**القبول:** تحديث ورجوع وظيفيان، ونتيجة متعثرة يمكن حسمها بدليل دون تكرار الأثر أو إخفاء الفشل.

**الاعتماد:** العقود من 0؛ الإجراءات تتطلب 2–5. **الملفات:** `apps/web/app/pages/vendor/**` وملفات اللغة واختبارات التنقل وBFF.

- [ ] عرض preflight والأثر والهدف قبل العمليات الحساسة، وتأكيدها بالطريقة الداخلية المعتمدة؛ المسارات صفحات، دون حوارات أعمال متراكبة.

**الاعتماد:** جميع الحزم السابقة. **الملفات:** اختبارات قبول تحت `deploy/` وواجهة نسق، ودليل تشغيل وتقرير نتائج جديد تحت `docs/verification/`.

- [ ] تشغيل سيناريو كامل من كتالوج منشور إلى عميلين عاملين، ثم تعديل سياسة وتجديد إداري ونسخ واستعادة وتحديث ورجوع.
- [ ] إثبات عزل القواعد والملفات والأسرار والهوية؛ لا تكفي اختلافات أسماء الموارد.
- [ ] إيقاف خدمة الإدارة وقاعدتها وعاملها واختبار عمل العميلين والواجهة العادية لنسق. الأعطال المشتركة للخادم لها اختبار منفصل.
- [ ] فحص استعادة خدمة الإدارة وسجلها أيضًا، وحفظ توافق سجل العمليات مع إيصالات العامل لمنع إعادة تنفيذ آثار قديمة بعد التعافي.
- [ ] مراجعة السجلات والاستثناءات والصلاحيات، وتوثيق إجراءات بدء التشغيل والتوقف والتدوير والاستعادة والمصالحة.
- [ ] إصدار تقرير بكل بوابة: pass/fail/skip، البيئة والإصدار والدليل والمحدوديات. اختبار متخطى لا يحسب قبولًا.

**القبول المحلي:** الحزم تعمل على موارد معزولة ودليلها قابل للمراجعة. **القبول التشغيلي:** إعادة التحقق على الاستضافة المستهدفة بعد تحديدها والتفويض بالنشر. لا يخلط التقرير بين الاثنين.

## 5. ترتيب التنفيذ والملكية

`0 → 1 → 2 → (3 و4) → 5 → 6 → 7`

يمكن العمل على عرض الواجهة بعد تثبيت العقود، لكن لا يعتمد قبل المحوّل. السياسات والنسخ مستقلتان وظيفيًا بعد الإنشاء، لكن operator/worker ملفات مشتركة؛ تفصل الوحدات والملكية قبل تفويض متوازٍ. المنسق وحده يملك الدمج والعقود والمهاجرات وإعدادات التشغيل المشتركة والتحقق النهائي.

لكل حزمة: اختبار فشل محدد → تنفيذ أدنى → اختبار مركز → مراجعة الفروق → تحقق مجمع مناسب → تقرير قبول. لا إعادة اختبارات ناجحة دون تغيير أو سبب، ولا حذف حراس أو اختبارات لإعلان الإنجاز.

## 7. التحقق والموارد

الأوامر الأساسية بحسب نطاق التغيير: `npm test` و`npm run lint` و`npm run build` و`npm run test:commercial` وبناء العقود التجارية وخدمة الإدارة. اختبارات PostgreSQL تستخدم قاعدة جديدة `nasq_control_scratch_<suffix>` مع `CONTROL_TEST_DATABASE_URL` صريح؛ غيابها وتخطي الاختبارات ليس نجاحًا. اختبارات Odoo على قواعد scratch صريحة مع addons المسار المختبر. تشغيل أدوات deploy والمتصفح يضاف وفق الحزمة.

قبل النشر يُحدد: الخادم المستهدف، النطاقات، إدارة DNS/TLS، مخزن الأسرار، تخزين النسخ، هوية المشغلين، وأهداف التعافي. يمكن تنفيذ المصدر والقبول المحلي قبل ذلك، ولا يجوز اختيار موارد حقيقية عشوائيًا أو الادعاء بأن الاختبار المحلي يثبت جاهزية الاستضافة.

لا حذف قواعد أو فروع أو نشر أو push ضمن تنفيذ غير مأذون؛ دمج كل حزمة ونشرها يخضعان لتفويضهما. لا يتطلب التخطيط الحالي إنشاء worktree أو تشغيل خدمات.
