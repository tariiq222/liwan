## نموذج التطبيق

ثلاث موارد يملكها `webvue_operations`:

1. **الإجراء**: الاسم والوصف، الشركة، حالة مسودة/منشور/مؤرشف، النسخة، نوع التنفيذ المسموح، ومراحل موافقة مرتبة. المرحلة تختار مراجعين من مستخدمي الشركة، وسياسة موافقة واضحة: فرد، أو أي واحد من مجموعة محددة. نشر إجراء يحتاج مراجعًا واحدًا على الأقل في كل مرحلة.
2. **الطلب**: رقم، مقدم الطلب، الشركة، إجراء ونسخته، عنوان وتفاصيل، حالته، رقم دورة الموافقة، ورقم نسخة للتزامن. يحمل snapshot ثابتًا للمراحل والمراجعين ونوع التنفيذ عند الإرسال، فلا يغيّر تعديل الإجراء طلبًا جارياً.
3. **أحداث الطلب والتنفيذ**: أحداث محفوظة للإرسال والقرارات والإرجاع والسحب وإعادة الإرسال والتنفيذ، مع الفاعل والوقت والتعليق. يحفظ حدث الإرسال والقرار لقطة داخلية لنسخة الإجراء والمراحل وحالاتها. يحمي قفل الطلب ونسخته وحالة الاكتمال وعدّاد التنفيذ أثرًا واحدًا في الدورة؛ أي إعادة إرسال تبدأ دورة جديدة، بينما تكرار القرار في الدورة نفسها لا يعيد الأثر.

المرفقات تتبع عقد تنزيل المرفقات والتحقق من ملكية المستند في ويب فيو. لا تُعاد ملفات/معرفات مراجعات أو مرفقات لا يملك المستخدم رؤية طلبها. النشر والتعديل في الإجراء لا يسمحان باختيار model تعسفي أو Python أو SQL أو server action من المستخدم.

## دورة الطلب والتنفيذ

`مسودة → قيد الموافقة → مكتمل` للطلب العام الذي يسجل الاعتماد، أو `مسودة → قيد الموافقة → منفذ` عند وجود إجراء عمل مسموح. توجد حالات `معاد` و`مرفوض` و`مسحوب`، مع سبب إلزامي للإرجاع والرفض. الإرجاع يتيح تعديل الطلب وإعادة إرساله بدورة جديدة؛ السحب للمقدم قبل اكتمال القرار.

الخادم يقرر الأفعال المتاحة ويعيدها ضمن detail serializer. الواجهة لا تستنتج إمكانية الاعتماد من اسم الدور أو الحالة وحدهما. كل قرار يحمل نسخة الطلب والدورة؛ القرار القديم يفشل بـ HTTP 409 مع طلب تحديث السجل.

لا توجد مرحلة تلقائية بلا مراجعين ولا تجاوز لترتيب المراحل. تغيير المراجع أو تعطيل حسابه قبل القرار يُعاد تقييمه؛ لا يوافق موظف بمجرد أنه كان مراجعًا عند عرض الصفحة.

الموافقة الأخيرة والتنفيذ داخل savepoint واحد، مع قفل المستند وسجل منع التكرار. فشل التنفيذ يعيد القرار الأخير والأثر الجزئي وسجل التنفيذ في قاعدة البيانات، ويعود الطلب قابلًا لإعادة المحاولة بعد تصحيح السبب. بعد rollback يُسجل حدث فشل في المعاملة المحيطة دون اعتماد ناجح أو أثر عمل جزئي. الطلبات المتزامنة تتبع سياسة busy/retry المحدودة؛ لا استمرار تلقائي بلا حد.

الضمان يشمل آثار قاعدة البيانات فقط. لا بريد أو دفع أو webhook بوصفه إجراء تنفيذ في هذه النسخة؛ إدخال تكامل خارجي يحتاج outbox/idempotency مستقلين.

الموظف يحصل على القراءة وإنشاء طلبه؛ المراجع يحتاج قدرة المراجعة مع تعيينه في المرحلة. مدير العمليات يستطيع إعداد الإجراءات ومتابعتها، ولا يُمنح تلقائيًا حق اعتماد طلب ليس مراجعًا فيه أو قدرات كتابة HR/PMO. `system_admin` و`vendor_support` لا يحصلان تلقائيًا على قدرات العمل.

ACL وقواعد السجلات تُطبّق أيضًا على ORM/RPC، وليس في API وحده. صلاحيات `tier.definition` الإضافية لمدير العمليات تُقصر على تعريفات نموذج طلب العمليات وشركته؛ لا تمنحه إدارة تعريفات محركات أخرى أو صلاحيات إدارة أودو العامة. كل public transition موروث على نموذج الطلب يعاد تغليفه بالقدرة والميزة والحالة لمنع استدعاء المحرك مباشرة كمسار تجاوز.

تظل الحقول المحمية وحالة التنفيذ والدورة والأحداث غير قابلة للتعديل بجسم API أو context JSON أو RPC عادي. لا تضيف طبقة ويب فيو `sudo()` جديدًا؛ يعمل المحرك المكيّف ضمن فحوص ويب فيو المعتادة دون إعفاءات.

## الربط بالتطبيقات

العمليات مستقلة وتعمل دون HR أو PMO أو الاجتماعات. الروابط تُعرّف من hooks لا تعرف أسماء تطبيقات أخرى؛ bridges تضيف الهدف والتنفيذ وتتحقق من visibility والشركة والميزة والقدرة الحالية.

الربط الأول في هذه الدفعة: `webvue_operations_pmo` لإجراء اعتماد إكمال مهمة، عبر `_webvue_accept_completion(revision)` الأصلي. يحمل الطلب معرف المهمة ونسخة طلب إكمالها؛ المراجع النهائي يجب أن يطابق المراجع المحدد في PMO، وينفذ في هويته الفعلية. لا نقل لصلاحيات مدير PMO إلى مدير العمليات.

قبل القرار الأخير يعاد فحص نسخة PMO والحالة والمراجع. إذا اعتُمد الطلب من مسار PMO الأصلي، أو سُحب أو تغيرت نسخته، يصبح طلب العملية القديم غير صالح؛ لا يُعاد إغلاق المهمة أو اختراع اعتماد آخر. يبقى PMO صاحب قرار تغيير حالة المهمة، والمحرك ينسّق المراحل السابقة ويستدعيه مرة واحدة.

ربط تعديل بيانات موظف أو اعتماد محضر اجتماع يحتاج نطاقًا واختبارات منفصلة بعد نجاح الربط الأول؛ لا تُعرض في هذه الدفعة خيارات تنفيذ لم تنفذ فعليًا. هذا تأجيل تكامل محدد، وليس استبعادًا من رؤية المنصة.

## API والعقود

المسارات تحت `/api/v1/operations`، `type='json2'` و`auth='user'` و`api_handler` وميزة التطبيق في كل route. جلسة المستخدم الحالية والشركة الحالية إلزاميتان. تُستخدم serializers بقوائم مفاتيح محددة وZod strict في `packages/contracts/src/operations`؛ القوائم `{items, total}` وكل كتابة تعيد detail كاملًا.

السطح: قوائم الطلبات حسب النطاق، إنشاء/قراءة/تعديل، إرسال/سحب/اعتماد/رفض/إرجاع، مرفقات وأحداث؛ وقوائم الإجراءات وإنشاء/تعديل/نشر/أرشفة. نطاق `pending` يُحسب بالخادم ولا تقبل قائمة مراجع يختارها العميل. لا API عام إلى `ir.actions.server` أو `tier.review.write`.

الأخطاء: 403 لغياب القدرة، 404 لسجل غير موجود أو غير مرئي، 422 لحقول غير صالحة، و409 لنسخة أو حالة قديمة أو تعارض قرار. الميزة المغلقة أو المستأجر غير القابل للكتابة يتبعان عقد `requires_feature` الحالي. كل حالات الخطأ تُختبر في طبقة HTTP أيضًا.

## ملكية الحزم وترتيبها

| الحزمة | الملفات والمسؤولية | الاعتماد السابق |
|---|---|---|
| استيراد المحرك | المحرك الأساسي، الترخيص، الجرد وفحوص التكييف | عقد الوصول والفحوص دون إعفاء |
| تطبيق العمليات | `odoo-addons/webvue_operations/**`، العقود، الصلاحيات والدورة وسجل التنفيذ | المحرك وعقود الموارد |
| الواجهة | `apps/web/app/{pages,components,composables,modules}/operations/**` والترجمات والقصص | العقود والقرارات المتاحة من API |
| الربط والقبول | `webvue_operations_pmo/**`، تسجيل الكتالوج والتثبيت، الاختبارات المتكاملة | التطبيق ثم التكامل الأول |

القراءة الحالية inline لأن تحديد المصدر وعقد التكييف سابقان لكل حزمة. لا يُرسل عمل كتابة قبل تثبيت التكييف والعقود. أثناء التنفيذ يمكن فصل الواجهة بعد تثبيت العقود، لكن منسق واحد يملك الملفات المشتركة والمعمارية والكتالوج وbarrel العقود و`DESIGN.md` وقوائم تثبيت الإصدار. أي تفويض يستخدم GPT-6.1 Sol فقط وملكية ملفات واضحة.

التنفيذ في worktree مؤقت من `main` الحالي، مع dependencies و`.nuxt` ومنافذ وقاعدة scratch منفصلة. تُفحص حالة main من جديد قبل البدء؛ تغييرات الدراسة المالية الحالية تحفظ كما هي. لا اختبارات على `odoo19`، ولا تشغيل أو ترقية أو تعديل حزمة إرادة الأصلية.

## معايير القبول والأدلة المطلوبة

- المصدر الأصلي محفوظ بالجرد؛ diff تكييف المحرك موثق، والترخيص ونسب التأليف محفوظة. اختبار manifest/dependency closure وقوائم التثبيت وصورة Odoo يثبت وجود المحرك في إصدار المرشح.
- إعادة اختبار المحرك الأصلي والمعدل: منع CRUD الموافقات والتزوير عبر context/الحقول، منع تجاوز الترتيب، منع callback مباشر، وضبط الوصول إلى المستند الأصلي والشركة.
- تثبيت التطبيق الجديد والموديولين مع اختباراتهما على قاعدة scratch جديدة، N أكبر من صفر، بلا failures/errors. إعادة تطبيق التحديث على القاعدة نفسها وتحقيق عدم فقد السجلات وتكرار التنفيذ. ترقية إنتاج قديم ليست مثبتة بذلك.
- طلب عام: إنشاء مسودة، إرسال، مرحلتان لمراجعين مختلفين، عدم التنفيذ بعد المرحلة الأولى، تنفيذ واحد بعد الثانية، حفظ سجل التاريخ، وتكرار قرار لا يكرر الأثر.
- رفض وإرجاع وسحب وإعادة إرسال، مع أسباب إلزامية ودورة جديدة وحفظ الدورة السابقة. تعديل تعريف الإجراء لا يبدل snapshot طلب جارٍ.
- فشل تنفيذ مصطنع بعد أثر جزئي: rollback القرار الأخير والأثر والمؤشر؛ تصحيح السبب ثم نجاح محاولة واحدة. طلبان HTTP متزامنان من جلستين مستقلتين يثبتان أن الأثر مرة واحدة.
- حالات أدوار الموظف والمراجع ومدير العمليات والمسؤول التقني، شركة ثانية، مستخدم معطل، قدرة مسحوبة، ميزة مغلقة ومستأجر قراءة فقط. الاختبارات تشمل ORM/RPC وHTTP ولا تعتمد على إخفاء الأزرار.
- جسر PMO: مراجع صحيح يوافق مرة واحدة عبر الدالة الأصلية؛ مراجع عمليات غير مخول في PMO يُرفض؛ طلب قديم وتغيير المراجع وقرار سبق في PMO تمنع الأثر المكرر.
- عقود serializer/Zod ومفتاح الشركة وenvelope القوائم والأخطاء HTTP متطابقة؛ فحوص الوحدة الموجهة ثم `npm test` وtype check من `apps/web`.
- قبول متصفح عربي/إنجليزي، المظاهر الثلاثة، 390/768/1440px، لوحة المفاتيح، الروابط المباشرة والتحديث والرجوع والفلاتر والمسودة، وحسابا مقدم ومراجع مستقلان. fixtures عبر Odoo.
- فحوص `ruff` والسياسات والكتالوج والـ git والـ arch مقابل `main` تمر دون نمو baseline أو أي توسيع للاستثناءات. مراجعة diff فعلية للمحرك والتطبيق والجسر، لا قبول بتقرير عامل وحده.

تُحفظ الأوامر والسجلات والبصمات ونتائج المتصفح في تقرير قبول محلي بتاريخ التنفيذ. لا تنسب نجاحًا جديدًا إلى اختبارات الجلسة السابقة، ولا يعني أي قبول محلي merge أو push أو deployment أو اعتمادًا تجاريًا.

نُفّذت المواصفة في فرع منفصل: المحرك الأساسي المكيّف، تطبيق العمليات وواجهته، وجسر اعتماد إنجاز مهمة. بقي الموديول التنفيذي المرتفع الصلاحية خارج التثبيت، ولم تتوسع الاستثناءات أو baseline. نجحت الفحوص المحلية والمراجعة المستقلة؛ سجل القبول حُذف وبقي في تاريخ Git.
