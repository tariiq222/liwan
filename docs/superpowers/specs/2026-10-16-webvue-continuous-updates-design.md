## 1. النتيجة المطلوبة وحدودها

تحديثات الواجهة والكود المتوافقة تستهدف استمرار القراءة والحفظ والجلسات أثناء التحويل. تحديثات قاعدة Odoo التي لم يثبت إمكان تشغيلها أثناء الاستخدام تدخل صيانة لعميل واحد، وتبقى قواعد العملاء الآخرين تعمل. لا نسمي إيقاف الحفظ أو تعليق الطلبات حتى تنتهي الترقية «بدون توقف».

لا يمكن ضمان كل تغيير مستقبلي في Odoo بلا أي انقطاع، خصوصًا الترحيلات الكاسرة وترقية الإصدار الرئيسي. إن كان المطلوب منع أي توقف حتى في هذه الحالات، فالقرار الآمن هو تأجيل ذلك التغيير إلى أن يوجد مسار مُثبت لاستمرار الكتابة؛ لا نفقد بيانات أو نعيد تشغيل نسخة قديمة على مخطط غير متوافق لإخفاء التوقف.

هذه الخطة لتوقفات التحديث المخطط لها. تحمل سقوط المضيف أو PostgreSQL أو التخزين أو الحافة مشروع توافر عالٍ منفصل. مجموعتا تطبيق على مضيف واحد لا تحققان ذلك.

## 3. متى تتوقف الخدمة؟

الحكم التالي هو **السياسة المقترحة بعد تنفيذ الخطة والتحقق منها**. الإعداد الحالي لا يضمن التحديث بلا توقف حتى للتغييرات البسيطة.

| نوع التغيير | التصنيف الافتراضي | أثره بعد تنفيذ الخطة |
|---|---|---|
| CSS أو ترجمة Nuxt أو مكوّن واجهة، دون كسر API | `online` | يستمر العمل؛ تخدم الأصول القديمة الصفحات المفتوحة حتى انتهاء فترة تصريفها. |
| كود Python فقط، بنفس المخطط والبيانات وعقد الطلبات، دون `-u` أو `-i` | `online` بشرط إثبات التوافق الدلالي | تحويل من المجموعة القديمة للجديدة مع بقاء الطلبات القائمة؛ لا تثبيت ملفات فوق حاوية تعمل. |
| تعديل serializer أو قواعد العمل بنفس الحقول | مراجعة إلزامية، وليس online تلقائيًا | online فقط إذا ظلت طلبات الواجهة المفتوحة والعمليات المتزامنة صالحة؛ وإلا صيانة العميل. |
| استحقاق/إعداد عبر API القائمة | عملية تشغيل عادية | لا نشر؛ تطبيق السياسة الحالية قد يمنع عملية أو ميزة مقصودة، ولا يقدم كطريقة لإخفاء توقف نشر. |
| ترجمة Odoo أو XML أو ACL أو record rule تحتاج تحميلًا عبر `-u` | `tenant_maintenance` | صيانة قاعدة العميل كاملة؛ عدم وجود حقل جديد لا يجعلها online. |
| حقل جديد، حتى اختياري أو غير مخزن، أو موديل/قيد/فهرس يتطلب ترقية موديول | `tenant_maintenance` | لا يُفترض أنه آمن تحت الطلبات؛ يقاس وقت الترقية والأقفال على نسخة معزولة. |
| إعادة تسمية/حذف/تغيير نوع/required/حساب مخزن أو تحويل بيانات | `tenant_maintenance` | توقف العميل المتأثر أثناء تصريف الكتابة والنسخ والترقية والفحص؛ الآخرون يستمرون. |
| تثبيت تطبيق أو جسر أو تغيير dependencies | `tenant_maintenance` | يشمل إغلاق التبعيات والوحدات التابعة، لا الموديول المطلوب وحده. |
| كسر عقد API أو تنسيق جلسة أو بروتوكول WS/AI | `tenant_maintenance` ما لم يوجد توافق مثبت ضمن السياسة | لا إجبار المستخدم على فقد المسودة أو إعادة الطلب. |
| تحديث كود خدمة AI بنفس schema/checkpoints ودلالة الأدوات | `online` بعد قبول AI مستقل | عنوان خدمة AI يثبت ضمن الإصدار، مع استمرار runs/claimed writes؛ لا يكفي قبول Odoo. |
| ترقية schema/checkpoints غير المتوافقة في قاعدة AI المشتركة | `service_maintenance` | قد تتوقف ميزة AI لكل مستخدمي تلك القاعدة، مع بقاء بقية نسق؛ عزل Odoo لكل عميل لا يحل ترحيل هذه القاعدة المشتركة. إن رُفض هذا التوقف يُحجب الإصدار حتى تصميم ترحيل حي مستقل. |
| تحديث محرك Odoo ضمن 19.0 | مراجعة الإصدار المثبت | online فقط بعد إثبات أنه كود متوافق بلا ترقية قاعدة أو اختلاف جلسات؛ خلاف ذلك صيانة العميل. |
| ترقية Odoo رئيسية أو تحويل تخزين كبير | `tenant_maintenance` أو مشروع مستقل | لا وعد بانعدام التوقف؛ نقل نسخة قاعدة دون نقل كل الكتابات اللاحقة يفقد بيانات. |
| تحديث guard أو صورة الحافة | `online` بعد إثبات التحويل والتصريف | reload إعداد يختلف عن استبدال العملية؛ اتصالات WS تحتاج معالجة صريحة. |
| تحديث PostgreSQL أو المضيف/التخزين دون HA مُثبت | `infrastructure_maintenance` | قد يشمل كل العملاء على المورد؛ مجموعتا التطبيق لا تمنعان ذلك. |
| تغيير مجهول الأثر أو غياب دليل توافق/نسخ | `blocked` | يُمنع النشر؛ لا يُحوَّل إلى online بالتخمين. |

مدة الصيانة ليست ثابتة: تصريف أعمال العميل + ضمان لقطة DB/filestore + الترقية + فحص القبول + التحويل. لا تقدير بالثواني قبل قياس بيانات وحمل مماثلين. تجاوز الموعد يوقف دفعة العملاء التالية؛ لا يلغي ترحيلًا جارياً أو يعيد فتح قاعدة مشكوكًا فيها تلقائيًا.

## 4. البدائل وقرار التصميم المقترح

| البديل | النتيجة | القرار المقترح |
|---|---|---|
| استبدال حاوية Odoo الوحيدة | انقطاع مشترك أثناء الإقلاع، لا عزل ترقيات | لا يحقق الهدف. |
| rolling عشوائي لكل طلب بين إصدارين | قد تتداخل جلسات/أعمال وعقود مختلفة على القاعدة نفسها | لا يُستخدم دون إثبات توافق، ولا يصلح لترقية مخطط كاسرة. |
| مجموعات إصدار مع تحويل كامل للعميل | يسمح ببقاء العملاء على إصدارهم ونقلهم تدريجيًا | الأساس المقترح. |
| قاعدة منسوخة ثم تبديلها بلا تصريف أو مزامنة | يخسر الكتابات والمرفقات بعد النسخ | مرفوض. |
| ترحيل حي لكل أنواع المخطط | يتطلب بنية مزامنة وتوافق وقيودًا لا يثبتها المصدر | بحث مستقل عند حاجة محددة؛ ليس وعد هذه الخطة. |

لا تغيير في تنظيم المستودع الواحد، ولا تعديل لمصدر Odoo، ولا fork لكل عميل. نسختا الحاويات أثناء النشر artifacts تشغيلية مؤقتة، وليستا مسارين قديمًا وجديدًا في المصدر. سياسة «مخطط واحد بلا بقايا» باقية؛ لا أعمدة ظل أو wrappers أو flags لحفظ سلوك قديم. أي اقتراح لاحق يخالفها يحتاج قرارًا صريحًا قبل إدراجه.

## 5. المعمارية المقترحة

### 5.1 حزمة إصدار ثابتة وواضحة الأثر

ملف الإصدار يربط commit نسق، وcommit Odoo، وبصمات الصور والأصول، ونسخ الموديولات، والتثبيت/الترقية المطلوبة وإغلاق تبعياتها، وتصنيف التوقف ودليل التوافق. تغيير كود خلفية لا يستدعي تحديث كل الوحدات بـ`-u all`. الفاحص يرفض اختلاف البيانات/المخطط أو التعليمات المخفية في hooks عن تصريح الإصدار. الفحص الآلي يساعد المراجع ولا يدعي استنتاج أثر كل Python من أسماء الملفات.

### 5.2 مجموعات تشغيل بإصدارات محددة

نبدأ بمجموعتين مؤقتتين عند النشر، وليس مجموعة دائمة لكل عميل. لكل مجموعة صور Nuxt/Odoo وWS محددة، وإعدادات تشغيل وميزانية موارد. تكون HTTP workers بلا cron؛ cron والـjobs يملكان عضوية عملاء صريحة وإصدارًا واحدًا صالحًا لكل عميل. تحتاج مجموعات الإصدار أذونات اتصال بقواعدها فقط، مع منع اتصالات جيل قديم وإغلاق الموجود منها قبل ترقية القاعدة؛ مجرد `REVOKE CONNECT` لا يقطع اتصالًا قائمًا.

بوابة سابقة لكل تحويل: حساب bootstrap/ترقية محصور بالمشغّل، وحسابات runtime لكل مجموعة ليست superuser أو CREATEDB أو CREATEROLE، ولا ترث دور الإدارة أو ملكية تمنحها تجاوز منع الاتصال. تلغى منح PUBLIC/الوراثة التي تفسد حصر CONNECT، وتُمنح صلاحيات التطبيق اللازمة بالإجراءات المعتمدة وتختبر مع Odoo الحقيقي. لا تُوزع أسرار bootstrap على حاويات الخدمة. في online تُصرف الطلبات القديمة أولًا ثم تحجب صلاحيتها؛ في migration لا تبدأ الترقية حتى تثبت استحالة اتصال/معاملة قديمة أو متوقفة مؤقتًا. إن لم يعمل stock Odoo بهذه الحدود يُحجب التحويل حتى حل التصميم، لا تضاف صلاحية تجاوز لإمرار الاختبار.

تُفصل إعدادات HTTP المشترك عن إعدادات cron/الترقية المحددة القاعدة عبر نقاط التهيئة العامة في Odoo. يبقى `dbfilter` وحد Host الموثوق ومنع تجاوز CLI كما هو في مسار HTTP. لا نضع override خاصًا داخل Odoo لإدارة الأجيال.

### 5.3 توجيه الإصدار مستقل عن هوية العميل

سجل الهوية الحالي يظل مالك tenant/Host/DB/filestore/الإبطال. سجل تشغيل مستقل يملك **حقيقة مختلفة**: مجموعة الإصدار وحالتها ومراجعة تحويلها. لا يغير تحويل إصدار فقط `registryRevision`، ولا يعيد تمكين عميل معطل، ولا يغيّر DB/filestore.

كل طلب يختار لقطة إصدار واحدة وتُستخدم عبر SSR وBFF وOdoo والمحتوى وWS؛ لا round-robin يختار إصدارًا مختلفًا في القفزة الثانية. الوجهات معرفات داخل قائمة operator ثابتة؛ لا URL أو DB يأتي من المتصفح. ترفض headers المزورة والوجهات الغائبة ولا توجد قاعدة بديلة صامتة.

نشر مسار إصدار لا يستعمل `.pending` الخاص بسجل الهوية العالمي. له تبديل ذري مع CAS وسجل دائم وأجيال؛ الفشل الملتبس يوقف العميل المستهدف، ولا يسمح باستخدام إصدار قديم فوق قاعدة رُقّيت. يبقى رفض سجل الهوية عند غموضه كما هو؛ انعدام توقف النشر لا يبرر إضعاف الإبطال. تقليل نطاق حواجز الهوية العامة مشروع منفصل إن لزم، وليس حذف الحاجز.

عقد النشر على المضيف الواحد: ملف route كامل لكل عميل في مجلد مشترك، مع منع symlinks وربط المجلد لا inode ملف منفرد. في **online** تسجل SQLite نية التحويل مع بقاء الإصدار السابق مصرحًا، ثم يكتب ملف مؤقت و`fsync` ثم `rename` ذري و`fsync` للمجلد؛ تعلن الـguards مشاهدة المراجعة الجديدة، وتسجل الحالة المرصودة، ثم يصرف القديم. لا حاجز يرفض طلبات العميل في التحويل online. إذا مات المنسق قبل النشر تبقى اللقطة السابقة الكاملة المصرح بها على قرصه؛ بعد النشر تصالح النية مع digest المرصود. لا يُلغى تصريح القديم أو يُوقف حتى مشاهدة التحويل وتصريفه. هذا تداخل إصدارات متوافق معلن، لا fallback إلى ملف قديم عند خطأ قراءة أو إبطال هوية.

في **migration** يُنشأ أولًا حاجز صيانة دائم **لهذا العميل فقط** ويُعمل `fsync` له ولمجلده؛ تؤكد guards والـeffects مشاهدته ويصرف الجاري، ثم يثبت fence وانعدام الكتاب القدامى وتسجل المرحلة قبل أي ترحيل. بعد القبول ينشر route الجديد ذريًا، وتثبت بصمته ومراجعته وأذونات الجيل الجديد في SQLite وتؤكد الجهات مشاهدته، ثم يرفع الحاجز و`fsync` للمجلد. حاجز باقٍ بعد تعطل المنسق لا ينتهي بمهلة ولا يُحذف إلا بمصالحة تثبت حالة القاعدة والصورة والمسار؛ بقية العملاء يقرؤون ملفاتهم دون هذا الحاجز. فشل قراءة ملف عميل أو تضارب جيله يمنعه وحده. صيانة قاعدة AI المشتركة لها حاجز خدمة AI منفصل لا يرفض واجهات ويب فيو الأخرى.

### 5.4 الجلسات والملفات والصفحات المفتوحة

يُختبر مخزن جلسات filesystem مشترك آمن للمجموعتين على المضيف نفسه مع keyring ثابت؛ هذا الاختيار للمراجعة محليًا ولا يثبت توافق تخزين شبكي متعدد المضيفين. الـfilestore واحد لكل عميل مع وصول متوافق للمجموعتين؛ لا نسخ دوري غير متسق. تبقى الأصول المرقمة القديمة في مخزن النشر طوال عمر الصفحات المدعوم، خارج مصدر المنتج.

طلب قديم جارٍ يُكمل على المجموعة القديمة، ولا يُعاد POST/PATCH/DELETE تلقائيًا عند قطع الشبكة. جاهزية التحويل تتطلب أن يكون القديم والجديد متوافقين مع كتابة متزامنة على القاعدة نفسها. اختلاف السلوك الذي لا يتحمل ذلك يصنَّف صيانة. يجري استئناف WS/AI stream من حالة محفوظة إن كان البروتوكول يدعمه؛ دون دليل لا نصنف قطعه كتحديث بلا أثر.

### 5.5 سلطة التشغيل وملكية الأعمال

محرك نشر واحد في `deploy/releases` يعمل بأمر مشغل صريح. يحتفظ بحالة SQLite محلية دائمة (على مضيف منسق واحد)، وقفل لكل عميل وقفل نشر المسارات، ومراحل قابلة للمصالحة بعد الانقطاع. لا queue جديدة داخل المنتج ولا اعتماد لتشغيل العميل على خدمة التحكم. تشغيل موزع متعدد المنسقين خارج النطاق حتى توجد سلطة مشتركة مُثبتة.

الـCLI المحلي صالح لـshared managed وdedicated/customer-hosted؛ مسار non_saas لا يستدعي خدمة التحكم. مصدر حقائق الهوية في shared يظل السجل المنشور الموثوق؛ CLI لا يبدله ولا يرفع الاستحقاقات. لوحة المزوّد تستطيع استهلاك تقارير النشر لاحقًا، وربط زر تنفيذ بها ليس ضمن هذه الخطة.

قفل SQLite الجديد وحده لا يمنع jobs القائمة. تُدمج بوابة عمليات runtime واحدة عند حدود effects الحالية: provision/backup/restore/reconfigure/admin-password/usage وأي عمل يفتح قاعدة، إضافة لمحرك الإصدار. تبقى جدولة أعمال خدمة التحكم وسلطتها الحالية، لكن عملية فعلية لا تعبر حجز عميل النشر؛ `busy` يؤجل العمل دون اعتباره أثرًا منفذًا. تشترك الأدوات المحلية في بوابة runtime نفسها دون اعتماد non_saas على خدمة التحكم. كل طريق غير خاضع للبوابة يحجب قبول fencing.

### 5.6 خدمة AI ومسار المخصص والانتقال الأول

يحدد PoolConfig عنوان وصورة AI أو مرجع مجموعة AI ثابتة لم تتغير، ويحدد manifest نسخة schema/checkpointer وتوافق قراءة وكتابة checkpoints. لا يعاد setup لقاعدة AI المشتركة من صورتين متعارضتين عند الإقلاع. في تحديث AI متوافق تُصرف runs والأدوات المطالب بتنفيذها قبل نزع ملكية القديم، وتبقى معرفات runs وclaims وحالتها؛ تعديل BFF يثبت عنوان الجيل ولا يعود إلى عنوان عام خلال الطلب. في ترحيل حالة AI غير المتوافق يلزم `service_maintenance` معلن لميزة AI على كل عملاء قاعدة الحالة، أو حجب التحديث؛ هذه ليست ترقية قاعدة Odoo لكل عميل.

adapter المخصص يقرأ binding واحدًا من إعداد operator المحلي (Host/DB/filestore/commercial_mode)، ويُبقي cookie Odoo الحالية ومسار جلساتها دون إدخال غلاف shared قسرًا. يملك Caddy المخصص اختيار مجموعة Nuxt/Odoo/WS وحالة الصيانة، ويثبت Nuxt عنوان Odoo وAI لنفس الجيل. الجلسات وAPI/auth والمرفقات لا تتجاوز بوابة الصيانة حتى إن كانت الوجهة داخلية. تُختبر هذه الوصلة مستقلة مع منع الشبكة نحو أي خدمة vendor؛ اشتراك CLI لا يثبت تكافؤ المسارين.

الانتقال الأول إلى مجموعات الإصدار مرحلة bootstrap مستقلة: إضافة مجموعة من **نفس الإصدار الحالي**، وحفظ الجلسات، وفحص أن reload الحافة يمكنه نقل الطلبات دون إيقاف النسخة الوحيدة، ثم إدخال سلطة runtime المقيدة. تغيير حساب DB أو مخزن الجلسات/صيغة cookie أو إيقاف singleton لا يُوصف online بلا تجربة. إذا تطلب وضع التشغيل الحالي إعادة تشغيل المورد الوحيد، تُصرح صيانة أولية بنطاقها أو يؤجل الانتقال حتى يوجد مسار موازي مثبت. لا ننسب قدرة النظام المستهدف إلى أول نشر له.

## 6. مسارا التنفيذ

### A. إصدار online

1. فحص artifact والتصنيف والتوافق والموارد، ثم تشغيل المجموعة الجديدة دون أي `-u`/`-i`.
2. قبول مسبق على عميل اصطناعي، وفحص جاهزية tenant الفعلي دون ترحيل أو آثار كتابة غير مصرح بها.
3. CAS يوجه الطلبات الجديدة للعميل الأول إلى الإصدار الجديد؛ الطلبات الجارية تبقى على القديم، ويتسلم cron/jobs الجديد ملكية العميل بعد تصريف القديم.
4. مراقبة القراءة والحفظ والجلسة والمرفقات وWS؛ لا نقل دفعة جديدة إذا فشل شرط.
5. توسيع الدفعات: 1 ثم 2 ثم البقية في التجربة الأولية. التراجع توجيهي فقط إذا أثبت الإصدار أن كل الكتابات الجديدة قابلة للقراءة والتعديل من القديم؛ المخطط وحده لا يكفي.
6. لا إيقاف للمجموعة القديمة حتى تصريف طلباتها واتصالاتها وأعمالها، وتثبيت عدم وجود عملاء عليها. انتهاء مهلة التصريف يعني إبقاءها أو إلغاء التوسعة، لا قتل كتابة جارية.

### B. إصدار يحتاج ترقية قاعدة

1. تجربة كاملة على نسخة معزولة مماثلة للحجم، مع منع البريد/webhooks/الأعمال الخارجية أثناء التجربة، وقياس الصيانة والاسترجاع.
2. صيانة تشغيلية معلنة للعميل المستهدف فقط، منفصلة عن تعطيل استحقاقه؛ تصريف كل الطلبات وcron وAI والأعمال المعلقة ومراقبي الاستخدام ثم إثبات عدم وجود كاتب قديم. تأجيل/قيد أعماله الجديدة دون فقدها أو تكرارها؛ لا الادعاء بقبول حفظ لم يُنفَّذ.
3. أخذ لقطة متسقة من DB وfilestore وهوية الصورة والجلسات المطلوبة، والتحقق من إمكانية استعادتها. هذه المرحلة نفسها قد تزيد وقت توقف العميل؛ النسخ اليدوي الحالي لا يكفي.
4. عامل ترقية واحد، مقيد بالعميل والإصدار وبوابة fence، يشغّل Odoo عبر أدواته العامة على الوحدات المطلوبة وتوابعها. لا وصول لكود الإصدار القديم إلى القاعدة بعد بدء الترحيل.
5. فحص حالة الوحدات والهوية والاستحقاقات وقراءة وكتابة عملية قبول مضبوطة والمرفقات على الإصدار الجديد، ثم تحويل المسار ورفع الصيانة وإعادة الأعمال.
6. إذا فشلت الترقية يبقى العميل في الصيانة وتُوقف الدفعة. الاسترجاع يستعيد صورة وDB وfilestore متوافقة؛ لا downgrade ولا صورة قديمة فوق مخطط جديد. بعد استئناف كتابة العملاء، استعادة لقطة سابقة تفقد ما تلاها، فتحتاج قرار حادث واستعادة/تسوية منفصلًا؛ لا rollback تلقائي مضلل.

اللقطة لكل عميل قد تؤخذ مع استمرار الآخرين فقط بعد تنفيذ fencing الحقيقي. المسار الحالي الذي يوقف خدمة Odoo كلها لا يُستدعى من محرك التحديث الجديد. لا تؤخذ نسخة توقف العميل قبل كل إصدار online وتظل التسمية online؛ يشترط له مسار استرجاع كود متوافق وحماية بيانات سابقة مثبتة.

## 7. القبول قبل أي ادعاء أو إطلاق

### اختيار العميل موعد الصيانة — إضافة مناقشة 2026-10-16

طلب المالك إتاحة جدولة العميل صيانته. يدخل ضمن المقترح أن يختار **مسؤول العميل المخول** نافذة صيانة متكررة حسب المنطقة الزمنية، أو موعدًا خاصًا لإصدار يحتاج صيانة. يبقى العميل على الإصدار المدعوم الحالي حتى موعده، وتستمر ترقية العملاء الآخرين حسب نوافذهم. لا تتطلب تحديثات online حجز صيانة، ولا يعد اختيار موعد تفويضًا لكل أثر خارج التحديث المعلن.

- تعرض الواجهة الإصدار والأثر والمدة المقدرة من تجربة مماثلة والموعد المؤكد وحالة التحديث. لا تظهر خانة مدة مضمونة من التخمين. تعرض حالة الصيانة ونتيجتها لمن يتأثر بها؛ إشعاراتها جزء من التنفيذ اللاحق، ولم تُرسل في هذه المراجعة.
- يخزن المصدر المالك تفضيل النافذة بمنطقة IANA الزمنية، ويمثل الحجز الفعلي لحظة UTC مع المنطقة المعروضة. الوقت المحلي المكرر أو غير الموجود عند تغيير التوقيت لا يفسر بصمت. إعدادات عميل لا تعدّل إعدادات آخر؛ الصلاحية والتدقيق على الخادم.
- الحجز مرهون بسعة مجموعات الإصدارات ونجاح preflight ووجود مدة نافذة تكفي للنسخ والترقية والفحص والاسترجاع المقاس. بلوغ الوقت وحده لا يبدأ ترقية غير جاهزة. التزاحم يرفض/يقترح حجزًا آخر قبل التأكيد، لا يوقف عملاء أكثر من السعة المتحققة.
- يسمح بالتعديل أو الإلغاء قبل حجز التنفيذ النهائي وبدء تصريف الأعمال. يتسابق الإلغاء والبدء عبر CAS واحد؛ بعد بدء الترحيل لا يقطع تغيير الموعد العملية ولا يعد بتراجع آلي. التأخر عن نهاية النافذة حالة تدخل معلنة، وليس مبررًا لقتل migration أو إعادة فتح قاعدة غير آمنة.
- لا تأجيل مفتوحًا: `docs/migrations.md` يدعم الحالي والسابق. يحدد الإصدار آخر موعد مسموحًا وسياسة التحديث الأمني العاجل وشروط الإشعار قبل إتاحته للحجز؛ هذه قرارات منتج لم يعتمد المالك قيمها بعد. إن سبق العميل أكثر من مسار الترقية المثبت، يختبر مسار مناسب أو تحجب الجدولة؛ لا نفترض قفزة إصدار غير مختبرة.
- صيانة AI ذات قاعدة الحالة المشتركة أو المضيف/PostgreSQL لا تصبح فردية لمجرد وجود تقويم لكل عميل؛ تظل نافذة جماعية معلنة أو تحتاج فصل مجموعات الخدمة/المورد. يوضح نطاقها قبل تأكيد الموعد.
- واجهة الإعداد والـAPI ومالك تخزين التفضيل تحتاج تحديدًا قبل التنفيذ؛ لا تُفتح مكالمة جديدة من واجهة العميل إلى خدمة التحكم بافتراض أن استثناء الاشتراك يسمح بها. يبقى R5 ومسار non_saas مستقلين. عامل الجدولة يستعمل محرك التحديث وfencing نفسه، ولا يصير محرك ترقية موازيًا.

معايير قبول الإضافة: عميلان بموعدين مختلفين لا يترقيان معًا؛ رفض مستخدم غير مخول أو حجز لعميل آخر؛ إعادة تشغيل المجدول أو تكرار المهمة لا يكرران الترحيل؛ صحة المنطقة الزمنية وتعارض الإلغاء/البدء؛ وعدم بدء تحديث متعثر أو أمني متجاوز للموعد دون تطبيق السياسة المعتمدة. جدولة الصيانة ميزة مخططة وليست موجودة أو مختبرة بهذا المستند.

قيم التجربة التالية اختيارات هندسية مقترحة وليست SLA معتمدًا: 10 عملاء اصطناعيين، 5 جلسات نشطة لكل عميل، حمل 30 دقيقة يشمل 10 تحويلات، وتكرار التمرين كاملًا مرتين. p95 لا يزيد عن 20% من baseline بنفس الحمل؛ تُراجع سعة البيئة قبل تثبيت هذا الحد.

- online: صفر أخطاء HTTP/مصادقة أو حفظ منسوبة للنشر، وصفر عمليات مؤكدة ضائعة أو مكررة، وصفر فقد مسودة أو إجبار خروج. يقارن سجل الطلبات بمعرفات أعماله والبيانات الفعلية؛ إخفاء الخطأ عبر retry ليس نجاحًا.
- WS وAI: انقطاع النقل يسجل منفصلًا؛ قبول استمرار الخدمة يحتاج إعادة اتصال واستعادة الحالة دون فجوة أعمال/تكرار إجراء أو فقد رد. إن لم يتحقق ذلك فلا يُعلَن هذا التدفق online.
- الصيانة: قياس بداية ونهاية منع الطلبات لكل عميل؛ التسعة الآخرون يحافظون على شروط online طوال drain/backup/upgrade/restore للعميل العاشر.
- انقطاع المنسق في كل مرحلة، وناشران متنافسان، ومسار قديم، ورفض ترقية مبهمة: مصالحة بلا ترحيل مكرر وبلا فتح قديم على قاعدة جديدة.
- عزل الأجيال: HTTP وcron وAI وone-off jobs من الإصدار القديم لا تصل للقاعدة بعد fence، وتُقاس الاتصالات القائمة لا منح الاتصال فقط.
- أدوار PostgreSQL: اختبار فعلي لاتصال قديم قائم وآخر جديد، ودور موروث وPUBLIC وحساب ذي صلاحية تجاوز؛ يمنع preflight هذه الإعدادات، ولا تنتقل سرية حساب الإدارة إلى runtime.
- AI: استمرار claim واحد وcheckpoint واحد عبر النسختين المتوافقتين، ورفض ترقية حالة غير متوافقة بوصفها online، وإثبات استمرار غير AI أثناء صيانة خدمة AI.
- نشر guard والحافة ومفتاح جلسة متوافق، وصفحة مفتوحة قبل الإصدار تطلب chunk قديمًا وترسل عقدها القديم، ورفع مرفق أثناء التحويل.
- فشل الترحيل والنسخ/التخزين وعودة جلسة بعد التحويل: لا فقد بيانات، لا توقف بقية العملاء، ولا إعلان جاهزية كاذب.
- dedicated وnon_saas: نفس بوابات السلامة، والتشغيل بلا اتصال vendor؛ لا توسعة نطاق الاستضافة ضمن تنفيذ هذه الخطة.
- bootstrap: تجربة انتقال التكوين الحالي إلى مجموعتين بنفس الإصدار، بقياس مستقل لأي توقف؛ لا تدمج نتيجتها مع اختبارات تحديث نظام جُهّز مسبقًا.

تثبت هذه التجارب السلوك تحت ظروفها فقط. يلزم قبول على بنية الاستضافة الفعلية قبل ادعاء قدرة إنتاجية أو تحديد زمن صيانة تعاقدي.

## 8. القرارات والتفويض

المؤكد من طلب المالك: إعداد خطة قبل التنفيذ، واستمرار عمل العملاء هدف أساسي. المقترحات الهندسية هنا (مجموعات الإصدار، SQLite لمنسق واحد، مخزن الجلسات، قيم التجربة) ليست موافقة منه بعد.

القرار المطلوب قبل البناء يميز ثلاثة استثناءات: صيانة عميل واحد عند ترقية Odoo/المخطط؛ وصيانة ميزة AI لكل مستخدمي قاعدة حالتها المشتركة عند ترحيل غير متوافق؛ وصيانة bootstrap أولية محتملة تشمل مستخدمي المورد الوحيد الحالي. لكل منها قبول صريح أو حجب/تأجيل ذلك المسار حتى إثبات بديل بلا توقف. كذلك يعتمد موقع الاستضافة والتخزين وحمل السعة وRPO/RTO قبل تنفيذ المرحلة التشغيلية. يجوز بناء واختبار الآليات محليًا لاحقًا بتفويض مستقل؛ لا ينفذ هذا المستند شيئًا.

خطة المهام: [خطة التنفيذ](../plans/2026-10-16-webvue-continuous-updates.md). لا commit أو push أو merge أو deployment ضمن هذه المراجعة.

## 9. مراجع تقنية أولية

- [Odoo 19 — المصدر المثبت للـregistry](https://github.com/odoo/odoo/blob/34eed49d88f0f4357e1f54fe82cb0ad280939572/odoo/orm/registry.py): المرجع المحلي المطابق هو دليل آلية reload والترقية، ولا نستنتج منه ضمان zero downtime.
- [PostgreSQL 16 — ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html): بعض تغييرات المخطط تأخذ أقفالًا حصرية؛ إضافة حقل ليست تصريحًا بترقية حية.
- [Caddy — reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy): reload قد يغلق streams؛ توجد إعدادات لتأخير الإغلاق، ولا تغني عن تجربة المسار كاملًا.
- [Caddy — reload](https://caddyserver.com/docs/command-line#caddy-reload): إعادة تحميل إعداد تختلف عن إيقاف عملية الحافة واستبدال صورتها.
