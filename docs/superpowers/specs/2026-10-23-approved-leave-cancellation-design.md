# Approved-leave cancellation policy and approval

## Intent and authority

Owner decision, 2026-10-23: the default for an employee cancelling approved leave is a cancellation request requiring the responsible manager's approval. Client-varying behavior belongs in company settings. This fixes the self-service split hiding an action supported by the engine, while implementing the newly chosen approval boundary. Existing authorization covers implementation, organized commits, protected PR integration and safe preservation/cleanup; no deployment or real database upgrade is included.

The owner chose manager approval and company configurability. Concrete identifiers, storage, conflict handling, native execution and presentation below are coordinator design calls using existing Odoo 19/Nuxt patterns, rather than additional owner decisions. “Manager” here means an existing authorized company-scoped `hr.leave.approve` holder with native visibility; it does not introduce an assignment to `employee.leave_manager_id` or a new management hierarchy.

## Behavior

- Company policy values: `manager_approval` (default even with no saved row), `direct_employee`, `manager_only`. Settings are company owned, revision checked; reading defaults creates nothing. HR settings explain all three in Arabic and English.
- An employee with `hr.leave.request` may request cancellation of their own fully approved (`validate`) leave when stock Odoo permits cancellation. Under the default this creates a pending request; the leave stays approved, its balance/work entries remain untouched, and a repeated submission returns the same pending request.
- Direct policy uses the existing native cancellation wizard immediately. Manager-only policy offers no employee cancellation action. Existing own pending-leave withdrawal (`confirm`) is unchanged; the policy governs fully approved leave, not initial approval or allocation.
- An authorized approver needs `hr.leave.approve`, current company access and native visibility. Native cancellation eligibility is evaluated as the employee who owns the leave, because native managers cannot cancel others' leave. The existing `hr.leave.manage` capability manages balances and grants no new cancellation-decision authority. Nobody approves or refuses their own cancellation request, including managers.
- Approving a pending cancellation records the real manager's approval, then runs a fresh `hr.holidays.cancel.leave.action_cancel_leave()` as the leave's ordinary employee user in the same transaction. A failed native cancellation rolls back the approval and leaves the cancellation request pending and the leave unchanged. Refusal requires a nonempty reason and leaves the approved leave/balance unchanged.
- Under all three policies an authorized approver may directly cancel another employee's approved leave through the same audited aggregate and native owner execution. In `manager_only` this supplies the manager action while employees have no cancellation action. Direct manager action on an existing pending request requires its current revision and resolves it atomically. Without a pending request it creates/reuses the aggregate and records the manager as its actual initiator and reviewer, never fabricating an employee submission. Direct employee cancellation under `direct_employee` remains owner-driven and needs no manager decision.
- Policy changes apply to subsequent submissions. They never approve/refuse an existing pending request. Pending requests remain visible and decidable with the same authorization after policy changes; direct cancellation must not bypass an already pending approval request.
- After refusal, the employee may submit a new reason under the current policy if the leave remains natively cancellable. The prior decision/reason remains in tracked history. No new employee cancellation-request-withdrawal flow is introduced.

## Ownership, security and storage

Everything is owned by `webvue_hr`; no new addon, private native/access override, raw SQL, new sudo, copied engine body or architecture baseline growth. Two narrow public native extension points are permitted: `hr.holidays.cancel.leave.action_cancel_leave` and `hr.leave.write`. Stock source remains read-only. These extensions enforce policy; they do not broaden native eligibility.

1. `webvue.hr.leave.settings`: one row per company, selection plus positive revision. `hr.leave.config` is a new application capability seeded into the existing customer HR manager role, not implied by leave balance management or ordinary system administration. The existing trusted vendor-support operator exception remains authoritative: core grants this identity every catalog capability, so its matching HR-owned native ACL group must also be linked. This preserves the existing operator policy; it does not grant customer custom roles an implicit permission or introduce an HR-specific capability evaluator. Existing company-scoped role assignments govern it. Settings-only custom roles can configure without employee/balance access. Ordinary company-scoped model read access for `hr.leave.read` permits the serializer/native policy guard to read the effective selection without elevation; only `hr.leave.config` permits configuration or the settings HTTP surface. Settings rows contain no employee/private data.
2. `webvue.hr.leave.cancellation`: owned `mail.thread` aggregate referencing native leave and owning company, requester (the employee user whose leave is affected), actual `initiator_id`, request reason/date, revision, state (`pending`, `approved`, `refused`), reviewer/review date/reason, and `leave_version` (native `write_date` at submission). One aggregate per leave, reused after a refusal, with tracked fields and explicit native chatter events preserving every submission/decision, including repeated equal reasons. Employee submissions have initiator=requester; manager direct initiation clearly records a different initiator and is described as manager initiated. Data for the leave/company/requester is derived, never independently writable from HTTP. Leave deletion must not cascade away the tracked aggregate; use a restrictive relation once cancellation history exists.
3. Public ORM create/write/unlink boundaries must enforce the same company, ownership, role and transition checks as HTTP; record rules restrict own requests versus legitimate HR approvers. Ordinary users cannot forge reviewer, approved state or another employee's request through ORM. Capability revocation is rechecked at every action. A new model is not permission to duplicate or override stock leave permissions.
4. Requests and decisions use native PostgreSQL/Odoo repeatable-read retry behavior plus revision/unique constraints. Duplicate pending submission is idempotent; duplicate/stale decisions produce structured `409 conflict`. Concurrency tests must prove one decision, preserving native balance/work entry effects.
5. A pending request records the native leave version at submission. If an outside native edit changes that leave, approval rejects with 409 and a clear reload message; the manager can refuse the stale request, and the employee can resubmit against the current leave. Manager direct cancellation of a leave with a pending request must atomically resolve that request with tracked manager identity, rather than leave a ghost pending item.

### Protected native execution and ORM policy

- The aggregate's private execution helper rechecks the real manager's current company-scoped capability, native leave read access, non-ownership, request revision and native version. It records that manager as reviewer before executing; it must not call the native wizard in the manager's environment.
- Resolve the employee principal from the native leave and require it to match the aggregate's protected requester. Require an active linked user with owning-company access, current `hr.leave.request`, an ordinary non-superuser environment, own native visibility, and true native `can_cancel`. Use `with_user(employee_user).with_context(allowed_company_ids=[company.id])`; do not accept an execution user or authorization flag from HTTP/context. Re-evaluate eligibility at execution, including date cutoff and validated work entries. A missing/deactivated/unlinked/privileged/ineligible owner fails closed with an actionable error; a manager cannot override these conditions.
- Wrap only the fresh owner-wizard call in `protected_write.marked` using an HR-owned marker keyed by aggregate id and exact approved revision. The private helper binds/checks leave id, requester, reviewer, owning company and recorded native version before issuing it. Wizard authorization requires both the protected approved aggregate and the live cursor-local marker. A persisted historical approval is never sufficient; context flags and aggregate IDs supplied by callers cannot issue the marker. Restore it on success and exceptions.
- The public native wizard extension checks current feature, company, own request capability and native eligibility. For fully approved leave, ordinary direct execution is allowed only under `direct_employee` with no pending request, or with the exact live internal approval marker. Any pending aggregate blocks an unmarked direct call regardless of current policy or native leave state. For other native cancellable states without pending cancellation preserve existing own cancellation behavior. The extension calls `super().action_cancel_leave()` exactly once after authorization; native internal elevation and work-entry effects remain native.
- The public `hr.leave.write` extension rejects a non-superuser attempt to set `state='cancel'` directly, including calls carrying `leave_fast_create` or forged policy/context flags. An employee/manager must use the policy-checked wizard; native `_force_cancel` already writes in its own superuser environment and passes this fence. Do not add a general write/access override or override native compute/private transition methods.
- Public aggregate create/write/unlink accept no forged state, reviewer, requester, company, revision or version. Public action methods perform all authorization before protected private transitions; ordinary direct write cannot reuse their transition privilege. No internal marker or alternate execution identity is exposed as a public action parameter.
- The native reason includes the real manager's id/name and whether the action approves a request or directly cancels it, plus employee submission/manager decision reasons as applicable. The aggregate is the authoritative manager audit; native chatter may be authored by the employee execution identity and must not be presented as manager-authored. All aggregate state/history, native chatter, balance and work-entry changes commit or roll back together.

## HTTP and contracts

Retain `/api/v1/hr/leave/requests/:id/cancel` for own confirm withdrawal, employee cancellation submission/direct cancellation, and authorized manager direct cancellation. It accepts `reason` and optional positive `revision`; manager direct resolution of a pending aggregate requires its matching revision. Capability gate accepts `hr.leave.request` or `hr.leave.approve`, and the owning service chooses/authorizes the exact path; confirmation withdrawal still requires own `hr.leave.request`. Under manager approval the employee's cancel action returns the updated leave with a pending cancellation aggregate, never a falsely cancelled leave. All action payloads reject unknown fields.

Add company GET/PATCH `/api/v1/hr/leave/settings`, guarded by `hr.enabled` and `hr.leave.config`; PATCH uses positive/zero default revision like shift settings. Effective employee policy is also present in the leave serializer; employees need no settings capability.

Add POST `/api/v1/hr/leave/requests/:id/cancellation/approve` and `/refuse`, accepting `revision` and optional approval reason / required refusal reason. All use structured errors, current owning company and native record visibility. Decision revision required, no stale overwrite. A `cancellation_state=pending` filter on existing request list supplies an actionable manager queue without depending on a later attention split. Unknown filter values are 422.

Extend strict `HrLeaveSchema` with nullable `cancellation` containing whitelisted aggregate id, state, revision, reason, requested_at, initiator, reviewed_at/reviewer/review_reason (nullable where absent), plus `cancellation_policy`, `can_request_cancellation`, `can_approve_cancellation`, `can_refuse_cancellation`. Existing `can_cancel` means actual direct employee or authorized manager cancellation is permitted; it is false for a pending approval (use the revision-bearing approval action). Personal views never render manager actions. Settings have their own strict schema. No compatibility wrapper/default is added merely to let stale mocks pass; update all fixtures and actual serializers together. The native version and internal marker never appear on the wire.

## User interface

Use existing page, form, confirmation and state components under DESIGN.md. Personal leave list/record display the effective cancellation action, pending/refused status, submission reason, and decision reason. Cancellation remains an inline-confirmed action, not a new stacked dialog or separate duplicate application.

HR administrator leave list adds a cancellation filter with URL persistence and pending badge; record/list expose authorized approve/refuse actions with rejection reason and refresh their data. Refresh/back/direct links preserve the list's origin/filter. A later attention cohort must include pending cancellations, but delivering this feature cannot depend on that future cohort.

HR application settings add a capability-scoped leave-policy section with company revision conflict handling, three options, Arabic/English copy and Storybook coverage. It works without payroll permission. No new client branding or shared presentation primitive is needed.
