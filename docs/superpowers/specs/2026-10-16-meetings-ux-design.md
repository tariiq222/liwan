## 1. الاتجاه المقترح

تُبنى التجربة حول: **أجد الاجتماع ← أجهّزه ← أوثّق النقاش والتوصيات ← أنهيه وأثبت نسخته ← أتابع التنفيذ**.
المطلوب تحسين دورة واحدة، لا تجميل كل صفحة منفردة. توجد لبنات جيدة: الإنشاء المرتبط بالمسار، حماية المسودات، صلاحيات السجل، النسخ التاريخية والطباعة. نحافظ عليها ونزيل التكرار والانقطاعات.

أوصي بثلاث وجهات قصيرة في القائمة: **الاجتماعات / المتابعة / الدورية**. تكون القائمة والتقويم عرضين للاجتماعات، وليسا قسمين متنافسين. صفحة الاجتماع نفسها تعرض: **نظرة عامة / المحضر / التوصيات / المرفقات / السجل**.
«المتابعة» صفحة جديدة مقترحة تجمع التوصيات المسموح بقراءتها، بما فيها الاجتماعات غير الدورية؛ تحتاج قراءة جديدة في API، وليست تعديلًا شكليًا فقط.

## 4. قرارات الصفحات

| الصفحة الحالية أو المقترحة | القرار |
|---|---|
| `/meetings` | تبقى المدخل التشغيلي: قائمة مع بحث ونطاق وفلاتر، ومبدّل «قائمة / تقويم» |
| `/meetings/calendar` | تبقى وجهة مباشرة؛ تزال فقط كرابط مستقل من القائمة الجانبية بعد إضافة مبدّل العرض. يظهر إنشاء اجتماع في رأس التقويم ومن اليوم المختار |
| `/meetings/follow-up` | **إضافة مقترحة** للمتابعة العامة، مع الاجتماع المصدر والمسؤول والموعد وحالة التنفيذ |
| `/meetings/new` | تبقى لوحة إنشاء مرتبطة بالمسار؛ بيانات أساسية ثم الحضور ثم جدول الأعمال الاختياري |

| `?tab=versions` | يفتح «السجل» على عرض النسخ. `?tab=history` يفتح النشاط؛ لا صفحة إضافية للنسخ |
| `/meetings/:id/edit` | تبقى صفحة بيانات الاجتماع وجدول الأعمال؛ لا تحرير المحضر هنا |
| `/meetings/:id/minutes` | تبقى صفحة تحرير المحضر الوحيدة، مع سياق الاجتماع والموضوع والرجوع |
| مسارا إنشاء وتعديل التوصية | يبقيان: إنشاء في اللوحة، تعديل في الصفحة، مع سياق واضح؛ لا نافذة أعمال متراكبة ولا صفحة تفاصيل توصية جديدة |
| `/meetings/:id/print` | تبقى صفحة الطباعة؛ نوع المصدر ورقم النسخة وتاريخها واضح قبل الطباعة |

لا أقترح صفحة لوحة مؤشرات إضافية، أو إعدادات عامة للاجتماعات، أو صفحة مستقلة لكل موضوع/قرار. الإضافة الجديدة الوحيدة هي المتابعة. تبقى مسارات البحث والإشعارات واجتماعات المشروع ومهامه كما هي.

## 5. توزيع المكونات

**المدخل:** العنوان وإجراء إنشاء واحد ← البحث والنطاق «الكل / اجتماعاتي» ومبدّل العرض ← فلاتر إضافية مطوية كما هي ← العدد والنتائج. لا تُحسب مؤشرات من صفحة نتائج جزئية.
أعمدة القائمة: الاجتماع والمرجع، الموعد، المنظّم، الحالة، التوصيات المفتوحة. العنوان أوسع عمود، والموعد لا ينكسر عند الساعة. الفلاتر المتقدمة تبقى حالة/مشروع/منظّم/فترة؛ بحث المنظّم يندمج داخل أداة اختياره بدل حقلين ظاهرين.

**السجل:** رجوع يسمّي وجهته ← الاسم والحالة والإجراء المناسب ← سطر مختصر للموعد والمكان/الانضمام والمنظّم ← التبويبات الخمسة ← محتوى التبويب. علاقة المشروع والدوري والمرجع خصائص مساندة بلا تكرار نفس الموعد أو الأشخاص.
النظرة العامة تعرض الموعد والحضور وجدول الأعمال ومساعدة «الخطوة التالية». المحضر يعرض المستند الحالي أو النسخة النهائية مع زر تحرير/معاينة حسب الصلاحية والحالة. تبويب التوصيات يملك وحده إجراءات التنفيذ؛ المرفقات لا تتكرر أسفل التبويبات الأخرى.

**المحرر:** سياق الاجتماع المختصر ← الافتتاح ← الموضوعات ونقاشاتها والتوصيات المرتبطة ← الختام ← بيانات التوقيع الاختيارية ← ملاحظات إضافية قابلة للطي. لا يعرض حقول توقيع قبل محتوى الاجتماع. لا يتحول الاسم المكتوب في خانة «المعتمد» إلى ادعاء بموافقة إلكترونية.
`minutes_form` يبقى مصدر المحتوى المنظم؛ `agenda` جدول الأعمال؛ `minutes` نص الملاحظات الإضافية الموجود. لا نسخ نص تلقائي فوق بيانات قائمة، ولا حذف حقول أو ترحيل بيانات ضمن هذا التصور. تبقى قراءة وطباعة المصادر السابقة مكتملة.

**الدوري:** القادم وآخر مكتمل ثم اللقاءات، مع فلاترها وعرضها الزمني/الجدولي. توضيح أن تعديل الإعدادات الافتراضية يخص اللقاءات الجديدة، وأن «هذا واللاحق» يطبّق فقط عقد الخادم الحالي ولا يغير حضور/محضر اللقاءات السابقة. لا محرر جديد لقواعد تكرار لا يسمح API بتعديلها.

## 6. الرحلات المطلوبة

1. **العثور والعودة:** القائمة أو التقويم أو المشروع أو الدوري أو البحث/الإشعار ← اجتماع ← تعديل/محضر/طباعة/توصية ← الاجتماع بالتبويب نفسه ← المصدر بفلاتره. نطاقات العودة دقيقة ومفحوصة بالصلاحية؛ لا قبول أي مسار قادم من query ولا رجوع اعتمادًا على history.
2. **الإنشاء:** اللوحة توضّح السياق الحقيقي؛ اليوم المختار يملأ التاريخ، ومشروع/سلسلة يمران بمعرّف لا باسم غير موثوق. عند النجاح تفتح صفحة السجل وتحمل المصدر؛ الإلغاء وEscape والإغلاق متكافئة مع حماية المسودة. لا تأكيد اجتماع تلقائيًا بمجرد إنشائه.
3. **الحفظ:** «إنشاء اجتماع» أو «حفظ التغييرات»، loading ومنع التكرار، نجاح بعد استجابة الخادم فقط. الفشل يبقي المدخلات، و409 يبقي المسودة ويعرض معالجة التعارض دون الكتابة على أحدث نسخة. انتهاء الجلسة لا يصبح نجاحًا.
4. **المحضر والتوصية:** حفظ المحضر أولًا؛ عند نجاحه تفتح لوحة التوصية وفيها اسم الاجتماع والموضوع. الإلغاء يعود للمحرر المحفوظ. نجاح إنشاء التوصية يعيد للمحرر والموضوع ويحددها محليًا مع تنبيه: «أُنشئت التوصية؛ احفظ المحضر لتثبيت ربطها بالموضوع». لا POST ثانٍ بعد refresh؛ إذا اختفى الموضوع تظهر التوصية غير مرتبطة بدل ربطها بموضوع آخر. فشل حفظ المحضر يمنع الانتقال إلى الإنشاء.
5. **الإنهاء:** المسودة تؤكّد؛ الاجتماع المؤكد يُنهى بواسطة المخوّل بعد وجود بداية ونهاية ومحتوى محضر وفق شرط الخادم الحالي. التأكيد يوضح تثبيت النسخة وإمكان استمرار متابعة التنفيذ. إعادة الفتح بواسطة المخوّل تعيد للمسودة وتحفظ النسخ السابقة. لا حالة جديدة «جارٍ» ولا مسار موافقات/توقيع إلكتروني جديد.
6. **المتابعة:** التوصية تظل في اجتماعها؛ بعد التحويل التنفيذ على المهمة. اقتراحي فتح المهمة الموجودة أو الناتجة في تبويب جديد مع نص صريح «فتح المهمة — تبويب جديد»، ويبقى الاجتماع وسياقه مفتوحين للمراجعة؛ لا نعيد تصميم تفاصيل المهام أو نعتمد على زر Back فيها. إذا تعذر قراءة المهمة يُعرض ارتباطها دون رابط أو اسم سري، ولا تعرض إجراءات تنفيذ بديلة تتجاوز القفل. المتابعة العامة لا تمنح المسؤول غير المشارك حق قراءة غير موجود اليوم.

## 7. عقد صفحة المتابعة المقترحة

- مسار الواجهة `/meetings/follow-up`، بقدرة `meetings.read` وميزة `meetings.enabled`، وبيانات تخضع لـACL وقواعد السجل والشركة الحالية.
- قراءة جديدة: `GET /api/v1/meetings/resolutions`. الغلاف `{items, total}`؛ كل عنصر من `MeetingPreviousResolutionSchema` الحالي، بلا نموذج أو جدول جديد.
- query: `q`، `mine=1` للمسند إلي ضمن السجلات المقروءة، `state=active|overdue|open|in_progress|done|cancelled`، `limit` افتراضي25 وأقصى100، `offset` افتراضي0. الافتراضي `state=active`؛ خيار «الكل» يحذف state. البحث في عنوان التوصية واسم الاجتماع كما في الدوري.
- الحالة المعروضة والمفلترة هي `execution_state` عند وجود مهمة مقروءة، وإلا `state` كما يفعل serializer الحالي. `active` تعني open/in_progress؛ `overdue` تضيف deadline قبل اليوم في منطقة المستخدم، ولا تعتبر مدة نصية بلا تاريخ «متأخرة».
- الفلترة والعدّ على الخادم قبل pagination وبنفس المجال؛ لا فلترة صفحة بعد تحميلها ولا fan-out لكل اجتماعات المستخدم. ترتيب ثابت: `deadline asc, id desc` مع الموعد الفارغ أخيرًا.
- التطبيق الأساسي لا يعرف `project.task`. يمدّ bridge `webvue_meetings_pmo` تفسير الحالة عبر hook في `webvue.meeting.links` وبصلاحيات القارئ نفسها. لا `sudo()` جديد ولا نسخة مخزنة لحالة التنفيذ.
- تُستخدم نفس دلالة الحالة في متابعة الدوري حتى لا يختلف فلتران للشيء نفسه. يجب فحص العدد والفلتر مع مهمة انتهت ومهمة أخفيت ومهمة مؤرشفة وبدون PMO.
- الصفحة تقرأ وتفتح اجتماع المصدر/المهمة؛ التعديل والتحويل وانتقالات التنفيذ تبقى في مواضعها الحالية، لتجنب محرر ثانٍ وإعادة بناء المهام.
