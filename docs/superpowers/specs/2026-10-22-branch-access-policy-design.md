# Branch access policy

Owner approved on 2026-10-22: explicit delegation by default, full isolation and controlled inheritance as configurable customer policies. Existing memberships must never imply sensitive access.

The current company owns a branch policy, editable only with access.users.assign_roles and access.roles.read. Modes are isolated, delegated (default), inherited. Isolated keeps requests on the current company. Delegated enables descendant memberships only for capabilities explicitly assigned in that company. Inherited additionally grants only selected built-in roles from the parent to selected descendant memberships, with per-branch opt-out. Unrelated companies and other tenants are always excluded. No policy creates memberships or grants all parent capabilities.

Settings live at /settings/team/branches. GET/PATCH /api/v1/admin/access/branches return a versioned policy. The API shape is {version, mode, branches: [{id, name, inherit, role_ids: number[]}], roles: [{id, key, name: {ar, en}, company_id: number|null}]}. PATCH takes {expected_version, mode, branches: [{id, inherit, role_ids}]}. Branch ids are the actor current company's descendant memberships; role ids are active assignable built-in roles only. Empty inheritance selects nothing. Settings changes use optimistic concurrency and audit.

Explicit per-branch user delegation has GET/PATCH /api/v1/admin/users/<id>/branches with {version, branches:[{id,name,role_ids}], roles:[same role shape]}; PATCH takes {expected_version, branches:[{id,role_ids}]}. Only memberships shared by actor and target within current descendants are editable; normal company roles remain untouched. Delegation permits active assignable built-ins and custom roles owned by the selected branch; inheritance permits built-ins only. A role bound to another branch is rejected. Role assignment changes revoke immediately and preserve the last administrator.

Capability checks must select the owning company of each record. API list/stock model operations must be scoped to companies authorized for the operation, including routes that check several capabilities. Global company membership must not leak through stock ACLs, exports, attachments or capabilities of another application. Requests without a declared capability scope stay on the current company. Existing single-company behavior stays intact.

Acceptance: parent-only finance capability cannot read/mutate a member branch; explicit read-only branch grant cannot write; full isolation denies branch records; controlled inheritance allows only selected roles and selected branches, revokes immediately when disabled; siblings/ancestors/unrelated membership/client company injection cannot widen; settings reject stale version, foreign ids and unauthorized actors; UI Arabic/English loading/error/save/draft and hydration boundaries. No live database or deployment.

### Contextual GET readers discovered by full-release verification

Existing PMO nested GET routes can authorize a current-company record through its contextual model policy without a company-wide read capability. Converting those readers to a mandatory company capability gate would revoke approved current-company behavior. Leaving every such reader undeclared would make an explicitly delegated branch project visible while its contextual subresources always return404.

For a known existing contextual read operation only, `declare_read_capability_scope(*keys, match='all')` declares its exact company capability keys without granting permission. Its candidate companies are the current company baseline union descendant memberships explicitly authorized for those read keys by the selected branch policy. This declaration intersects every earlier scope gate. The existing contextual record check and native model/operation fence remain mandatory; the declaration never replaces either. Unknown/undeclared routes (including chat routes with no registered company operation capability) remain current-only.

The helper is restricted to the identified GET read owners (project milestones/updates/governance/schedule/followers/timeline and task attachments/dependencies/thread readers), never mutation routes. Tests must preserve current contextual readers without a company-wide capability, allow explicitly delegated same-operation branch reads, reject wrong-capability/member-only/foreign/private-context access, preserve earlier all/any intersections and request reset, and prove read scope cannot lend a native write. No new permission key or customer setting is invented: the already approved isolated/delegated/inherited branch policy owns cross-branch variation.

Native relational identity compatibility: upstream Odoo's `base.res_partner_rule` deliberately excludes partners linked to internal users (`partner_share=False`) from its company rule so author/user references stay readable. The added fence preserves only that existing exemption for reads, still AND native rules/ACLs. Ordinary business contacts and every foreign-company identity mutation stay fenced; this is not a blanket partner-model exemption.
