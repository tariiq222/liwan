## 1. النطاق والتفويض

اعتمد المستخدم في هذه المراجعة خيار **«دورة SaaS كاملة»**: لوحة البائع والكتالوج وتسجيل/إنشاء العميل، دخول العميل والوحدات والصلاحيات، ثم متابعة العمليات والفشل والمصالحة وتغيير الاشتراك والنسخ والاستعادة والترقية.

- المستخدمون: مشغل البائع، مسؤول العميل، مستخدم العميل صاحب الدور المحدد.
- الهدف المقاس: اكتمال رحلة قابلة للاستخدام والتشغيل، لا مجرد وجود دوال أو نجاح اختبارات وحدات.
- المعايير: UI/API/queue/worker/adapter متصلة، حالات النهاية والفشل قابلة للفهم والمعالجة، تسليم آمن للعميل، عمليات لاحقة مدعومة فعلًا، وإثبات من طرف إلى طرف للبوابات الحرجة.
- هذه مراجعة فقط: لا إصلاح تطبيق أو إعدادات متتبعة، لا تغير بيانات أو خدمات، لا دمج/نشر/تنظيف موارد القبول.
- سمح المستخدم بحفظ dossier في `docs/project-closure/`، ثم وافق صراحة على توليد `.nuxt` ومخرجات فحص الأنواع المحلية لإكمال الاختبارات. الـfixtures المؤقتة خاصة بالفحوص المعزولة وحدها.
- ليست إعادة اختبار تفصيلي لكل وظيفة HR/PMO/Chat أو تدقيق اختراق/حمل/WCAG شامل. لا اعتماد إنتاج ضمنيًا ولا تفويض عملاء حقيقيين. الفوترة والدفع ليستا تنفيذًا مأذونًا؛ غيابهما موضح كي لا يُخلط كتالوج التركيب بنظام اشتراكات تجاري مكتمل.
- قرار الإغلاق أو اعتماد إصلاحات لاحقة يملكه المستخدم؛ هذا التقرير توصية مستندة إلى أدلة.

## 4. النتائج مرتبة حسب الأولوية

### SAAS-01 — حرجة لإغلاق الرحلة: التسجيل لا يصل إلى مسار managed

**نوع الدليل: مصدر + إعادة إنتاج معزولة + تأكيد مراجع مستقل.**

1. UI يأخذ الاختيارات من `/v1/targets`؛ الخدمة تعدّ فقط `inventory(config)` من `config.inventoryPath`، صيغة v2 (`http.ts:68-79,218-221`).
2. `POST /v1/tenants` يتحقق من نفس v2 ويرفض الهدف إن غاب (`:233-238`).
3. `resolveTargetLane` يستطيع قراءة v3 managed، لكن فقط لاحقًا وبعد أن لا يجد المعرف في v2 (`:82-109`).
4. تكرار الهدف في v2 لا يصلح المشكلة: `kind=customer` يُرفض عند حل lane، و`kind=scratch` يسلك scratch لا managed.

إعادة الإنتاج: descriptor v3 له digest صحيح، ويحل فعلًا إلى `compose-local`، لكن `/targets` يعيد قائمة خالية وPOST يعيد422 `inventory_target`. الاختبار يستدعي handler الحقيقي دون socket وخلفه SQL double.

**الأثر:** الإنشاء الحقيقي الموجود في العامل/المحوّل لا يمكن الوصول إليه من مسار تسجيل البائع الطبيعي في الكود الحالي. اختبارات العامل تنشئ claim/tenant مباشرة وتتجاوز هذه الوصلة.

**المطلوب لاحقًا:** توحيد اكتشاف/التحقق/تسجيل الهدف المصرح بين الواجهة وAPI وحل lane، دون تخفيف ضوابط العزل، ثم اختبار تسجيل v3 وenqueue حقيقيين.

### SAAS-02 — مرتفعة: inspect معلن لكنه يفشل عبر العامل

`managed_runtime._read_only` يعيد `ok/snapshot` مع lifecycle وdescriptor_revision ولا يعيد `profile` (`managed_runtime.py:743-755`). العامل يطلب `safeProfileFeatures(receipt.profile, ...)` ويحوّل absent profile إلى `failed` (`worker.ts:13-26,300-305`).

إعادة الإنتاج استدعت عملية Python الحقيقية من العامل مع fixture خاص وقاعدة محاكاة: **العملية failed بينما الإيصال status=ok, stage=snapshot**. الاختبار الموجود `worker-managed.test.ts:271-280` يقبل profile مصطنعًا في الفرع الناجح؛ لا يثبت أن المحوّل ينتجه.

**المطلوب لاحقًا:** عقد inspect متفق عليه وقراءة فعلية آمنة، أو إظهار محدودية metadata بصدق بدل عرضه كفحص حالة/سياسة مكتمل.

### SAAS-03 — مرتفعة: الصحة المستقلة غير موصولة

الأمر `health` في `managed_runtime.py:748-753` يعيد دائمًا conflict/`health_unverified`. helper الصحة المستخدم عند إنشاء العميل لا يُستدعى هنا. أُعيد إنتاج `failed/health/health_unverified` عبر العامل والمحوّل الحقيقيين دون Docker.

هذا لا ينفي صحة **عند الإنشاء** المثبتة سابقًا. لكنه يعني أن زر الصحة والمتابعة المستمرة لا يكملان دورة التشغيل. `health_checked_at` الذي يُسجل عند create تاريخي، وليس مراقبة متجددة.

### SAAS-04 — مرتفعة: رفض آمن يترك حالة provisioning بلا نهاية

- `worker.ts:308-315` يضع `deployment_ready=false` لكل create غير مثبت، ثم يحذفه فقط لثلاثة أخطاء preflight خاصة.
- `finishClaim` يعيد tenant إلى registered عند فشل create فقط إذا `deployment_ready !== false` (`:247`)؛ وينقله إلى intervention فقط عندما تكون **حالة العملية** needs_intervention (`:248`).
- بقية الرفض الآمن، مثل `port_shared` أو `database_exists`، يعطي failed + changed=false + deployment_ready=false، فلا يحدث أي انتقال لحالة tenant.
- `http.ts:168` يرفض create التالي لأن tenant لم يعد registered؛ ليست هذه حالة حجر معلنة لها عملية جارية.

**إعادة الإنتاج:** المحوّل الحقيقي مع probe يحاكي منفذًا مشغولًا وrunner/resolver يرفضان أي أثر. النتيجة `failed/preflight/port_shared/changed=false`؛ لم يصدر العامل أي SQL لإعادة الحالة، وبقيت قيمة fixture `provisioning`. لم تُستخدم قاعدة PostgreSQL حقيقية.

**المطلوب لاحقًا:** فصل رفض مثبت قبل الأثر عن نشر غير مكتمل وأثر غير مؤكد، مع انتقال نهائي صحيح واختبارات جميع فئات الرفض، دون تحويل الحجر غير المؤكد إلى إعادة آلية.

### SAAS-05 — مرتفعة: عمليات ما بعد الإنشاء غير مكتملة

`http.ts:169` يرفض `tenant.entitle/backup/restore/upgrade` لمسار compose-local. توجد حراسات رفض إضافية في العامل والمحوّل. مع ذلك تقدم صفحة العميل `backup` و`tenant.entitle` في قائمة العمليات بحسب حالة tenant/نوعه لا بحسب lane المدعوم (`tenants/[id].vue:95-101`)؛ الطلب مرفوض وليس عملية قابلة للاستخدام. restore/upgrade لهما عقود API لكن لا مسار UI تنفيذي مماثل.

التمييز المهم:

- **الكتالوج موجود** ويحدد الوحدات/الميزات. ليس صحيحًا أنها غير منفذة كليًا.
- tiers في `platform.json:5` تسميات تركيب وليست باقات تجارية مسعرة؛ العدد والسعة الافتراضيان null. لا يوجد اختيار باقة/دفع/تجديد تجاري متكامل.
- محرك Odoo يملك active/suspended/expired وحراسات (`entitlement_service.py:54-88`)؛ لكن ذلك ليس رحلة تشغيل تجديد/تعليق متصلة من control-plane.
- أدوات scratch للنسخ والاستعادة والترقية موجودة؛ إخراجها صريح بـ`UNVERIFIED` و`recovery_ready=False` والاستعادة إلى قاعدة scratch منفصلة (`operator.py:692-765`). نجاحها لا يثبت نسخ عميل managed أو استرداد الإنتاج.

**المطلوب لاحقًا:** تنفيذ وربط العمليات المعتمدة واختبار نتائجها، أو تضييق نطاق المنتج صراحة وإخفاء/شرح غير المدعوم. لا إزالة حواجز scratch لتجاوز الفجوة.

### SAAS-06 — مرتفعة: تدخل مطلوب دون مسار مصالحة مكتمل

الحجر والأقفال ورفض mutation المتعارضة نقاط قوة. لكنها لا تساوي اكتمال الاسترداد:

- صفحة العملية تعرض تنبيه reconcileHint، دون إجراء مصالحة (`operations/[id].vue:35-38,97-105`).
- retry متاح فقط لعمليات القراءة الفاشلة inspect/health؛ ليس create ولا حالة needs_intervention (`http.ts:289-297`).
- status في المحوّل يقرأ الإيصال ولا يفحص العالم ولا يفك الحجر ولا يفعّل العميل، صراحة (`managed_runtime.py:764-770`).
- enum الطلبات العامة لا يضم `status` (`packages/commercial-contracts/src/index.ts:26-34`). فروع status الباقية في العامل ليست دليلًا على API مصالحة قابل للوصول. **لم نعدّ اختلاف تلك الفروع خطأ حيًا مستقلًا.**

يلزم workflow/operator runbook موثوق يجمع الدليل، يقرر retry/recovery/تعطيل، ويحدث حالات control-plane/journal باتساق وتفويض. لا يُنصح بتعديل receipts يدويًا أو اعتبار صحة لاحقة نجاحًا رجعيًا.

### SAAS-07 — مرتفعة: تسليم العميل ليس رحلة مكتملة

المحوّل يهيئ كلمة مرور فعلية لـ`base.user_admin` ويتحقق من hash. ليس صحيحًا «لا توجد تهيئة دخول» مطلقًا. لكن ذلك الحساب مضاف إلى vendor support (`odoo-addons/nasq_core/data/res_users_data.xml:3-5`)؛ ليس إنشاء مسؤول عميل محدود الصلاحيات ثم دعوته.

عقود tenant/operation والصفحات لا تعطي customer URL/domain أو دعوة/تفعيل/تسليم اعتماد آمن وخطوة «ابدأ الاستخدام» (`commercial-contracts/src/index.ts:38-49`؛ `tenants/[id].vue:106-167`؛ `operations/[id].vue:122-127`). إخفاء السر من الإيصال صحيح أمنيًا؛ لا يُصلح بإظهاره في JSON.

توجد صفحة login وMFA وتغيير كلمة مرور وإدارة أدوار عامة. **لم يثبت أن عميلًا جديدًا يتسلم حسابه ويسجل الدخول بدوره وتظهر له وحداته فقط**. فحص HTTP للصفحة والتحقق من hash ليسا دليل جلسة متصفح أو صلاحيات مستخدم عادي؛ `managed_health.py:192-197` يصرح بذلك.

### SAAS-08 — متوسطة: متابعة التقدم تتوقف بصمت نسبيًا
