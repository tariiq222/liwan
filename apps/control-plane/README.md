# Nasq control service

This headless PostgreSQL service holds vendor grants, tenant registration, catalog state, operations and audit separately from the vendor company's Odoo database and all customer databases. Only a trusted same-origin BFF may call `/v1/*`. `GET /healthz` checks database liveness and exposes no tenant data.

Node 22+ and PostgreSQL are required. Configure `CONTROL_DATABASE_URL` for a dedicated database, `CONTROL_INSTALLATION_ID` to the configured vendor Odoo installation ID, `CONTROL_SERVICE_KEY` to a random secret of at least 32 bytes, `NASQ_CLI_INVENTORY` to the private version-2 operator inventory, `NASQ_CLI_STATE_DIR` to its private state directory, and `NASQ_REPOSITORY_ROOT` to this checkout. Optional `CONTROL_HOST`/`CONTROL_PORT` default to `127.0.0.1:4179`. Non-loopback binding requires `CONTROL_TLS_KEY` and `CONTROL_TLS_CERT`. `NASQ_CLI_PYTHON` selects the trusted Python executable.

Run `npm -w apps/control-plane run migrate`, then the API with `npm -w apps/control-plane run dev` and the independent worker with `npm -w apps/control-plane run worker`. Bootstrap the first vendor owner out of band with `npm -w apps/control-plane run admin -- bootstrap-owner <email> <display name> <reason>`, which prints a one-time enrollment link; a locked-out account is reset with `admin -- reset-account <email> <reason>`; this CLI command is also the only recovery path for a lost last owner, because the API refuses a self-reset by the last active owner (409 `last_owner`). Both need the `ADMIN_*` settings. A vendor's authority is computed from its account's roles and status on every request and every queued-work recheck (there is no stored copy); a worker also rechecks the account's role before invoking the operator. `admin -- catalog-import <version> <reason>` imports a draft from trusted source. Vendor operators then validate and publish it through the API. `admin -- approve-restore <tenant-uuid> <successful-backup-receipt-id> <reason>` creates a one-hour persisted, single-use approval.

The BFF signs the exact method, full path/query and raw request body using `@nasq/commercial-contracts/server`. The assertion carries only the validated positive Odoo user ID and configured installation ID. A service nonce is stored in PostgreSQL; grants are never inferred from Odoo roles or email. The worker claims the durable queue under a PostgreSQL advisory lock per inventory target. Mutation success requires the real operator's matching durable receipt. Expired mutation leases become `needs_intervention` and are never retried automatically. Public results whitelist receipt fields and exclude local paths or child logs.

Schema migrations 1 and 2 are `src/schema.sql` and `src/schema_002.sql`, recorded in `schema_migrations`. Subsequent schema changes require a new numbered migration. A CP2 receipt that reports `deployment_ready:false` leaves provisioning in `needs_intervention`; it does not claim a usable frontend, domain or vendor admin login. Focused integration tests require `CONTROL_TEST_DATABASE_URL` pointing to a new loopback database named `nasq_control_scratch_<suffix>`; the test refuses any other URL before migrations or cleanup.
