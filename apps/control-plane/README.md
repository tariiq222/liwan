# LiwanOS control service

This headless PostgreSQL service holds vendor grants, tenant registration, catalog state, operations and audit separately from the vendor company's Odoo database and all customer databases. Only a trusted same-origin BFF may call `/v1/*`. `GET /healthz` checks database liveness and exposes no tenant data.

Node 22+ and PostgreSQL are required. Configure `CONTROL_DATABASE_URL` for a dedicated database, `CONTROL_INSTALLATION_ID` to the configured vendor Odoo installation ID, `CONTROL_SERVICE_KEY` to a random secret of at least 32 bytes, `LIWAN_CLI_INVENTORY` to the private version-2 operator inventory, `LIWAN_CLI_STATE_DIR` to its private state directory, and `LIWAN_REPOSITORY_ROOT` to this checkout. Optional `CONTROL_HOST`/`CONTROL_PORT` default to `127.0.0.1:4179`. Non-loopback binding requires `CONTROL_TLS_KEY` and `CONTROL_TLS_CERT`. `LIWAN_CLI_PYTHON` selects the trusted Python executable.

Run `npm -w apps/control-plane run migrate`, then the API with `npm -w apps/control-plane run dev` and the independent worker with `npm -w apps/control-plane run worker`. Bootstrap the first vendor owner out of band with `npm -w apps/control-plane run admin -- bootstrap-owner <email> <display name> <reason>`, which prints a one-time enrollment link; a locked-out account is reset with `admin -- reset-account <email> <reason>`; this CLI command is also the only recovery path for a lost last owner, because the API refuses a self-reset by the last active owner (409 `last_owner`). Both need the `ADMIN_*` settings. A vendor's authority is computed from its account's roles and status on every request and every queued-work recheck (there is no stored copy); a worker also rechecks the account's role before invoking the operator. `admin -- catalog-import <version> <reason>` imports a draft from trusted source. Vendor operators then validate and publish it through the API. `admin -- approve-restore <tenant-uuid> <successful-backup-receipt-id> <reason>` creates a one-hour persisted, single-use approval.

The BFF signs the exact method, full path/query and raw request body using `@liwan/commercial-contracts/server`. The assertion carries only the validated positive Odoo user ID and configured installation ID. A service nonce is stored in PostgreSQL; grants are never inferred from Odoo roles or email. The worker claims the durable queue under a PostgreSQL advisory lock per inventory target. Mutation success requires the real operator's matching durable receipt. Expired mutation leases become `needs_intervention` and are never retried automatically. Public results whitelist receipt fields and exclude local paths or child logs.

Schema migrations 1 and 2 are `src/schema.sql` and `src/schema_002.sql`, recorded in `schema_migrations`. Subsequent schema changes require a new numbered migration. A CP2 receipt that reports `deployment_ready:false` leaves provisioning in `needs_intervention`; it does not claim a usable frontend, domain or vendor admin login. Focused integration tests require `CONTROL_TEST_DATABASE_URL` pointing to a new loopback database named `liwan_control_scratch_<suffix>`; the test refuses any other URL before migrations or cleanup.

The vendor configures the platform AI at `/v1/platform/ai-provider` (`GET`, `PATCH`, `GET …/presets`, `POST …/models`, `POST …/test`; capability `vendor.ai.manage`, held by the owner role only, so every write and every call that sends a key to a provider needs a fresh passkey). The configuration is several providers (each a catalog preset with its endpoint and its own key), a list of models (a provider, a name at it, optional prices in USD per million tokens), one margin (`margin_bps`, 0 to 10000) and a map: `routes.default` plus, for each quality level (`economical`, `balanced`, `best`), a model per capability (`quick`, `standard`, `analysis`, `writing`); a cell left out falls back to the balanced one, then to the default. `GET` returns all of it (per provider only `configured` and the last four characters of the key); one `PATCH` replaces it atomically after checking that every model names a provider and every route a model. `models` and `test` take the id of a saved provider and use its stored key; a successful `test` of a saved model records whether the reply carried token counts (`usage_reported`, kept while the model and its provider's endpoint and token-count option stay the same). A route that is new or points at another model (or at a model whose name or provider endpoint changed) must reach a model that has an input and an output price and whose last test saw token counts (`model_not_priced`, `model_not_tested`); a route unchanged from the stored configuration is accepted as it is, so the unpriced `main` model carried forward by the migration keeps running, uncharged, while the vendor adds and tests a replacement and switches the default in a later save. A save with no default route is stored as `incomplete` and writes no file, so a provider can be saved and tested before anything is routed. The control plane connects only to public addresses, checked where the connection is made (`ai-provider/guarded-fetch.ts`: loopback, private, link-local, unspecified, metadata and IPv4-in-IPv6 forms are refused, redirects are not followed, replies are capped at 1 MB), with the self-hosted Ollama preset as the one exception. Keys are sealed with `ADMIN_SECRET_KEY` (AES-256-GCM, `admin-auth/crypto.ts`) in `ai_provider` and never returned; the tables are `ai_provider_config`, `ai_provider`, `ai_model` and `ai_route` (schema 42, which carried the former single provider forward as provider and model `main`); each save is audited with counts and without any key. When `LIWAN_AI_PLATFORM_PROVIDER_PATH` (absolute) is set, a complete save also replaces that JSON file atomically (mode 640, only the providers and models some route uses) before it commits, and the shared AI service reads it (`apps/ai-service/README.md`, "Platform provider"): the product keeps running on the last file when the control plane is down. Without the variable the choice is stored and shown as not delivered. The catalog also decides whether each provider's stream is asked for token counts (`stream_usage`, which cost and charge depend on): on for every hosted preset, off for Ollama (which reports them itself) and for a custom endpoint unless the vendor ticks it; the connection test streams a reply as the service does and returns `usage_reported`.

AI balance top-ups: the vendor edits the offered amounts, the SAR per USD rate and the trial and monthly free allowances at `/v1/commercial/ai-billing-settings` (`GET` with `vendor.read`; `PATCH` with `vendor.billing.manage` and a fresh passkey, audited; a change that alters the allowances is pushed to every tenant with an applied subscription in the same transaction, one small job each). A customer buys a top-up as the one-time `ai_topup` line of a quote (`ai_topup_minor`); the quote line carries the units and rate it was shown, and payment records exactly those in `ai_topups`. Every delivery to a tenant (fulfilment, trial and suspension expiry pushes, restore repair, ledger pushes) carries `ai.balance.granted`, `ai.allowance.trial` and `ai.allowance.monthly` computed from that ledger and the settings at that moment, never from the subscription snapshot. A refund of a top-up order by any route (`POST /v1/commercial/ai-topups/:order_id/refund`, the generic invoice refund, a provider refund or chargeback, a failed fulfilment) marks its ledger row refunded and queues a push.

How the tenant is kept equal to the ledger: every ledger or settings event queues one AI-only push (`ai_push`) for the tenant's applied revision, under the same per-tenant lock a claim and a completion take, unless a queued, dispatchable push for that binding and revision already exists. Every job reads the live values when it is claimed, and a completed delivery is compared with the live values and queues a push when they differ. A push may run behind a quarantined job but never behind a running one, and an expired one is failed, not quarantined. The usage collector then compares the three AI values each live tenant reports (`trialing`, `active`, `past_due`) with the ledger on every pass and queues a push on a mismatch, logging which keys differed: a log line means an event path missed a change. The sweep covers every tenant that can still be used (any subscription state but `suspended`, the same rule that maps a subscription to its tenant status). Correction takes seconds through the event path; a tenant whose push failed, or could not be queued, is put first in the collector's order and is observed in the next pass (about five minutes); the full cycle (at most 50 tenants per pass, least recently attempted first, so about 100 minutes for 1,000 tenants) is only the backstop for an event path that was missed. A restore is not published until its restored database holds the live values (the readiness check queues a new repair per differing observation, reusing only one that is still outstanding).

Open points and limits, stated on purpose:
- The cap is on lifetime purchases: a delivered AI value never exceeds 1,000,000,000 units (about 10,000 USD of top-ups per customer). A quote that would pass it is refused, a payment that would pass it is credited back, and a ledger already over it is delivered clamped. Whether the cap should apply to the current balance instead is an open product decision.
- `units_used` at refund time is supplied by the operator, because the control plane cannot read tenant usage (R5). There is no automatic check.
- Under a VAT-inclusive pricing policy the units are computed on the gross amount of the line. The active policy today charges no tax.
