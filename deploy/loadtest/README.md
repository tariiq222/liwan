# مجموعة اختبار الحمل (Load-Test Kit)

أدوات قياس سقف التزامن في LiwanOS بهدف التحقق من قدرة المنصة على خدمة ما يقارب **5000 مستخدم متزامن**، وتحديد نقطة الانهيار الفعلية قبل أي نشر إنتاجي.

## المتطلبات

- `k6` عبر Homebrew: `brew install k6`
- `node` (لتشغيل `probe.cjs`)
- نسخة Odoo تجريبية (scratch) + نسخة Nuxt تعملان محليًا — لا تُجرى الاختبارات أبدًا على قاعدة بيانات الإنتاج أو `odoo19`.

## السكربتات

جميع سكربتات k6 تقرأ `BASE` (الافتراضي `http://[::1]:3100`) و`LOGIN` و`PASSWORD`، و`LOGIN` و`PASSWORD` **إلزاميان**: لا قيمة افتراضية لهما، وتشغيل السكربت بدونهما يتوقف فورًا برسالة تحدد المتغير الناقص. القاعدة الواحدة في `k6/credentials.js` وتستوردها السكربتات الثلاثة.

> **بيانات الاعتماد:** المستودع عام، ولذلك لا تُحفظ أي بيانات اعتماد فيه ولا تُقبل قيمة افتراضية.
> مرّر `LOGIN` و`PASSWORD` لحساب اختبار مؤقت في القاعدة المؤقتة التي تختبرها، ولا تستخدمها أبدًا
> على أي حساب حقيقي — staging أو إنتاج.

```bash
export LOGIN='scratch-account-login'
export PASSWORD='scratch-account-password'

# دخان سريع: التحقق من أن الخدمة تستجيب
k6 run k6/smoke.js

# تدرّج الحمل: صعود تدريجي من 100 إلى 5000 VU
k6 run k6/ramp.js

# عاصفة تسجيل الدخول: ضغط مسار المصادقة تحديدًا
k6 run k6/auth-storm.js

# مسبار node:http: طلبات متزامنة بجلسة مصادقة جاهزة
BASE=http://[::1]:3100 CONC=100 TOTAL=200 \
COOKIE="session_id=..." PATH_=/api/v1/... node probe.cjs
```

متغيرات `probe.cjs`: `BASE` (العنوان)، `CONC` (التزامن)، `TOTAL` (إجمالي الطلبات)، `COOKIE` (كوكي الجلسة)، `PATH_` (المسار المطلوب).

### الغلافان الجاهزان

```bash
# مسبار متدرج: يمر على مستويات التزامن ويطبع جدولًا لكل مستوى
./run-probe.sh http://[::1]:3100 /api/v1/me "session_id=..." '100 500 1000 2000 5000'

# سلّم k6 مع حفظ السجل والملخص في results/ باسم مؤرّخ
./run-ramp.sh http://[::1]:3100 ramp    # smoke | ramp | storm
```

`run-ramp.sh` يقرأ `LOGIN` و`PASSWORD` من البيئة ويرفض التشغيل إذا لم تصدّرهما، ويمرر `BASE` وحده بـ`-e`. متغيرات البيئة تصل إلى k6 تلقائيًا، فلا تُمرَّر بيانات الاعتماد بـ`-e` كي لا تظهر في سطر أوامر العملية.

### قالب إعداد Odoo

`odoo-loadtest.conf` قالب جاهز لوضع workers — كل المسارات فيه قيم بديلة (`<...>`) تُملأ قبل التشغيل، ومعه تُطبق قاعدة `PGGSSENCMODE=disable` أدناه.

### pgbouncer (اختياري — لفك قيد `max_connections`)

`pgbouncer-loadtest.ini` قالب مُجرَّب مع Odoo 19 في وضع transaction pooling: القراءات والكتابات وcron نجحت في اختبار الدخان. انتبه لملاحظتين موثقتين فيه: `db_host = 127.0.0.1` صراحةً في إعداد Odoo، وتمرير قاعدتي `postgres`/`template1` في قسم `[databases]`. التوافق العميق (advisory locks بين العمال وNOTIFY) يحتاج فترة soak قبل الإنتاج.

## إعداد Odoo في وضع workers

- `workers = N` (عدد العمليات العاملة).
- `db_maxconn` لكل عامل: يجب أن يبقى حاصل `workers × db_maxconn` أقل من هامش `max_connections` في PostgreSQL، وإلا استُنفدت الاتصالات وانهار الطلب فورًا.
- **إلزامي:** ضع متغير البيئة `PGGSSENCMODE=disable` قبل تشغيل Odoo. سبب واحد: في macOS ينهار العامل المشتق (forked) داخل GSSAPI/krb5 عبر XPC بعد `fork()` (`pg_GSS_have_cred_cache → xpc_connection_resume → Data Abort`)، وتعطيل تشفير GSS يمنع المسار المنهار. الوضع المُخيّط (threaded) غير متأثر لأنه لا يستخدم fork.

## النتائج المقيسة

جميع القياسات بتاريخ 2026-10-22 على macOS arm64 (14 نواة / 24GB)، بـ k6 v2.3.0 + مسبار `node:http`، على قاعدة scratch باسم `liwan_scratch_deploy_performance`.

| السيناريو | النتيجة |
| --- | --- |
| Odoo مُخيّط (db_maxconn 64 ثم 80) | سقف صلب ~160 طلبًا مصادقًا متزامنًا/عملية؛ `psycopg2 PoolError` يُرفع فورًا بلا طوابير انتظار (42,414 حدثًا) |
| k6 تدرّج 100→5000 VU (مُخيّط) | فشل 99.7% من ~898 ألف طلب؛ p95 للطلبات الناجحة 20.6s→37.1s |
| عاصفة الدخول عند 5000 متزامن | ~40 دخولًا ناجحًا/ثانية (نجاح 34%، زمن استجابة 17–40s) |
| workers=12, db_maxconn=4, conc=100 | 200/200 ناجح — p50 643ms، p95 1.36s |
| workers=12, conc=500 | 108/1000 فقط أجابوا (البقية TCP resets — فيض accept-backlog) |
| workers=12, conc=1000 | 120/2000 |
| workers=12, conc=2000 | 132/4000 |
| workers=12, conc=5000 | 204/10000 |
| **بوابة التزامن في Nuxt** (`withUpstreamSlot` على مساري `/api/v1` و`/api/auth/login`) + Nuxt production + workers=32 | conc=500: **1000/1000 ناجح** (p50 1.9s)؛ conc=1000: 2000/2000؛ conc=2000: 4000/4000 (p50 7.5s)؛ conc=5000: 7861/10000 (البقية مهلة طابور 15s مرتبة — صفر TCP resets) |
| نفس الحزمة مع workers=48 | بلا تغيّر يُذكر (~270–318 طلب/ث) — السقف صار CPU الجهاز (14 نواة مشتركة) لا عدد العمال |
| k6 ramp كامل حتى 5000 VU على الحزمة المبوّبة | فشل 68.4% (انتظار طوابير SSR الثقيلة) مقابل 99.7% فشل فوري قبل الإصلاح؛ PoolError هبط من 42,414 إلى 36 |

**الخلاصة:** الوضع المُخيّط يعلق عند ~160 طلبًا متزامنًا لكل عملية بفشل فوري. بوابة التزامن في Nuxt حوّلت الانهيار إلى تدهور رشيق (صفر انقطاعات حتى 2000 متزامن على مسار API)، والسقف المتبقي على هذا الجهاز هو CPU (~280–320 طلب/ث). الوصول إلى 5000 مستخدم يحتاج توسعًا أفقيًا (عدة مضيفات) لا ضبطًا أحادي الجهاز.

## السياق

هذه الأدوات ضمن worktree `deploy-performance` على الفرع `codex/deploy-performance`، في المسار `deploy/loadtest/` (`k6/smoke.js`، `k6/ramp.js`، `k6/auth-storm.js`، `probe.cjs`، `run-probe.sh`، `run-ramp.sh`، `odoo-loadtest.conf`)، والتقارير في `results/`.
